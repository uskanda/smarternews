# Design

## Context

動機は `proposal.md` のWhyを参照する。決定は `grilling.md` のとおりである。

- 項目ごとの表示の設定は、表 `list_views` に1項目1行で保存している。設定が既定の項目は行を持たず、行のある項目だけをAPIと設定ファイルに出す（移行015と、#48の `design.md`）。#48の `design.md` は、形式を列1つとして足す前提で書かれている
- Webの一覧は50件ずつ取得し、本文は記事ごとに取得する。本文のペイン（`ArticleView`）は、記事を描くと要約の依頼と翻訳を始める。開いた記録の送信と、全文を待つ記事の取得の依頼は、記事を開いたときに `ReaderPage` が送る
- スクロールで既読にする仕組み（#50）は、一覧の `ul` の子を行として測り、上端を越えた行を既読にする

## Goals / Non-Goals

**Goals:**

- 形式を並び順と同じ単位で保存し、Webとアプリのどちらから変えても、もう一方の設定が残ること
- 「展開」で、読まずに通り過ぎた記事へ費用のかかる処理を走らせないこと

**Non-Goals:**

- アプリでの形式の切り替えと表示
- 「展開」での記事の仮想化（描いた記事を画面の外で外すこと）

## Decisions

### 保存：`list_views` に列を足す

移行041で、`ALTER TABLE ... ADD COLUMN` により `format` 列を足す。値は `standard`、`compact`、`expanded` のどれかに限り、既定は `standard` とする。

- 計画では、移行031と同じく表を作り直すとしていた。作り直しが要るのは既存のCHECKを変えるときである。新しい列に自分のCHECKを付けて足すことは、SQLiteでもそのままできる。既存の行は既定値の `standard` を受け取る
- 番号は、計画の時点の032ではなく、origin/mainの最大の040の次の041にした

`setListView` は、渡されなかった値を保存済みの値のまま残す。並び順と形式の両方が既定に戻った行だけを消す。行の有無で「変えた項目」を表す今の約束を保つためである。

### APIの形

`listViewSchema` の `format` は `.default("standard")` にする。形式を返さない古いサーバーの応答も、新しいアプリでそのまま読めるようにするためである。部分更新の `listViewUpdateSchema` には、省略できる `format` を足す。

### 画面への先行の反映を1つの関数にまとめる

Webとアプリは、表示の設定の変更を、サーバーの応答より先に画面へ反映している。今の実装は項目の行を `{ key, sort }` で置き換えるので、アプリで並び順を変えると、Webで選んだ形式が画面の上で消える。

clientに `withViewChange(views, key, patch)` を置く。変えない値を残し、両方が既定に戻った項目だけを外す。Webの `useListViewChange` と、アプリの `useListSortChange` の両方がこれを使う。

### 形式を出す項目

形式のメニューは、`hasSortMenu` が真の項目だけに出す。それ以外の項目は `standard` として扱う（`listFormatOf`）。保存の単位を並び順と同じとした決定のとおりで、表の制約を広げずに済む。

### メニューの共通化

`SortMenu` の作りを、値の型を引数に取る `ChoiceMenu` へ移す。並び順のメニューと形式のメニュー（`FormatMenu`）の両方がこれを使う。キー操作と見た目が2つで食い違わないようにするためである。

### タイトルのみ

`ArticleRow` に `compact` を足し、1段の行を描く。重要度の印、選択中の印、未読と重要度の読み上げは、「標準」の行と同じ部品を使う。

### 展開：表示範囲に入るまで記事を描かない

- 「展開」の各記事は `ExpandedArticle` が描く。表示範囲に入るまでは、一覧の要約（`ArticleSummary`）だけで補足、見出し、要約を出し、記事を取得しない。`IntersectionObserver` で初めて表示範囲に入ったら、`ArticleView` を描く
- `ArticleView` は、描かれたときに要約の依頼と翻訳を始める。描くのを遅らせるだけで、要約と翻訳の対象は、表示範囲へ入った記事だけになる。記事が届いたら、`ReaderPage` が開いた記録を送る。全文を待つ記事なら、全文の取得も頼む
- 表示範囲に入る前の記事は、高さを画面の半分ほど取っておく。短い代わりの行のままだと、10件がまとめて表示範囲に入り、すべての記事を取得してしまうからである
- 一度描いた記事は、一覧を読み直すまで描いたままにする。スクロールで戻ったときに描き直さないためである

10件をすべて描き、要約と翻訳だけを遅らせる案も考えた。この案は、`ArticleView` の中の自動の処理へ表示範囲の状態を渡す必要があり、本文のペインの振る舞いまで変わる。そのため選ばなかった。

### 展開：読み込みの件数

`useArticleList` に1ページの件数を渡せるようにし、「展開」では10件にする。件数の違う一覧はページの切れ目が違うので、キャッシュのキーに件数を足して分ける。50件のときはキーを変えない。

表示の設定が届くまで一覧を取得しない今の仕組みにより、50件で取得してから10件で取り直すことはない。末尾に近づいたら続きを読む仕組みは、今の一覧と同じものを使う。

### 展開：対象の記事とキー

- 対象の記事は、表示範囲の上端を越え切っていない最初の記事とする。#50の `firstRowBelow` で求め、スクロールのたびと、一覧が変わるたびに求め直す
- `j`・`k` は、対象の次と前の記事の見出しを上端へ送り、その記事を既読にする。対象の見出しが上端より上にあれば、`k` はまず対象の見出しへ戻る
- 最後の記事での `j` は、今の `moveOn` で続きを読み込む。届いた最初の記事が描かれてから、その見出しを上端へ送る
- `Space` と `Shift+Space` は、本文のペインと同じく1画面より1行少ない分だけ、一覧を送る
- `s`、`m`、`o` は対象の記事の行で働く。`x`、`w`、`c` は対象の記事で働く。対象の記事は表示範囲にあるので、取得済みである
- 見出しは押せるボタンにする。押すと、`j` と同じく見出しを上端へ送って既読にする

### 展開：本文のペインと記事のパス

「展開」では本文のペインを閉じる。記事の中のリンクから来て、パスで記事が指定されたときは、狭い画面と同じく、その記事だけを一覧へ戻るリンクとともに表示する。`ReaderPage` の「1つのペインだけを出す」条件を、狭い画面のときと「展開」のときの両方へ広げて実現する。

### 配信された内容の表示の切り替え

全文と配信された内容の切り替えは、今は開いた記事1つ分だけを覚えている。「展開」では複数の記事が並ぶので、記事のIDの集合で覚える。記事を開き直すと消える振る舞いは変えない。

## Risks / Trade-offs

- 危険：多くの記事を読み進めると、描いた記事が増えて重くなる。→ 対策：10件ずつ読み込み、表示範囲に入った記事だけを描く。仮想化はNon-Goalsとし、重さが問題になったら別のissueで扱う。
- 危険：表示範囲に入る前の記事の取っておく高さが、実際の高さと違う。→ 対策：記事は下から表示範囲に入るので、高さが変わっても上端より上はずれない。
- 危険：アプリの古い版は `format` を知らない。→ 対策：古い版は知らない項目を読み飛ばす。並び順を変えると画面の上だけ形式が消えるが、部分更新なのでサーバーは形式を残す。

## Migration Plan

- 移行041は列を足すだけで、既存の行は `standard` になる。戻すときは、古い版が `format` 列を読まないので、そのまま動く。
- 設定ファイルは、`format` のない古いファイルも読める。新しいファイルを古いサーバーに読み込むと、`format` は読み飛ばされ、並び順だけが入る。
