# Design

## Context

動機は `proposal.md` のWhyに書いた。

- フィルターの入力欄は `apps/web/src/settings/FilterForm.tsx` にある。設定の画面と、選んだ文からフィルターを作るダイアログが共有する。
- 入力を変える操作は、すべて `change` を通る。`change` は下書きを書き換え、確認の結果、欄ごとの誤り、全体の誤りを消す。
- 件数の確認は `check` が担う。`api.previewFilter` の応答を待ち、成功なら件数を、失敗なら `refused` で誤りを表示する。応答が届くまで、ボタンは `busy` で押せない。

## Goals / Non-Goals

**Goals:**

- 確認の応答を待つ間に入力を変えたとき、古い入力に対する件数と誤りを出さない。

**Non-Goals:**

- 保存の応答の扱い。保存は送った内容を確かに保存しており、その結果を知らせる通知は、入力が変わっても正しい。
- 問い合わせの中断。
- 待つ間の表示の変更。

## Decisions

### 下書きの版を数で持つ

版は `useRef` の数で持つ。`ReaderPage.tsx` の `keyStep` と同じ書き方である。
`change` が呼ばれるたびに1足す。新しいフィルターを保存して下書きを空に戻すときも1足す。
状態にしないのは、版が変わっても描き直す必要がないためである。

### 確認は版を控え、変わっていれば応答を捨てる

`check` は問い合わせる前に版を控える。応答が届いたときに版が変わっていれば、成功と失敗のどちらの応答でも何もせずに戻る。

- 成功の応答では、件数、欄ごとの誤り、全体の誤りを書き換えない。件数の欄は `change` が消したままになる。
- 失敗の応答では、`refused` も件数の消去も呼ばない。古い条件に対する誤りを、新しい条件の欄の横に出さないためである。
- `busy` は版にかかわらず `finally` で戻す。戻さないとボタンが押せないままになる。

### 問い合わせは止めない

`AbortController` で問い合わせを止める案は採らない。版を比べれば足りる。止めるには `api.previewFilter` の引数を変える必要があり、変更が広がる。

## Risks / Trade-offs

- 待つ間に入力を変えると、確認の結果は何も出ない。利用者はもう一度確認を選ぶ必要がある。ボタンは応答が届くと押せるようになる。
