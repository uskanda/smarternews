# Design

## Context

追加のフォーム（`AddFeedForm.tsx`）は、設定の画面と、カテゴリの一覧の上のダイアログで使う。
フォームは3種類の要求を出す。フィードを探す `discoverFeeds`（数秒）、候補を求める `pageCandidates`（数分）、見本を求める `pagePreview` である。
どの要求も、応答が届いたときに、要求したときの入力と今の入力を比べていない。
`api` クライアントには、要求を取り消す口がない。

## Goals / Non-Goals

**Goals:**

- 入力を直したあと、またはフォームが消えたあとに届いた応答が、画面の状態にも登録にも反映されないようにする。
- 探している数秒の間、URLを直せないことを、フォーカスを奪わずに示す。

**Non-Goals:**

- サーバーの側の処理を止めること。
- 候補を待つのをやめるボタン。

## Decisions

### 応答を捨てる連番

要求ごとに `useRef` の連番を進め、応答が届いたときに、要求したときの番号と今の番号を比べる。違えば、状態に触れずに終える。
番号を進めるのは、新しい要求を出すとき、入力を直したとき、部品が消えるとき（`useEffect` の後始末）である。

- `useCandidates`：`ask` と `reset` と部品が消えるときに進める。古い応答では `null` を返す。編集の画面の「候補を出し直す」にも同じ守りが入る。
- `SelectorEditor` の見本：`look` と欄の変更と部品が消えるときに進める。欄を直したときは `busy` も解き、直したあとの組ですぐに「見本を見る」を押せるようにする。古い応答は、見本、失敗、`onTested`、`busy` のどれにも触れない。
- `AddFeedForm` のフィードを探す要求：URLの欄の変更と、部品が消えるときに進める。古い応答は、購読、フィードの一覧、見つからない旨のどれにも触れない。`run` の失敗の表示と `busy` の解除も、古い要求では行わない。

代わりに `AbortController` で要求を取り消す案もあった。`api` クライアントに取り消しの口を足す必要があり、取り消してもサーバーの側の処理は止まらない。応答を捨てれば、画面の側の効果は同じである。

### URLの欄は読み取り専用

フィードを探している間（`busy` で、まだページを選んでいないとき）、URLの欄に `readOnly` を付ける。
`disabled` にするとブラウザーがフォーカスを外し、Enterで送った人が応答のあと欄へ戻る操作が要る。読み取り専用ならフォーカスも読み上げも残る。
共通の入力欄に `read-only:` の見た目（文字を `on-surface-muted`、枠を `outline`）を足し、止まっていることを見て分かるようにする。
候補を待つ間は編集できるままにする。URLを直すことが、待つのをやめる手段になる。

### 最新のカテゴリと切り替えで登録する

`subscribe` は、カテゴリと3つの切り替えを、`add` を呼んだ時点の値ではなく、`useRef` に写した最新の値から読む。
探している間に変えた値が、画面に見えているとおりに登録される。

## Risks / Trade-offs

- [古い要求のサーバーの処理は続く] → 候補の生成ではLLMを1回使ったまま捨てることになる。URLを直す人は、その候補を求めていないので受け入れる。
- [読み取り専用の欄に、入力できない理由の文言はない] → 待つ間はボタンが無効になり、状態は数秒で戻る。見た目で止まっていることを示す。
