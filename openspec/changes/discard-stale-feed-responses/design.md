# Design

## Context

追加のフォーム（`AddFeedForm.tsx`）は、設定の画面と、カテゴリの一覧の上のダイアログで使う。
フォームは3種類の要求を出す。フィードを探す `discoverFeeds`（数秒）、候補を求める `pageCandidates`（数分）、見本を求める `pagePreview` である。
どの要求も、応答が届いたときに、要求したときの入力と今の入力を比べていない。
画面がAPIを呼ぶ部品（`@smarternews/client` の `api`）は、要求を取り消す口を持たない。

## Goals / Non-Goals

**Goals:**

- 入力を直したあと、またはフォームが消えたあとに届いた応答を、画面の状態と登録のどちらへも反映しない。
- 探している数秒の間、URLを直せないことを、フォーカスを奪わずに示す。

**Non-Goals:**

- サーバーの側の処理を止めること。
- 候補を待つのをやめるボタン。

## Decisions

### 応答を捨てる連番

要求ごとに `useRef` の連番を進める。応答が届いたら、要求したときの番号と今の番号を比べ、違えば状態を変えずに終える。
番号を進めるのは、新しい要求を出すとき、入力を直したとき、部品が消えるとき（`useEffect` の後始末）である。
この仕組みは `PageSelectors.tsx` の `useLatest` にまとめ、3つの要求で共有する。

- `useCandidates`：`ask`、`reset`、部品が消えるときに進める。古い応答では `null` を返す。編集の画面の「候補を出し直す」も、同じ守りを持つ。
- `SelectorEditor` の見本：`look`、欄の変更、部品が消えるときに進める。欄を直したときは `busy` も解き、直したあとの組ですぐに「見本を見る」を押せるようにする。古い応答は、見本、失敗、`onTested`、`busy` のどれにも触れない。
- `AddFeedForm` のフィードを探す要求：追加の操作、URLの欄の変更、部品が消えるときに進める。古い応答は、購読、フィードの一覧、見つからない旨のどれにも触れない。`run` の失敗の表示と `busy` の解除も、古い要求では行わない。URLを直したときは `busy` も解く。ページを登録している間は欄を編集できるので、直したあとに `busy` が残らないようにするためである。

代わりに `AbortController` で要求を取り消す案もあった。`api` に取り消しの口を足す必要があり、取り消してもサーバーの側の処理は止まらない。応答を捨てる方法でも、画面の側の効果は同じである。

### URLの欄は読み取り専用

フィードを探している間（`busy` で、まだページを選んでいないとき）、URLの欄に `readOnly` を付ける。
`disabled` にするとブラウザーがフォーカスを外し、Enterで送った人が応答のあと欄へ戻る操作が要る。読み取り専用なら、フォーカスと読み上げが残る。
共通の入力欄に `read-only:` の見た目（文字を `on-surface-muted`、枠を `outline`）を足し、止まっていることを見て分かるようにする。
候補を待つ間は編集できるままにする。URLを直すことが、待つのをやめる手段になる。

### 最新のカテゴリと切り替えで登録する

`subscribe` は、カテゴリと3つの切り替えを、`add` を呼んだ時点の値ではなく、`useRef` に写した最新の値から読む。
探している間に変えた値が、画面に見えているとおりに登録される。

## Risks / Trade-offs

- 古い要求のサーバーの処理は続く → 候補の生成ではLLMを1回使ったまま、結果を捨てることになる。URLを直す人はその候補を求めていないので、これを受け入れる。
- 読み取り専用の欄には、入力できない理由の文言がない → 待つ間はボタンが無効になり、数秒で元に戻る。止まっていることは、欄の見た目で示す。
