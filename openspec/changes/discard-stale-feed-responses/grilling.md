# grilling 記録: discard-stale-feed-responses

Issue #98「購読フィードの追加で、URLを直す前の応答が反映される」で、計画についての質問に答えてもらった。
Issueの直し方（要求ごとに連番を付けて古い応答を捨てる、探している間は入力欄を編集できないようにする）を前提に、残った論点を問うた。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 候補を待つ間のURLの欄 | A：編集できるままにし、URLを直したら古い候補の応答を捨てる。URLを直すことが、待つのをやめる手段になる | Issue #98 第1ラウンド Q1 |
| 見本の古い応答 | A：このIssueで直す。見本の要求にも連番を付け、セレクターを直したあとに届いた見本を捨てる | Issue #98 第1ラウンド Q2 |
| 探している間に変えたカテゴリと切り替え | A：変えられるままにし、購読するときの値を使う。探している間に変えた値が登録に反映される | Issue #98 第1ラウンド Q3 |
| URLの欄を止める方法 | A：読み取り専用（`readOnly`）にする。フォーカスは欄に残り、応答のあとすぐ直せる | Issue #98 第1ラウンド Q4 |
| 閉じたあとに届いた応答 | A：捨てる。ダイアログを閉じたあと、または画面を離れたあとに届いた応答では購読しない | Issue #98 第1ラウンド Q5 |
| 計画の承認 | 上の5つの答えに沿った計画を承認 | Issue #98への返答（`/ok`） |

## 後回しにしたもの

- 候補を求める要求を途中でやめるボタン。URLを直すことで、待つのをやめられるため足さない
- `AbortController` による要求の取り消し。画面がAPIを呼ぶ部品に取り消しの口がなく、サーバーの処理も止まらないため、応答を捨てる方法にした
