# Spec Delta

## MODIFIED Requirements

### Requirement: タスクの限定

サーバーは、解釈、判定、集約、本文の生成、検索、要約、翻訳、セレクターの提案、ダイジェスト、トピックの書き直しの案の10個のタスク以外の目的でLLMを呼び出してはならない（MUST NOT）。

#### Scenario: フィードだけの実行

- **WHEN** 新しい候補が1件もない実行をする
- **THEN** その実行でLLMは1回も呼び出されない

### Requirement: 1日あたりの呼び出し回数の上限の既定

サーバーは、1日あたりの呼び出し回数の上限の既定を380回にしなければならない（MUST）。
既定の値は、セレクターの提案の1日の上限の既定である50回と、試しの1日の上限の既定である30回を含む。書き直しの案の1日の上限の既定である20回も、この中に含む。

#### Scenario: 上限を書かない設定

- **WHEN** `config.yaml` に1日あたりの呼び出し回数の上限を書かずにサーバーを起動する
- **THEN** 1日あたりの呼び出し回数の上限は380回になる

## ADDED Requirements

### Requirement: 書き直しの案のタスク

書き直しの案のタスクは、トピックの文章と判定基準、カテゴリの種類、出力言語、読み手情報、開いた記事、スターの記事、外れの見出し、判定が関連なしとした除外を入力としなければならない（MUST）。
出力は1つか2つの案で、案ごとに、トピックの新しい文章と、変えた点の説明を持つ。説明は出力言語で書き、判定基準がどう変わるはずかも述べる。
案の文章は、トピックの文章の上限の文字数以内とする。今の文章と同じ案と、同じ文章の2つの案は、不正な出力として扱う。
記事、外れ、除外の内容は、収集した資料として渡す。書き直しの案のタスクは、道具を使わない。

#### Scenario: 案を出す

- **WHEN** 開いた記事とスターの記事と外れの印があるトピックで、書き直しの案のタスクを実行する
- **THEN** 出力は1つか2つの案で、どの案も今と異なる文章と、出力言語の説明を持つ

#### Scenario: 今と同じ文章の案

- **WHEN** LLMが、今の文章と同じ文章の案を2回とも返す
- **THEN** サーバーはその出力を捨て、タスクは失敗として扱われる

### Requirement: 書き直しの案に渡す記事

サーバーは、書き直しの案のタスクに、そのトピックに結び付いた記事と候補だけを渡さなければならない（MUST）。
開いた記事は直近30日に開いた生成記事を、新しく開いた順に20件まで渡す。スターの記事は直近30日に作られた生成記事を、新しい順に20件まで渡す。どちらもタイトルと要約を渡す。
除外は、直近30日に作られた候補のうち、判定が関連なしとしたものを、新しい順に30件まで、タイトルと理由を渡す。公開日時が不明、件数上限、重要度が基準未満のような、プログラムの理由による除外は渡さない。
外れは、解釈のタスクと同じく、90日以内に印を付けたものを新しい順に20件まで、見出しだけを渡す。

#### Scenario: プログラムの理由の除外

- **WHEN** 判定が関連なしとした除外と、重要度が基準未満で除外した候補があるトピックの案を求める
- **THEN** タスクの入力には、判定が関連なしとした除外だけが入る

#### Scenario: 古い記事とほかのトピックの記事

- **WHEN** 40日前に開いた記事と、ほかのトピックの記事を開いた状態で、案を求める
- **THEN** タスクの入力の開いた記事には、どちらも入らない

### Requirement: 書き直しの案を呼ぶ時点

サーバーは、利用者がトピックの書き直しの案を求めたときにだけ、書き直しの案のタスクを呼び出さなければならない（MUST）。
1回の求めでは、タスクを1回呼び出す。未解釈のトピックでは呼び出さない。

#### Scenario: 案を1回求める

- **WHEN** 利用者が解釈済みのトピックの案を1回求め、タスクの1回目の出力が正しい
- **THEN** 書き直しの案のタスクの呼び出しは1回である

#### Scenario: 未解釈のトピック

- **WHEN** 未解釈のトピックの案を求める
- **THEN** LLMは呼び出されず、サーバーは未解釈を理由に断る

### Requirement: 書き直しの案のタスクの割り当て

サーバーは、書き直しの案のタスクを、設定が割り当てたプロバイダーで実行しなければならない（MUST）。
割り当てがないとき、`smart` という名前のプロバイダーがあればそれを使い、なければ既定のプロバイダーを使う。

#### Scenario: 割り当てのない既定

- **WHEN** `config.yaml` に `providers` と `tasks` を書かずにサーバーを起動する
- **THEN** 書き直しの案は `smart` で実行される

### Requirement: 書き直しの案の1日の上限

その日の書き直しの案の呼び出し回数が書き直しの案の1日の上限に達している間、サーバーは書き直しの案のためにLLMを呼び出してはならない（MUST NOT）。
呼び出し回数は、やり直しを含めて数える。上限の既定は20回とし、設定で変えられる。0のとき、書き直しの案は使えない。

#### Scenario: 上限に達した日

- **WHEN** 書き直しの案の1日の上限が2回で、その日の書き直しの案の呼び出しが2回ある状態で、案を求める
- **THEN** LLMは呼び出されず、サーバーは上限を理由に断る

#### Scenario: 既定の上限

- **WHEN** `config.yaml` に書き直しの案の1日の上限を書かずにサーバーを起動する
- **THEN** 書き直しの案の1日の上限は20回になる

#### Scenario: 書き直しの案の上限に達しても実行は止まらない

- **WHEN** その日の書き直しの案の呼び出しが上限に達し、1日あたりの呼び出し回数には余裕がある状態で、実行が始まる
- **THEN** 実行はLLMを呼び出す

### Requirement: 1日あたりの上限と予算への書き直しの案の計数

サーバーは、書き直しの案の呼び出しを、1日あたりの呼び出し回数と月の予算に数えなければならない（MUST）。
その日の呼び出し回数が1日の上限に達している間、サーバーは書き直しの案のためにLLMを呼び出してはならない（MUST NOT）。
予算の期間の合計が月の予算に達している間、サーバーは書き直しの案のために `anthropic` のプロバイダーを呼び出してはならない（MUST NOT）。

#### Scenario: 案のあとの呼び出し回数

- **WHEN** その日の呼び出し回数が10回の状態で、書き直しの案を1回呼び出す
- **THEN** その日の呼び出し回数は11回になる

#### Scenario: 予算に達した状態で案を求める

- **WHEN** 書き直しの案のタスクに `anthropic` のプロバイダーを割り当て、予算の期間の合計が月の予算に達した状態で、案を求める
- **THEN** LLMは呼び出されず、サーバーは予算を理由に断る

### Requirement: 書き直しの案の呼び出しの記録

サーバーは、書き直しの案の呼び出しを、どの実行にも属さない呼び出しとして記録しなければならない（MUST）。
案は保存しない。呼び出しの記録のほかに、データベースに書き込むものはない。

#### Scenario: 案を求めたあとで確かめる

- **WHEN** 案を1回求めたあとで、呼び出しの記録とトピックを読む
- **THEN** 書き直しの案のタスクの呼び出しが、実行なしで1件記録されている。トピックの文章と判定基準は、求める前と同じである
