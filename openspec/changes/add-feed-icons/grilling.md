# grilling 記録: add-feed-icons

Issue #222（購読フィードのアイコン）で、計画についての質問に2ラウンドで答えてもらった。
Issueの案は、サーバーがサイトのアイコンを取得し、左のペインと一覧の行の配信元の前に出すものである。
`PRODUCT.md` の「記事を大きな枠や画像で飾らない」に照らして、入れるかどうかと範囲を決めた。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| アイコンを出す範囲 | B：Webの左のペインのフィード名の前にだけ出す。一覧の行は文字だけのまま | Issue #222 第1ラウンド Q1 |
| ICOのアイコンの扱い | A：中継の判別にICOを加え、`image/x-icon` として返す。記事の画像にも同じ判別が効く | Issue #222 第2ラウンド Q2 |
| アイコンを探す順番 | A：Atomの `<icon>` とJSON Feedの `favicon`、HTMLの `<link rel="icon">`、`/favicon.ico` の順に探し、最初に取得できたものを使う。RSSの `<image>` は使わない | Issue #222 第2ラウンド Q3 |
| Androidのドロワー | A：Webの左のペインだけに出す。Androidは別のissueにする | Issue #222 第2ラウンド Q4 |
| アイコンのないフィードの行 | A：アイコンの分の幅を空けたまま何も描かない | Issue #222 第2ラウンド Q5 |
| 保存の仕方と探し直す時機 | A：`feeds` にアイコンの元のURLと最後に探した時刻を記録し、画像は中継とディスクの保存に配らせる。30日ごとに探し直す | Issue #222 第2ラウンド Q6 |
| 計画の承認 | 上の答えに沿った計画を承認 | Issue #222への返答（`/ok`） |

## 選ばなかった案

- 入れずにissueを見送る案（Q1のA）。名前の長いフィードの見分けにくさが残る
- 一覧の行の配信元の前にも出す案（Q1のC）。フィードの記事の行にだけ画像が付き、主役のまとめた記事よりも目立つ
- ICOをアイコンの取得のときだけ受け付ける案（Q2のB）。安全面の得がないのに、判別の経路が2つに分かれる
- ICOを受け付けない案（Q2のC）。`/favicon.ico` しかないサイトにアイコンが出ない
- RSSの `<image>` を最後に使う案（Q3のB）。横長のロゴが文字の高さに潰れて並ぶ
- HTMLを取得しない案（Q3のC）。HTMLにだけアイコンを書くサイトで、古いアイコンか何も出ない
- Androidのドロワーにも出す案（Q4のB）。ICOの表示の確認と行の組み直しが別に要る
- アイコンのない行で幅を取らない案（Q5のB）。名前の書き出しが行ごとにずれる
- 画像のバイト列を新しい表に保存し、専用のエンドポイントで配る案（Q6のB）。中継と同じ安全の仕組みが二重になる

## 前提にした既存の決定

- 一覧の行に記事の画像を出さない（add-feed-subscriptionsの第2ラウンドQ13）。この変更でも変えない
- 画面は他のサイトの画像を直接読み込まず、署名した中継のパスだけを読み込む（image-proxy、web-shellの「画像の読み込みの制限」）
- SVGはスクリプトを含められるので、中継で拒む（image-proxyの「SVGの拒否」）
