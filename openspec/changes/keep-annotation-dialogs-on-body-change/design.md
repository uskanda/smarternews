# Design

## Context

`ArticleView`は`AnnotatedBody`に、全文の表示と訳の有無から作った`key`を付けている。全文の表示と訳の有無が変わると、`AnnotatedBody`が丸ごと作り直される。作り直しが要るのは、`useBodyAnnotations`が集めた本文の文字列と、それから探したハイライトの位置だけである。ところが、選択のメニュー、各ダイアログ、削除の確認の状態も同じ部品の中にあるので、一緒に消える。

## Goals / Non-Goals

**Goals:**

- 本文の差し替えで作り直す範囲を、本文のDOMとハイライトの位置に絞る。
- 差し替え後のハイライトの位置は、今の作り直しと同じ結果にする。

**Non-Goals:**

- 状態を`ArticleView`まで引き上げること。
- #195の扱い。

## Decisions

### `key`の代わりに`bodyKey`を渡す

`AnnotatedBody`に`key`を付けるのをやめ、同じ値を`bodyKey`というpropで渡す。`AnnotatedBody`は`bodyKey`を`useBodyAnnotations`に渡し、本文を描く部分（`render`の結果）にだけ`key={bodyKey}`を付ける。

本文のDOMが差し替わるので、`Markdown`と訳の部品の`onText`がまた呼ばれ、新しい本文の文字列が集まる。ダイアログ、選択のメニュー、削除の確認の状態（`writingFor`、`filteringFor`、`topicFor`、`opened`、`removing`、`returnTo`）は、作り直されない側に残る。

選ばなかった案：状態を`ArticleView`へ引き上げる。ダイアログは`AnnotatedBody`の中の`add`や`returnTo`を使うので、変更が大きくなる。

### `useBodyAnnotations`は`bodyKey`の変化で集め直す

フックは、集めた文字列（`texts`、`known`）を`bodyKey`と組で持つ。`bodyKey`が変わったら、前の本文のものは捨てて、初めから集め直す。表示中の文字列（`shown`）も`bodyKey`と組で持ち、今の`bodyKey`のものでなければ使わない。これで、古い本文の文字列で新しい本文のハイライトを探すことがない。

部品の数が変わると、後ろの部品が先に文字列を知らせることがある。まだ知らせていない部品は配列の穴になるので、穴を残さない配列で揃ったかを確かめる。

### 一覧から選んだハイライトへの移動

`focusId`で一度移ったハイライトの記録（`focused`）も、これまでは作り直しで消えていた。本文が差し替わったら同じハイライトへもう一度移る、今の動きを保つ。そのため、記録は`bodyKey`と組で持つ。

### 差し替えのときの選択

本文が差し替わると、選択していたDOMが消えるので、選択は消える。開いているダイアログは、開いたときの引用文や値を自分で持っているので、そのまま使える。書きかけのメモは、差し替え後の本文にそのまま保存する。位置は引用文と前後の文字で決まる。

## Risks / Trade-offs

- 差し替わった本文が、ダイアログの引用文を含まないことがある。→ハイライトは保存され、「元の本文にあった箇所」に出る。本文が変わったときの既存の扱いと同じである。
- ダイアログを閉じたときのフォーカスの戻り先が、差し替え前のハイライトのDOMを指すおそれがある。→戻り先はハイライトの番号で持ち、閉じるときに差し替え後のDOMから探す。なければ本文へ戻す。
