# Proposal

## Why

追いたい話題のニュースを毎日集める作業は、LLMに検索から要約までをすべて任せる1本の指示文でも実現できる。
この方式の結果は1通の文章なので、記事ごとの既読や保存を扱えない。話題を追加または修正するたびに、指示文全体を書き直すことになる。
毎回の実行がLLMの利用枠を多く使い、同じ入力から同じ結果を得ることも難しい。

このchangeは、収集をプログラムへ移し、LLMを判断と文章の生成だけに使うサーバーを作る。
成果は記事の単位で保存し、APIとRSSで読めるようにする。
WebとAndroidアプリは、このAPIの上に後のchangeで作る。

## What Changes

- カテゴリとトピックを登録できるようにする。トピックはキーワードまたは文章で書く。LLMがその内容から検索語と判定基準を作る。
- 読み手情報と全体設定（出力言語、タイムゾーン、ニュース検索の言語と地域）を持ち、APIで編集できるようにする。
- カテゴリ、トピック、読み手情報を設定ファイルとして書き出し、読み込めるようにする。特定の利用者のデータはリポジトリに含めない。
- 取得元としてフィード、ニュース検索、LLM検索の3種を用意する。使う取得元はトピックごとに選べる。
- LLMの仕事は、解釈、判定、集約、本文の生成、検索の5つのタスクだけとする。プロバイダーはアダプターで差し替えられる。アダプターは `claude` コマンドとOpenAI互換HTTPの2つを作る。
- 候補の関連判定、重要度付け、同じ話題の集約、記事本文の生成を1回の実行として通す。72時間以内の続報は既存の記事を更新する。
- 種別がイベントのカテゴリでは、開催日を基準にして記事を作る。
- カテゴリごとのスケジュールで実行し、APIから即時にも実行できるようにする。実行履歴と、除外した候補とその理由を残す。
- 記事の一覧、既読、スターを扱うAPIを用意し、固定のトークンで認証する。
- カテゴリごとと全体のRSS 2.0を出力する。
- リポジトリを公開できる状態に保つため、ライセンス、README、CI、個人情報らしい文字列の検査を加える。

## Capabilities

### New Capabilities

- `settings`: カテゴリ、トピック、読み手情報、全体設定の登録と編集、設定ファイルの書き出しと読み込み。
- `sources`: 3種の取得元による候補の収集と、相手のサイトに対する取得の作法。
- `llm-tasks`: タスクの定義、プロバイダーとアダプター、タスクごとの割り当て、呼び出し回数の上限。
- `article-pipeline`: 候補から記事を作る処理。関連判定、重要度、集約、本文の生成、続報による更新、イベントの扱い、除外の記録。
- `runs`: スケジュールによる実行と即時の実行、実行履歴、保存期間による削除。
- `http-api`: 認証、記事の閲覧、既読とスター、設定と実行を操作するAPI。
- `rss-output`: カテゴリごとと全体のRSS 2.0の出力。

### Modified Capabilities

なし。このchangeが最初の仕様になる。

## Impact

- コードは新規に作る。pnpm workspaceに、共有の型と処理を置くパッケージと、サーバーのアプリを置く。
- 実行時にNode 24とSQLiteを使う。LLMの既定のプロバイダーは `claude` コマンドで、導入と認証は利用者が済ませておく。
- 外部への通信は、登録されたフィード、ニュース検索、候補のページ、設定したプロバイダーに限る。
- DB、トークン、APIキー、設定ファイルはリポジトリの外に置く。
- サーバーはLANとTailscaleから到達できる範囲で待ち受ける。外部のネットワークには公開しない。
- リポジトリにはライセンス（MIT）、英語と日本語のREADME、GitHub Actionsの設定が加わる。
