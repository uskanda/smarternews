# grilling 記録: add-crawler-api-rss

この記録は、システム全体の要件と設計を決めた3ラウンドの質問をまとめたものである。
質問の時点では、トピックを別の名前で呼んでいた。用語集を作るときに現在の名前へ改めた。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| changeの分割 | 3本に分ける。このchangeは全体設計と、クローラー、API、RSSまで。WebとAndroidアプリは後のchange | 第1ラウンド Q1 |
| 稼働先と常駐方式 | 利用者のLinuxサーバー1台で、systemdのユーザー単位のサービスとして動かす | 第1ラウンド Q2 |
| 利用者と到達範囲 | 利用者は1人。到達経路はLANとTailscaleに限り、固定のAPIトークン1本で認証する | 第1ラウンド Q3 |
| 登録単位 | カテゴリの下に複数のトピックを持つ2階層。RSSはカテゴリ単位 | 第1ラウンド Q4 |
| 候補の集め方 | 取得元を差し替え可能にする。初版からフィード、ニュース検索、LLM検索の3種を使える | 第1ラウンド Q5 |
| LLMの担当範囲 | トピックの解釈、関連判定と重要度付け、同じ話題の集約、記事本文の生成の4タスクに限る | 第1ラウンド Q6 |
| 初版のアダプター | `claude` コマンドとOpenAI互換HTTPの2つ。タスクごとにプロバイダーを割り当てられる | 第1ラウンド Q6 |
| ニュース以外の扱い | 種別を持つ共通の記事モデルにする。初版の種別はニュースとイベント。状況は種別だけ予約する | 第1ラウンド Q7 |
| 毎朝のまとめ記事 | 初版では作らない。記事本文は敬体の中立な要約にする | 第1ラウンド Q8 |
| 技術構成 | TypeScriptとpnpm workspace、Node 24、Hono、SQLite、ViteとReact、Expo、Vitest | 第1ラウンド Q9 |
| Androidアプリの対象 | Androidのみ。ストアを通さずAPKで入れる | 第1ラウンド Q10 |
| リポジトリの初期化 | `main` と `develop` の2本。GitHubにリポジトリを作る | 第1ラウンド Q11 |
| 圏外での閲覧 | 端末への記事の保存はしない。Tailscale経由でサーバーに届けばよい | 第2ラウンド Q1 |
| 続報の扱い | 72時間以内の続報は既存の記事を更新する。それ以降は別の記事にする | 第2ラウンド Q2 |
| クロールの頻度 | カテゴリごとに実行時刻のリストを持つ。APIからカテゴリ単位で即時に実行できる | 第2ラウンド Q3 |
| 選別の厳しさ | 重要度を付け、カテゴリごとに最低重要度と1回の件数上限を設定する。除外した候補も理由つきで記録する | 第2ラウンド Q4 |
| 読み手情報 | 全体設定に文章を1つ持ち、判定に渡す。記事には読み手への影響を1文、別の項目として付ける。文章はAPIで編集できる | 第2ラウンド Q5 |
| 本文の取得 | 関連判定を通った候補だけ本文を取得する。取得した本文は30日で消す | 第2ラウンド Q6 |
| LLM検索を使う範囲 | トピックごとに取得元を選ぶ。登録時にLLMが既定の組み合わせを提案し、利用者が直せる | 第2ラウンド Q7 |
| モデルと上限 | 判定と集約は軽いモデル、解釈と本文生成と検索は上位のモデルを既定にする。呼び出し回数に上限を置く | 第2ラウンド Q8 |
| 既読と保存期間 | 既読とスターはサーバーに持つ。スターのない記事は180日、除外した候補と実行履歴は30日で消す | 第2ラウンド Q9 |
| RSSの形 | RSS 2.0。カテゴリごとと全体の2種類。最新50件。トークンはURLに付ける | 第2ラウンド Q10 |
| イベントの扱い | 開催日を基準にする。開催日時、会場、料金、申込の要否を持つ。名称と開催日で同一と判定する | 第2ラウンド Q11 |
| 運用の見える化 | 実行履歴をAPIで見せる。通知は初版では出さない | 第2ラウンド Q12 |
| 初期データ | 特定の利用者のカテゴリや読み手情報はリポジトリに入れず、設定ファイルの読み込みで投入する | 第2ラウンド Q13、第3ラウンド Q3 |
| 公開範囲 | リポジトリは公開する。個人情報と公開に向かないものは入れない。カテゴリ、トピック、読み手情報はデータとして扱い、設計は特定の利用者に依存させない | 第2ラウンド Q14 |
| コミットの作者情報 | このリポジトリではGitHubが発行するnoreplyの宛先を使う | 第3ラウンド Q1 |
| 公開の意味 | 1つのサーバーを1人が使うセルフホストを対象にする。複数人で共用する機能は作らない | 第3ラウンド Q2 |
| 個人データの置き場所 | 設定ファイル、DB、トークン、APIキーはリポジトリの外に置く。リポジトリには特定の個人や地域に依存しない例を置く | 第3ラウンド Q3 |
| 公開する文書の書き方 | 成果物には決定と理由だけを書く。例とテスト用のデータは架空にする。個人情報らしい文字列の検査を `make verify` に足す | 第3ラウンド Q4 |
| ライセンス | MIT | 第3ラウンド Q5 |
| 文書とUIの言語 | READMEは英語を主にして日本語版も置く。UIは日本語のみ。記事の出力言語は設定で選べる | 第3ラウンド Q6 |
| 地域とタイムゾーン | タイムゾーンと、ニュース検索の言語と地域は全体設定に持つ。検索の言語と地域はトピックごとに上書きできる | 第3ラウンド Q7 |
| 他の人の導入手段 | 初版は手順書とsystemdの設定の雛形だけ | 第3ラウンド Q8 |
| CI | GitHub Actionsで `make verify` を走らせる。`main` と `develop` を保護する | 第3ラウンド Q9 |
| 取得の作法 | User-Agentを設定値にする。robots.txtに従い、ホストごとに間隔を空け、取得するページ数に上限を置く | 第3ラウンド Q10 |

## 後回しにしたもの

- Webの画面。APIが固まってから別のchangeにする。
- Androidアプリ。通知の設計もそのchangeで扱う。
- 種別が状況のカテゴリ（天気や道路規制など、1日1回の現況）。構造化データを直接取る専用の取得元として後のchangeで作る。
- 毎朝のまとめ記事。記事の集約と重要度付けの上に載る生成タスクとして後から足す。
- DockerfileとCompose。
- UIの多言語化。
- 呼び出し回数の上限の既定値。実測してから設計の値を見直す。
