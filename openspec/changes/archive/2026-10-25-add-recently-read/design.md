# Design

## Context

記事の既読は、記事の表の `is_read` だけで持っている。いつ既読になったかは保存していない。
`is_read` を書き換える処理は、`packages/core/src/db/articles.ts` の次の4つである。

- `setArticleFlags`: `PATCH /api/v1/articles/:id` の既読の変更。開いた記事の既読化、`m` のキー、アプリの行を払う操作、長押しの操作、本文の画面の未読に戻す操作が、すべてここを通る
- `markArticlesRead`: 一括の既読
- `markArticlesUnread`: まとめて未読に戻す操作。一括の既読の取り消しが使う
- `reviseArticle`: 続報で生成記事を書き換え、未読に戻す

スクロールで既読にする操作（#50）は、まだない。入るときも、上の既読の変更か一括の既読のどちらかを通る。
項目の一覧は、`packages/client/src/nav.ts` の `buildNav` が、Webの左のペインとアプリの引き出しの両方のために組み立てる。
一覧の取得は `targetFilter` が項目から問い合わせのパラメーターを作り、`GET /api/v1/articles` を呼ぶ。
読んだ記事を一覧に残す処理は、`mergeKept` が、取得した記事と残す記事を更新の時刻の順で混ぜる。

## Goals / Non-Goals

**Goals:**

- 既読になる経路がこの先増えても、サーバーの処理を通る限り、時刻を記録し漏らさない。
- 一覧の取得、続きの取得、行の部品を、いまの仕組みのまま使う。

**Non-Goals:**

- 既読の履歴を、操作ごとに残すこと。記事ごとに最後の1つだけを持つ。
- 一括の既読の操作ごとのまとまりと、まとめて未読へ戻す画面の操作（#51の第1ラウンドQ4で後回しにした）。
- 機能を入れる前から既読の記事の時刻を、推測で埋めること。

## Decisions

### 既読の時刻は記事の表の列にする

移行で、記事の表に `read_at` の列を足す。番号は、実装の時点で空いている次の番号にする（011番を使った）。同じ時期の別の変更も移行を足すからである。値はISO 8601の文字列で、空を許す。
移行の時点で既読の記事は、空のままにする。最近読んだ記事の一覧には出ない（#51の第2ラウンドQ4）。
`(read_at, id)` の部分索引を、`read_at` が空でない行に張る。一覧の並びと続きの取得がこの索引を使う。

既読の履歴を別の表に1行ずつ足す案は採らない。決定は「記事ごとに最後の時刻を1つ」であり、別の表は削除と件数の管理が増えるだけである。

### 時刻はサーバーがその場で書く

時刻はサーバーの時計の値を使い、画面からは受け取らない。4つの処理を次のように変える。

- `setArticleFlags`: 既読への変更では、未読だった行にだけ時刻を入れる。すでに既読の行は時刻を変えない。未読への変更では時刻を空にする
- `markArticlesRead`: 既読へ変えた行すべてで、同じ時刻を入れる
- 上の2つは、残した配信記事と一緒に重複も既読にする。その重複でも、同じ時刻を入れる
- `markArticlesUnread`: 未読に戻した行の時刻を空にする
- `reviseArticle`: 未読に戻すので、時刻を空にする

これで、「既読の時刻があるのは既読の記事だけ」が常に成り立つ。
すでに既読の記事への既読の変更で時刻を変えないのは、既読の記事を開き直しただけで一覧の先頭へ動かないようにするためである。
いまの画面は、既読の記事を開いても既読の変更を送らない。サーバーの側でも、同じ結果を保証する。

時刻を受け取る引数は、各処理の呼び出し元で `clock()` から渡す。いまの `setArticleFlags` と `markArticlesRead` は時刻を受け取らないので、最後の引数に足す。

### 一覧は、記事の一覧のパラメーター `recentlyRead` で取得する

`GET /api/v1/articles?recentlyRead=true` を足す。新しいパスは作らない。

- 条件は、`is_read = 1` かつ `read_at` がいまから7日（168時間）前以降であること。フィルターで隠れている配信記事は、ほかの一覧と同じく除く。重複の除去が有効な間は、重複として記録した配信記事も、すべての記事の一覧と同じく除く。重複は残した配信記事と同じ時刻で既読になるので、出すと同じ記事が2行並ぶ
- 並びは `read_at DESC, id DESC`。続きの値は `read_at` と `id` の組にする
- 終了したイベントの記事も含める。`includeEnded` の指定は見ない
- カテゴリ、由来、購読フィード、未読、スター、種別、重要度の下限のどれかと一緒に指定されたときは、HTTPステータス400を返す。絞り込みとの組み合わせは画面で使わないので、意味を決めずに断る

`/articles/recently-read` のような別のパスは、`/articles/:id` と並ぶため、登録の順に依存する。応答の形も記事の一覧と同じなので、パラメーターにしたほうが、画面の続きの取得をそのまま使える。
7日は、全体設定のタイムゾーンの暦の日ではなく、いまからの168時間で数える。日付の境目で一覧が急に減ることがなく、問い合わせも単純になる。

### 応答の各記事に `readAt` を足す

記事の一覧と詳細の各記事に `readAt` を足す。未読の記事と時刻のない記事では `null` にする。
`articleSummarySchema` に足せば、詳細の `articleSchema` にも入る。古いアプリは知らない項目を無視するので、そのまま動く。

### 項目は `buildNav` の上部の項目に足す

`ListTarget` に `{ type: "recentlyRead" }` を足し、`buildNav` の `views` の「AI生成」のあとに、ラベル「最近読んだ記事」、未読数0で置く。未読数0の項目は数字を出さないので、数字は付かない。
`listKey` は `recently-read`、Webのパスは `/recently-read` にする。`targetFilter` は `{ recentlyRead: "true" }` を返す。
上部の項目は、どちらの画面でもドラッグの対象の外で描いている。並べ替えの処理は変えずに、動かせないことをテストで確かめる。

### 一覧の上部の操作は出さない

`hasReadToggle` は、この項目で偽を返す。一括の既読と重要度4以上の切り替えも出さない。
一覧の記事はすべて既読なので、一括の既読は何もしない。重要度の下限は配信記事を外すので、読んだ記事を探す一覧では、配信記事が消えて見える。
判定は、`packages/client` に項目ごとの関数を足し、Webとアプリで同じものを使う。

### 残す行の並びには、表示したときの既読の時刻を使う

`mergeKept` に並びの鍵を渡せるようにする。最近読んだ記事の一覧では `readAt` で並べ、ほかの一覧では、いまと同じく更新の時刻で並べる。
この一覧で未読に戻した記事は、サーバーの応答では `readAt` が `null` になる。画面は、残す行として、未読に戻す前の `readAt` を持った記事を保ち、同じ位置に置く。行の時刻も、その値を出す。
60秒ごとの再取得とアプリが前面に戻ったときの再取得は、残す行を消さない。いまの未読の一覧と同じである。
既読を変えたあとは、最近読んだ記事の一覧のキャッシュを古いものとして扱う。別の項目から戻ったときに、未読に戻した記事が古いキャッシュから出ないようにするためである。

### 行の時刻は、行の部品に何の時刻を出すかを渡して切り替える

Webとアプリの `ArticleRow` に、更新の時刻と既読の時刻のどちらを出すかを渡す。最近読んだ記事の一覧だけが既読の時刻を選ぶ。
日時の整形は、いまの `formatShort` と全体設定のタイムゾーンをそのまま使う。

## Risks / Trade-offs

- 続報で生成記事が書き換わると、既読の時刻が消え、最近読んだ記事の一覧から外れる → その記事は「未読」の一覧に出るので、見失わない。既読の時刻があるのは既読の記事だけ、という約束を守るほうを選ぶ
- 一括の既読で数百件が同じ時刻になる → 並びは `id` で決まるので、続きの取得で記事が重複したり抜けたりしない。操作ごとのまとまりは後回しの決定どおり扱わない
- 移行の前から既読の記事は、時刻がないので一覧に出ない → 決定どおり。導入の直後は一覧が空に近いことを、記事がないときの表示で伝える
- 7日を過ぎた既読の時刻は消さずに残る → 列は1つの文字列で、記事の削除と一緒に消える。容量の問題は小さい

## Migration Plan

1. `read_at` の列を足す移行を足す。列の追加と索引だけで、既存の行は書き換えない。
2. サーバーを入れ替えると、その時点から既読の時刻が記録される。
3. 戻すときは、前の版のサーバーに戻す。足した列は前の版から使われないので、そのまま残してよい。
