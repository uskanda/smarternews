# Design

## Context

動機はproposal.mdの「Why」にある。直す箇所の今の作りは次のとおり。

- 1文字のキーは `apps/web/src/lib/keys.ts` の1つの `keydown` の処理が受ける。`isTyping` は `INPUT`、`TEXTAREA`、`SELECT` を種類を見ずに入力中とみなす。`Space` を部品に渡すのは、ボタンと、roleがcheckboxなどの要素だけである。
- `data-hotkeys="off"` の印を持つ要素の中では、1文字のキーを止める。developで印を持つのは `FormDialog`、`ConfirmDialog`、キー操作の一覧だけである。項目のメニュー（`apps/web/src/shell/order.tsx`）と、狭い画面の項目の引き出し（`apps/web/src/shell/Shell.tsx`）は持たない。
- どの一覧の経路も同じ `ReaderPage` を描くので、一覧を移ってもスクロールの要素は同じものが残る。先頭へ戻すのは、並び順が変わったときだけである。
- 一括の既読のボタンを出す条件は、読み込んだ行に未読があるかだけを見る。
- 知らせ（`apps/web/src/shell/toast.tsx`）は、出した時点から消すまでの時間を数え始め、マウスやフォーカスがあっても止めない。
- 未読に戻すAPIは、識別子を5000件まで受け付ける（`packages/core/src/api.ts` の `markUnreadSchema`）。既読にするAPIは、件数の上限なしで識別子を返す。Webとアプリはどちらも、返った識別子を1回の要求で送る。
- 取り消しのあとに呼ぶ `refresh` は、一括の既読を押した時点の一覧の識別子で、残した行を消す。

mainには、ダイアログに印を付ける修正（542ccd0、#86）がある。developにはまだない。mainの `add-feed-from-category` の要件は、狭い画面の左のペインを、キーを止める対象から外している。その中のキーで項目を移るためである。

## Goals / Non-Goals

**Goals:**

- 仕様の差分（`specs/web-shell/spec.md`、`specs/web-reader/spec.md`）の要件を、Webの画面と、Webとアプリの共有の処理で満たす。
- 取り消しの件数の上限は、Webとアプリの両方で外す。

**Non-Goals:**

- 一覧ごとのスクロールの位置を覚えて戻すこと。狭い画面で一覧に戻ったときの位置は、#112で扱う。
- スターと既読の変更の失敗を知らせること。#114と#95で扱う。
- アプリの取り消しの失敗を知らせること。件数の上限は共有の処理で外れるが、アプリの画面は変えない。
- mainとdevelopの食い違いを直すこと。

## Decisions

### 1. 入力中かどうかは要素の種類で決める

`isTyping` は、文字を打つ種類の `INPUT`、`TEXTAREA`、編集できる領域だけを入力中とみなす。
文字を打つ種類は、typeの指定がないもの、text、search、url、email、number、password、telなどである。
checkbox、radio、buttonの種類の `INPUT` と、`SELECT` は入力中とみなさない。
これらにフォーカスがあるときの `Space` は、ボタンと同じく部品に渡す。

選択欄で1文字のキーを受けると、ブラウザーの先頭文字での選択は働かなくなる。
絞り込みの選択欄の項目はカテゴリと購読フィードの名前で、日本語が多いので、先頭文字の選択はほとんど使えない。
選択は矢印キーで変えられる。

ほかの案として、選択欄で選んだあとにフォーカスを本文の区画へ移す方法を考えた。
キーボードで選び直そうとした利用者のフォーカスを奪うので、採らない。

### 2. メニューには印を付け、左のペインには受け付けるキーを限る印を付ける

項目のメニューの中身に `data-hotkeys="off"` を付ける。メニューはPortalで描かれるが、キーの対象はメニューの中の要素なので、`closest` で印を見つけられる。

狭い画面の項目の引き出しには、別の印 `data-hotkeys="nav"` を付ける。
この印の中では、`Shift+J`、`Shift+K`、`/`、`?`、`g` とそれに続くキーだけを処理する。
引き出しを全部止めると、引き出しの中で項目を移るキーまで止まる。mainの要件が左のペインを外した理由と同じである。

### 3. 一覧の識別子が変わったら先頭へ戻す

一覧の識別子（`listKey`）が変わったときに、スクロールの位置を0にする。
`listKey` は並び順を含まないので、並び順の変化には今の処理を残す。

開いている記事の行が見える位置へ動かす案も考えたが、採らない。
下へ動かすと、スクロールでの既読が、上へ流れた行を既読にするおそれがある。
先頭へ戻すのは上への移動なので、既読は起きない。

### 4. 一括の既読を出す条件に、続きのページを足す

読み込んだ行に未読があるか、続きのページがあるときに、一括の既読を出す。
続きのページがあれば、まだ読み込んでいない未読がありうるからである。

左のペインの未読数を使う案も考えた。
未読数は、重要度の絞り込みや検索の範囲と一致しないので、採らない。
続きのページがすべて既読のときは、選んでも0件の既読になる。害はないので許す。

### 5. 知らせはマウスとフォーカスの間は止め、離れたら最初から数え直す

知らせの要素の `onMouseEnter` と `onFocus` で止め、`onMouseLeave` と `onBlur` の両方が外れたら、表示時間を最初から数え直す。
止めている間に新しい知らせが来ても、離れるまでは数えない。
残りの時間から再開する案は、状態が増える割に利点が小さいので採らない。

### 6. `z` で知らせの操作を選ぶ

`ToastProvider` で `useHotkeys` を使い、操作のある知らせを出している間だけ `z` に操作を割り当てる。
知らせがないときは割り当てないので、キーは他に渡る。
入力中の扱いは、他の1文字のキーと同じである。

`z` は今の割り当てにない。取り消しのキーとして、Gmailなどで広く使われている。
知らせの操作には「もう一度試す」もあるので、キー操作の一覧には「知らせの操作（取り消す、もう一度試すなど）」と書く。

### 7. 未読に戻す要求は、共有の処理で5000件ずつ分ける

`packages/core/src/api.ts` に上限の定数 `MAX_MARK_UNREAD` を置き、`markUnreadSchema` と、Webとアプリの共有の処理の両方で使う。
`MAX_MARK_SEEN` と同じ作りである。
共有の処理（`packages/client`）の `markUnread` は、識別子を上限ごとに分けて順に送り、戻した件数を足して返す。
途中で失敗したら、その時点で失敗として返す。

未読に戻す操作は、もう未読の記事を変えない。
そのため、途中で失敗したあとに全件を送り直しても、結果は同じになる。

サーバーで範囲を指定して戻すAPIを足す案も考えた。
APIの変更とアプリの変更が要るので、採らない。

### 8. 取り消しのあとは残した行を消さずに読み直す

取り消しが成功したら、記事の一覧と件数のキャッシュを無効にして読み直す。残した行は消さない。
一括の既読の時点で、元の一覧の残した行はすでに消してある。
取り消しのあとに消すと、次の項目へ移った先で読んだ行まで消える。

取り消しが失敗したら、「既読を取り消せませんでした」と「もう一度試す」の知らせを出す。
「もう一度試す」は、同じ識別子で取り消しをやり直す。

## Risks / Trade-offs

- ［選択欄の先頭文字での選択が働かない］→矢印キーで選べる。項目の多くは日本語の名前である。
- ［取り消しの途中で失敗すると、一部だけが未読に戻る］→失敗を知らせ、「もう一度試す」で全件を送り直す。送り直しても結果は変わらない。
- ［残した行を消さないので、取り消したあとも、取り消しの前に読んだ行が既読のまま残る］→読み直しで、サーバーの状態に合わせて表示し直す。
- ［mainをdevelopへ取り込むときに、`keys.ts`、`Shell.tsx`、`add-feed-from-category` の要件がぶつかる］→取り込みのときに突き合わせる。印の付け方はmainの542ccd0と同じなので、ダイアログの部分はどちらの版を採っても同じ結果になる。

## Migration Plan

画面と共有の処理の変更だけで、データの移行はない。通常どおりサーバーを入れ替える。
戻すときは、前の版の画面を配信し直す。
