# Design

## Context

取得の処理は、`packages/core/src/feeds/ingest.ts` の `storeItems` である。文書の項目ごとに、まず `feed_items_seen` へ識別子を書き、そのあとで保存するかどうかを決める。
そのため `feed_items_seen` には、古い項目の除外で保存しなかった項目も、保存期間で記事を消した項目も入っている。取得の前に読む `seenBefore` と、保存済みの記事の `stored` のどちらにもない識別子が、その購読フィードに初めて現れた項目である。
重複の除去で重複と記録した配信記事は、保存してから `duplicate_of` に印を付けるので、保存されている。

記事の表は、隠れ方を記事の列に持つ。フィルターは `filtered`（スターがあっても1のまま、表示ではスターが優先する）、重複は `duplicate_of` である。保存の時刻は `created_at` にある。
全体設定は `settings` の表の1行で、設定ファイルの書き出しは `getSettings` の値をそのまま書く。

Webの購読フィードの設定（`apps/web/src/settings/FeedsPage.tsx`）は、一覧の行の中で編集の欄（`EditFeed`）を開く。統計の区画は、この編集の欄の中に置く。
Webの本文のペイン（`apps/web/src/reader/ReaderPage.tsx`）は、開いた記事を1回だけ既読にする `useEffect` を持つ。アプリの本文の画面（`apps/mobile/src/reader/ArticleScreen.tsx`）は、横に払う並びで、表示中の記事を `currentId` で持つ。
スクロールで既読にする操作（#50）は、本文を表示しないまま記事を既読へ変える。開いた時刻と既読の時刻（#51）を分ける理由の1つである。

## Goals / Non-Goals

**Goals:**

- 新しい項目の判定を、取得の処理がすでに持つ情報だけで行い、取得の回数と相手のサイトへの要求を増やさない。
- 日数の設定を変えたら、次の一覧の取得から判定に反映する。
- 開いた時刻を、関連度での並び（#60）がそのまま使える形で残す。

**Non-Goals:**

- 統計の期間を変える設定。直近30日に固定する。
- 統計の推移（日ごとの数）を残すこと。いまの記事の状態から、その場で数える。
- 開いた時刻の索引と、#60での使い方。#60で決める。

## Decisions

### 新しい項目は `feed_items_seen` と保存済みの記事で見分ける

`storeItems` の中で、`seenBefore` と `stored` のどちらにもない識別子が1つでもあれば、購読フィードの表の新しい列 `last_new_item_at` へ取得の時刻を書く。
登録のときの取得も同じ処理を通るので、項目を配信しているフィードは、登録の時刻が入る。項目のないフィードは値なしのまま残り、判定では `created_at` から数える。

配信記事の保存の時刻の最大値から求める案は採らない。古い項目の除外で保存しなかった項目を数えられないからである（#64の第2ラウンドQ5）。
文書の中の識別子のない項目と、1回の上限（`MAX_NEW_ITEMS`）を超えた項目は、いまの処理のとおりに扱う。上限を超えた項目も `feed_items_seen` に入るので、新しい項目として数える。

### 更新が止まったかどうかは、問い合わせのときに計算する

判定は、有効であることと、`coalesce(last_new_item_at, created_at)` から日数×24時間が過ぎたことの2つで決める。結果は保存しない。
定期の処理で印を保存する案は採らない。日数の変更をすぐ反映できず、判定の時刻と表示の時刻がずれるからである。
無効な購読フィードは判定しない。取得していないので、相手のサイトが止まったかどうかを知る手段がない。

### 日数は全体設定の列にし、全体設定の画面で編集する

`settings` の表に `stale_feed_days`（既定60）を足し、APIの全体設定に `staleFeedDays` として出す。1から365の整数だけを受け付ける。
設定ファイルは `getSettings` の値を書くので、書き出しには自然に入る。読み込みでは、ないときに保存済みの値を残す。
編集の場所は、重複の除去の切り替えと同じ全体設定の画面（`SettingsPage.tsx`）にする。決定が「全体設定で変えられる」だからである。

### 開いた時刻は記事の表の列にし、専用の操作で書く

記事の表に `opened_at` を足す。書くのは `POST /api/v1/articles/:id/open` だけである。`UPDATE articles SET opened_at = coalesce(opened_at, ?)` として初めの時刻を残す。応答は `{ "openedAt": "..." }` である。
既読の時刻とは独立させ、既読の変更、一括の既読、未読に戻す操作、続報での書き換えのどれも、この列に触れない。
記事の一覧と詳細の各記事に `openedAt` を足す。

次の案は採らない。

- 記事の詳細の取得で記録する。画面は要約や全文を待つ間に詳細を何度も取り直し、アプリは隣の記事を先に読み込む。取得は副作用を持たないほうがよい。
- 既読の変更（`PATCH /api/v1/articles/:id`）に印を足す。スクロールでの既読（#50）や一括の既読と同じ経路になり、取り違えやすい。未読に戻しても消さない値を、既読の操作に載せる理由もない。

関連度での並び（#60）は、この列を読む見込みである。どう使うか、索引を張るかは#60で決める。

### 画面は、開いた時刻のない記事を表示したときだけ記録を送る

Webは、開いた記事を既読にするいまの `useEffect` の中で、`openedAt` が空なら記録の操作を呼ぶ。送ったあとは、詳細と一覧の取得結果の `openedAt` を書き換え、同じ記事で二度送らない。
アプリは、表示中の記事（`currentId`）が変わったときに同じことをする。先に読み込んだ隣の記事では送らない。
記録の失敗は画面に出さない。読む操作を止めるほどのことではなく、次に開いたときに送り直せる。

### 統計は1つの問い合わせで数える

対象は、`origin = 'feed' AND feed_id = ? AND created_at >= 30日前` の行である。由来の条件を付けるのは、生成記事が同じ表にあるからである。

- 届いた記事は、行の数である
- 開いた記事は、`opened_at IS NOT NULL` の数である
- スターを付けた記事は、`starred = 1` の数である
- フィルターで隠した記事は、`filtered = 1 AND starred = 0` の数である。フィルターの一覧の件数と同じく、スターのある記事は隠れていないので数えない
- 重複の除去で隠した記事は、重複の除去が有効なら `duplicate_of IS NOT NULL` の数、無効なら0である

APIは `GET /api/v1/feeds/:id/stats` を足す。応答は `since`、`received`、`opened`、`starred`、`hiddenByFilters`、`hiddenAsDuplicates`、`lastNewItemAt` を持つ。
割合は画面が四捨五入で求める。表示の形の問題で、APIに持たせる必要がない。
購読フィードの一覧の `recentArticleCount` は、同じ条件の行の数を購読フィードごとにまとめて数える。どちらも1つの関数から作り、値が食い違わないようにする。
移行で `(feed_id, created_at)` の部分索引を `feed_id IS NOT NULL` の行に張る。いまの `articles_feed_updated` は並びの時刻の索引で、保存の時刻の範囲には使えない。

期間を公開日時ではなく保存の時刻で測るのは、「届いた」がsmarternewsに届いたことを指すからである。公開日時のない項目もある。

### 一覧の印と並べ替え

`FetchState` に、更新が止まっていることの印（`Badge`）を足す。印の言葉は、更新が止まっていることをそのまま言う短い文にする。無効な購読フィードの印と取り違えないよう、「停止」の語は使わない。
行には、直近30日の件数と、最後に新しい項目が現れた日時を足す。新しい項目が一度も現れていなければ、その旨の言葉を出す。

並べ替えは、一覧の上の切り替え（チェックボックス）にする。入れている間は、更新の止まった購読フィードと直近の取得に失敗した購読フィードを、安定した分け方で先頭へ移す。並べ替えは画面の中だけで行い、保存した並び順は変えない。
切り替えの状態は画面の中だけに持ち、画面を開き直すと切れた状態に戻る（#64の第3ラウンドQ9）。
ブラウザーに覚えさせる案は採らない。開くたびにいつもの並び順で表示すれば、並び順が左のペインと違う理由を利用者が覚えておく必要がない。

### 移行

次の空いている番号の移行で、3つの列と索引を足す。同じ時期の別の変更も移行を足すので、番号は実装の時点で決める。

- `last_new_item_at`: 登録済みの購読フィードには、その購読フィードの配信記事の `created_at` の最大値を入れる。配信記事がなければ値なしにする
- `opened_at`: すべて値なし。既読の時刻から埋めない。既読の時刻には一括の既読も含まれ、開いたかどうかを表さないからである
- `stale_feed_days`: 既定60

## Risks / Trade-offs

- 更新の直後は、開いた記事の数が少なく出る → 開いた時刻は、この版から記録を始める。直近30日の統計がそろうのは、更新から30日後である。`docs/api.md` に書く
- `feed_items_seen` は、長く配信されなかった識別子を消す → 消えた項目をフィードがまた配信すると、新しい項目として数える。まれな場合で、数えすぎても印が出ないだけで済む
- 識別子を毎回変えて同じ記事を配信するフィードは、止まっていると判定されない → フィードに新しい項目が現れたことで数えると決めた（#64の第2ラウンドQ5）。受け入れる
- 記事を開くたびに要求が1つ増える → 開いた時刻のない記事でだけ送る。2回目からは送らない
- フィルターで隠した数は、いまのフィルターでの数である → 受け取ったときの隠れ方は残していない。フィルターを変えると、過去30日の数も変わる。統計の区画の説明に書く

## Migration Plan

1. 移行を足した版に更新する。列の追加と索引の作成だけで、記事の書き換えはない。
2. 更新の直後から、一覧の印と統計が出る。開いた記事の数は、更新のあとに開いた記事から増える。
3. 戻すときは、更新の前に取ったデータベースの控えに戻す。
