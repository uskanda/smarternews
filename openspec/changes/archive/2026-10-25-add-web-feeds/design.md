# Design

## Context

動機はproposal.mdのWhyにある。ここでは、方式を決めるのに要る現状だけを書く。

- 購読フィードの取得は `fetchFeed`（`packages/core/src/feeds/ingest.ts`）が行う。文書を `parseSubscription` で `ParsedSubscription` に読み、`storeItems` が項目を配信記事として保存する。識別子のない項目は、元のページのURLで見分ける。公開日時のない項目は、取得の時刻で並ぶ。
- 取得は `FeedPoller`（`packages/core/src/feeds/poller.ts`）の1本の列で直列に動く。登録（`subscribe`）も `exclusive` でこの列に入る。
- 購読フィードの取得は、`Fetcher` の取得先の制限、ホストごとの間隔、User-Agent、大きさと時間の上限に従う。`robots.txt` には従っていない。`robots.txt` に従うのは、全文の取得と要約が使う `PageFetcher`（`packages/core/src/fetch/pages.ts`）である。
- フィードを探す操作（`discoverFeeds`、`packages/core/src/feeds/discover.ts`）は、`linkedom` でページを読む。この依存は、セレクターでの抜き出しにも使える。
- LLMの呼び出しは `TaskRunner`（`packages/core/src/llm/runner.ts`）だけが行う。呼び出しは `llm_calls` に1行ずつ残る。1日の数え方は2つある。`callsToday` は要約以外のすべてを数え、`summariesToday` は要約だけを数える。やり直しの2回目も1回と数える。
- 割り当てのないタスクは `resolveAssignment`（`packages/core/src/config.ts`）が決める。要約と翻訳は `fast` があればそれへ、ほかは `tasks.default` へ回す。`providers` を書かない設定の `tasks.default` は `smart` である。
- タスクの入力のうちWebから得た文字列は、`material()`（`packages/core/src/llm/tasks.ts`）で囲み、指示として読ませない。
- AGENTS.mdの規則は「購読フィードの取得、配信記事の保存、フィルターの判定ではLLMを呼ばない」と書いている。この変更は、規則にセレクターの提案のタスクだけを例外として書き足す。AGENTS.mdはこの変更の仕様の段階では書き換えず、tasks.mdの作業として実装と同じブランチで直す。

## Goals / Non-Goals

**Goals:**

- Webページの購読フィードの取得と保存を、いまの `storeItems` にそのまま通す。項目の識別、書き換えの検出、古い項目の除外、重複の除去、フィルター、新しい項目が現れた時刻の記録を、作り直さずに使う。
- LLMを呼ぶのは、利用者が候補を求めた1回だけにする。取得の経路には、LLMを呼ぶコードを置かない。
- 上限とLLMの失敗のどちらでも、候補を求める操作をエラーにしない。

**Non-Goals:**

- JavaScriptを実行するブラウザーでの取得。
- 一覧のページの複数ページ目をたどること。登録したURLの1ページだけを読む。
- 3時間前のような相対の日時を読むこと。読めない日時は、日時なしとして扱う。
- セレクターの提案の回数を、プロバイダーの状況のAPIと実行の画面に出すこと。

## Decisions

### 種類とセレクターの組は、`feeds` の表の列に置く

移行で `feeds` に2つの列を足す。表の作り直しは要らない。

- `format`：`feed` か `page`。既定は `feed` とし、登録済みの購読フィードは `feed` になる
- `page_selectors`：セレクターの組のJSON（`item`、`title`、`link`、`date`）。`format` が `page` のときだけ値を持つ

APIの項目名も `format` と `selectors` にする。`kind` は種別（カテゴリの `kind`）と紛れるため使わない。
4つの列に分ける案は採らない。セレクターの組は常にまとめて読み書きするため、1つの値で扱うほうが単純である。
移行の番号は、実装のときに、その時点の最後の番号の次にする。並行して書いているほかの変更も、移行を足す見込みがあるためである。

### 抜き出しは `ParsedSubscription` を作り、保存は `storeItems` に任せる

ページから記事を抜き出す処理を `packages/core/src/feeds/page.ts` に置く。処理はHTML、ページのURL、セレクターの組を受け、`ParsedSubscription` を返す。

- `title` はページの `<title>`、`siteUrl` はページのURLとする。
- 項目ごとに `key` は空、`url` はリンクの絶対のURL、`contentHtml` は空の文字列、`author` は空とする。`key` が空なので、`storeItems` はURLで項目を見分ける。
- タイトルのセレクターがなければ、リンクの要素の文字列を使う。リンクのセレクターがなければ、項目の中の最初の `a[href]` を使う。項目の要素そのものが `a` のときは、その要素を使う。
- 日時は、要素の `datetime` の属性、なければ要素の文字列を読む。読める形は、ISO 8601、`YYYY-MM-DD`、`YYYY/MM/DD`、`.` で区切った年月日、`YYYY年M月D日` と、それに続く時刻である。時差のない日時は、全体設定のタイムゾーンで読む。

`fetchFeed` と `subscribe` は `format` を見て、文書の読み方だけを切り替える。そのため、保存より後の処理は種類を区別しない。

### ページの取得は `PageFetcher` を通す

Webページの購読フィードの取得、登録、候補、見本は、すべて `PageFetcher` でページを取得する。`robots.txt` の禁止は、失敗の理由 `robots.txt forbids` として購読フィードに記録する。
`FeedPoller` は、全文の取得の処理と同じく、`remember: false` の `PageFetcher` を1つ持ち、1日ごとに作り直す。作り直すのは、変わった `robots.txt` を読み直すためである。
Webページの購読フィードでは、`ETag` と `Last-Modified` による条件付きの要求をしない。`PageFetcher` にその経路がなく、記事の一覧のページはこの値を持たないことが多いためである。版を示す値を保存しないため、仕様の「変更のないフィードの取得」の条件にも当たらない。

### 記事が見つからない取得は失敗として記録する

項目のセレクターに当たる要素がないとき、抜き出しの処理は `no element matches the item selector` の理由で例外を投げる。`fetchFeed` はほかの失敗と同じく、これを捕まえて `recordFetchFailure` で記録する。`storeItems` は呼ばれず、`last_new_item_at` は変わらない（第4ラウンドQ1）。
失敗として記録するのは、構造の変化を次の取得の直後に知らせるためである。購読フィードの一覧は、失敗している購読フィードの行に失敗の理由を出す（web-settingsの「購読フィードの一覧」）。成功として記録すると、更新の止まった印が付くまで、利用者は気づけない。
仕様の「失敗が続くときの間隔」は、この失敗にもそのまま当てはまる。続けて失敗するたびに間隔が2倍に延び、24時間で止まる。構造の変わったページを取得周期のたびに読み続けないため、当てはめを外す理由はない。
更新の止まった購読フィードの判定は、取得の失敗とは別に行う。そのため、この状態が止まったとみなす日数より長く続けば、失敗の理由に加えて更新の止まった印も付く。第2ラウンドQ7が挙げた目印は、そのまま働く。
項目のセレクターに当たる要素はあるが、どの要素からもリンクかタイトルを抜き出せないときは、決定の範囲の外である。この設計は、その取得を成功として記録する。

### セレクターの候補を作る処理

候補の処理を `packages/core/src/feeds/propose.ts` に置く。順は次のとおりである。

1. `PageFetcher` でページを取得する。取得できなければ、理由を付けて入力が不正であることを返す。
2. `TaskRunner` に、提案を呼べるかどうかを問う。提案の1日の上限か、`llmCallsPerDay` に達していれば、手順4へ進む。
3. HTMLを整え、セレクターの提案のタスクを呼ぶ。タスクの予算は、実行と結び付かない新しい `CallBudget`（`runId` は空）とする。`LlmLimitError` と `TaskFailedError` は捕まえて手順4へ進む。返った候補を元のHTMLに当て、記事を1件以上抜き出せたものだけを残す。1件も残らなければ手順4へ進む。
4. プログラムで候補を推定する。
5. 候補ごとに見本（件数と10件までの記事）を作って返す。手順4を通ったときは、LLMの提案を使わなかったことと、その理由（`limit`、`failed`、`empty`）を付ける。

候補は、整えたHTMLではなく元のHTMLに当てる。定期的な取得が読むのは元のHTMLだからである。位置で数えるセレクター（`:nth-child` など）は、取り除いた要素の数でずれるため、プロンプトで避けるよう指示する。
見本の要求は、手順1と手順5だけを通る。LLMは呼ばない。

### LLMに渡すHTMLの整え方

`linkedom` で読んだ文書から、`script`、`noscript`、`template`、`style`、`link[rel~=stylesheet]`、`iframe`、`embed`、`object` の要素を取り除く。要素の `style` の属性と、`on` で始まる属性も取り除く。コメントも取り除く。
残りを文字列に戻し、先頭から50,000文字までを `material()` で囲んで渡す。`class` と `id` の属性は、セレクターの手がかりなので残す。

### プログラムでの候補の推定

`packages/core/src/feeds/infer.ts` に、リンクの多い領域を探す処理を置く。

- 要素ごとに、子の要素を、要素名と `class` の組で分ける。
- 3つ以上の要素からなり、その8割以上が文字列を持つ `a[href]` を含む組を、候補の領域とする。`nav`、`header`、`footer`、`aside` の中の組は除く。
- 点数は、要素の数とリンクの文字列の長さの中央値の積とする。点数の高い順に3つまでを候補にする。
- 項目のセレクターは、最も近い `id` を持つ祖先からの子の結合子で作る。`id` がなければ、`class` を3段までつなぐ。項目が `time` の要素を含むときは、日時のセレクターを `time` にする。

規則で決まる推定にしたのは、結果を再現でき、テストで固定できるからである。

### タスクの名前、出力、割り当て

タスクの名前は `proposeSelectors` とし、`TASK_NAMES` と `config.yaml` の `tasks` の項目に足す。
出力のスキーマは、1つから3つの候補の配列とする。各候補は `item`（必須）と `title`、`link`、`date`（省略可）の文字列で、1つの値は300文字までとする。
スキーマで表せない検査は `check` に置く。各セレクターを空の文書の `querySelector` に渡し、例外になれば出力を不正とする。不正な出力は、ほかのタスクと同じく1回だけやり直す。
`resolveAssignment` では、要約と翻訳の `fast` と同じ形で、このタスクに `smart` を優先させる。`smart` がない設定では、`tasks.default` を使う。ほかのタスクの割り当ては変えない。

### 回数の上限

`config.yaml` の `limits` に `selectorProposalsPerDay`（既定50、0以上）を足す。0は、LLMを呼ばずに推定だけを使う設定になる。
`llmCallsPerDay` の既定を300から350にする。
`TaskRunner` の `#spend` は、このタスクについて、その日の `proposeSelectors` の呼び出しと `callsToday` の両方を上限と比べる。`callsToday` は要約以外を数えるため、提案は何も変えずに `llmCallsPerDay` へ数えられる。

### APIの操作

- `POST /api/v1/feeds/page/candidates`：`{ url }` を受け、候補、見本、`usedModel`、`fallback` を返す。
- `POST /api/v1/feeds/page/preview`：`{ url, selectors }` を受け、件数と10件までの記事を返す。
- `POST /api/v1/feeds`：`format: "page"` と `selectors` を受ける。`format` を省けば、いまと同じフィードの登録とする。
- `PATCH /api/v1/feeds/{id}`：`selectors` を受ける。`format` が `feed` の購読フィードへの指定は400で拒否する。`format` は変えられない。
- 購読フィードの一覧と詳細は、`format` と `selectors` を返す。

「候補を出し直す」には専用の操作を足さない。画面は、購読フィードのURLで候補の操作を呼び、選んだ組を `PATCH` で保存する。
候補の操作は、LLMの応答を待ってから返す。待つ時間の上限は `llm.timeoutMs`（既定180秒）である。

### 設定ファイルとOPML

設定ファイルの購読フィードの項目に、省略できる `selectors` を足す。`selectors` があれば、Webページの購読フィードとして扱う。
読み込みで、URLの一致する購読フィードと種類が違うときは、その項目の位置を示して、ファイル全体を拒否する。
OPMLの書き出しは、`format = 'feed'` の購読フィードだけを書く。

### 画面

`apps/web/src/settings/FeedsPage.tsx` の追加と編集を変える。

- フィードが見つからないときの文に、「このページを購読する」ボタンを足す。押すまで、候補の操作は呼ばない。フィードが見つかったときは、このボタンを出さない（第4ラウンドQ2）。フィードを持つサイトはフィードで読むほうが確かで、ページの抜き出しは構造の変化で外れるためである。
- 候補を待つ間は、候補を探していることを表示する。候補は1つだけ選べる形で並べ、各候補の下に件数と見本を出す。
- `usedModel` が偽のときは、LLMを使わずに候補を出したことを伝える一文を、誤りでない文の見た目で出す。文言はUIの文として敬体で書く。候補が空のときは、同じ一文に続けて、セレクターを入れる欄と「見本を見る」ボタンを出す。
- 全文を自動で取得する切り替えは、入った状態で始める（第4ラウンドQ3）。ページから得るのはタイトル、リンク、日時だけで、切り替えが切れていると配信記事の本文が空のまま残るためである。サーバーの既定（無効）は変えない。
- 編集の画面には、`format` が `page` のときだけ、セレクターの組の欄、「見本を見る」、「候補を出し直す」を出す。

アプリは変えない。Webページの購読フィードの配信記事は、ほかの配信記事と同じに表示する。

## Risks / Trade-offs

- ページのHTMLに、LLMへの指示に見える文字列が含まれる → `material()` で囲み、出力をセレクターの文字列だけに限る。不正なセレクターは `check` で捨て、候補はページに当てて確かめてから返す。
- `class` の名前がビルドのたびに変わるサイトでは、セレクターがすぐに外れる → 一覧の失敗の理由と更新の止まった印で気づき、「候補を出し直す」で直す。推定とLLMのどちらにも、意味のある名前の `class` を優先させる。
- 全文を取得するまで、配信記事の本文は空である → 追加の画面で全文の自動の取得を入れた状態にする。本文のペインには、元のページへのリンクと、いまの全文の取得の操作が出る。
- 提案の呼び出しは `llmCallsPerDay` を使うため、多く求めた日は実行が早く上限に達する → 提案の1日の上限で50回までに抑え、`llmCallsPerDay` を50回増やす。
- `llmCallsPerDay` を書いていない利用者は、更新で1日の上限が50回増える → READMEと `docs/providers.md` に既定の変更を書く。
- Webページの購読フィードだけが `robots.txt` に従い、RSSとAtomの購読フィードは従わない → 決定（第1ラウンドQ6）の範囲である。フィードは配信のために公開されているため、いまの扱いを変えない。
- 候補の操作はLLMの応答を最長180秒待つ → 画面は待っていることを表示する。時間切れは推定に切り替わるため、エラーで終わらない。

## Migration Plan

1. 移行で、`feeds` の表に `<format>`（既定 `feed`）と `<page_selectors>` の列を足す。登録済みの購読フィードは、すべて `feed` になる。
2. `config.ts` の `llmCallsPerDay` の既定を350にし、`selectorProposalsPerDay` を足す。`examples/config.example.yaml` と文書を同じ値に直す。
3. AGENTS.mdの規則に、セレクターの提案のタスクの例外を書き足す。
4. 戻すときは、前の版のサーバーへ戻す。足した列は前の版から読まれないが、Webページの購読フィードは `feed` として取得されて失敗し続ける。戻す前に、Webページの購読フィードを削除するか無効にする。
