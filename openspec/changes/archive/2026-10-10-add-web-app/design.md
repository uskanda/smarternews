# Design

## Context

動機と範囲は `proposal.md` に書いた。ここでは作り方を決める。

サーバーには、記事、設定、実行を扱うAPIがそろっている。画面はこのAPIだけを使う。
設計を縛る条件は次の4つである。

- 利用者は1人で、到達できるのはLANとTailscaleの中だけ。通信は素のHTTPで、証明書はない。
- サーバーはビルドなしで動いている。画面はビルドを要するので、画面を使わない人の手順を増やさない。
- 後のAndroidアプリも同じAPIを使う。APIの型は `packages/core` のスキーマを正本にする。
- 見た目の値は `DESIGN.md` を正本にする。画面のコードに色や大きさの値を直接書かない。

## Goals / Non-Goals

**Goals:**

- 毎朝の未読を、記事を開く操作と次へ進む操作だけで読み終えられる。
- トピックの文章を直すのに必要な情報（除外の理由、検索語、判定基準）へ、画面の中でたどり着ける。
- 画面のテストを、偽のAPIではなく実物のAPIに対して動かす。
- 幅の狭い端末でも、同じ機能を使える。

**Non-Goals:**

- 記事の検索、圏外での閲覧、サーバーからの通知。
- プロバイダーの設定の変更。表示だけにする。
- 複数の利用者と、利用者ごとの表示設定の保存。

## Decisions

### D1. 構成

`apps/web` を足す。React、Vite、TypeScriptで書き、ビルドの結果を `apps/web/dist` に出す。

| 役割 | 採用するもの | 理由 |
|---|---|---|
| 取得と再取得 | TanStack Query | 60秒ごとの再取得、続きの読み込み、楽観的な更新を持つ |
| 画面の切り替え | React Router | URLで項目と記事を表せる |
| スタイル | Tailwind v4 | `DESIGN.md` から出力した値をそのまま使える |
| ダイアログなどの部品 | Radix | キーボード操作と読み上げへの対応を持つ |
| 本文の表示 | react-markdown | 生のHTMLを解釈しない |
| 書体 | fontsourceのパッケージ | 外部のサーバーから読み込まずに同梱できる |

状態を持つ場所は3つに限る。サーバーの内容はTanStack Queryの中、選んでいる項目と記事はURL、トークンはブラウザーの保存領域である。

### D2. サーバーからの配信

`apps/server` に、`apps/web/dist` のファイルを返す処理を足す。

- `/assets/` の下のファイルは、名前に内容のハッシュが入るので、長い期間キャッシュさせる。
- それ以外のGETは、`/api/` と `/rss/` で始まるものを除いて `index.html` を返す。画面の中のパスを直接開いても表示できる。
- `dist` が無いときは、ビルドのコマンドを書いた短い文を返す。APIとRSSは変わらず動く。

HTMLの応答には次のヘッダーを付ける。

```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
  img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none';
  frame-ancestors 'none'; form-action 'self'
Referrer-Policy: no-referrer
X-Content-Type-Options: nosniff
```

スタイルだけ要素の属性での指定を許すのは、Radixが位置の計算結果を `style` 属性で付けるためである。スクリプトは同じオリジンのファイルに限る。
`Referrer-Policy` は、出典のサイトへ遷移するときにサーバーの宛先が伝わるのを防ぐ。

### D3. トークン

トークンは `localStorage` に保存する。入力されたトークンは、設定の取得を1回呼んで確かめてから保存する。
APIがHTTPステータス401を返したら、保存したトークンを消して入力の画面へ戻す。

ブラウザーに置いたトークンは、画面でスクリプトを実行されると読み取られる。対策は次の3つである。

- 記事の本文はreact-markdownで表示し、生のHTMLを解釈させない。リンクは `http`、`https`、`mailto` だけを通す。
- Content-Security-Policyで、外部のスクリプトと、HTMLの中に直接書いたスクリプトを禁じる。
- 画面のコードは `innerHTML` に当たる書き方を使わない。ESLintの規則で検出する。

### D4. URLと画面

| URL | 画面 |
|---|---|
| `/unread`、`/all`、`/starred` | 全カテゴリの一覧 |
| `/c/<識別名>` | カテゴリの一覧。種別がイベントならイベントの一覧 |
| 上の各URL + `/<記事の番号>` | 同じ一覧と、その記事の本文 |
| `/settings` | カテゴリの一覧、読み手情報、全体設定、設定ファイル、プロバイダー、トークン |
| `/settings/categories/<番号>` | カテゴリの編集と、そのトピック |
| `/runs`、`/runs/<番号>` | 実行履歴と、実行の詳細 |

`/` は `/unread` へ移す。既読を含める切り替えと重要度4以上の切り替えは、URLのパラメーターに持つ。再読み込みや戻る操作で同じ表示に戻る。

### D5. ペインと画面の幅

| 幅 | 表示 |
|---|---|
| 1100px以上 | 3ペイン |
| 720pxから1099px | 記事の一覧と本文の2ペイン。項目の一覧はボタンで開く |
| 719px以下 | 1ペイン。一覧から記事を開くと本文に切り替わり、戻るボタンで一覧に戻る |

狭い幅では、記事のURLが選ばれているかどうかで、一覧と本文のどちらを見せるかを決める。別の仕組みは持たない。

### D6. 一覧の動き

- 一覧は、APIの続きの値を使って50件ずつ読み込む。末尾が見えたら次を読み込む。
- 記事を開くと、既読への変更をすぐ画面に反映し、APIへ送る。失敗したら表示を戻して失敗を示す。
- 未読の一覧で既読になった記事は、その一覧に居る間は消さない。再取得の結果に、この一覧で読んだ記事を足して表示する。項目を移るか手動で更新すると消える。
- 再取得で先頭に記事が増えても、スクロールの位置は動かさない。ブラウザーの位置の固定に任せ、テストで確かめる。
- 一括の既読は、一覧を読み込んだ時刻、カテゴリ、重要度の下限をAPIに送る。応答の識別子を10秒間保持し、その間は取り消しのボタンを出す。

### D7. APIの変更

| 変更 | 内容 |
|---|---|
| 記事の一覧 | `minImportance` を受け付ける |
| 件数 | `GET /api/v1/counts`。全体の未読数とスターの数、カテゴリごとの未読数と総数を返す |
| 一括の既読 | `minImportance` を受け付け、既読にした記事の識別子を返す |
| 未読に戻す | `POST /api/v1/articles/mark-unread`。識別子の一覧を受け取る |

件数は、終了したイベントの記事を未読数に含めない。
全カテゴリの「未読」の一覧にも終了したイベントを出さないよう、種別を指定しない一覧でも終了したイベントを既定で除く。`includeEnded` を指定すると含める。

### D8. イベントの一覧

開始日時を全体設定のタイムゾーンの日付に直し、日付ごとにまとめる。すでに始まっていて終わっていないイベントは、先頭の「開催中」にまとめる。
複数の日にまたがるイベントは開始日の下に1度だけ出し、同じ行に終了日も表示する。

### D9. 設定の画面

カテゴリの編集とそのトピックを1つの画面に置く。トピックは、行を開くとその場で編集できる。
入力の検証は、`packages/core` のスキーマをそのまま使う。サーバーが返した誤りは、項目の名前で入力欄に結び付ける。
保存していない変更があるときは、移動の前に確認する。

カテゴリの削除の確認には、件数の操作が返す総数と、トピックの数を出す。

### D10. 実行の表示

待機中または実行中の実行がある間だけ、実行の一覧を3秒ごとに取得する。なくなったら60秒ごとに戻す。
除外した候補は、理由の順とトピックごとの2通りで見せる。まとめ直すのは画面の中で行い、APIは変えない。

### D11. PRODUCT.md と DESIGN.md

リポジトリの直下に置く。`DESIGN.md` の値は、grillingで確認した見本から取る。

| 役割 | 明るい配色 | 暗い配色 |
|---|---|---|
| 地 | `#F3F5F8` | `#10151B` |
| 紙面 | `#FFFFFF` | `#171D25` |
| 文字 | `#17202B` | `#E7EBF0` |
| 既読と補足 | `#586473` | `#9DA9B7` |
| 罫線 | `#D8DEE6` | `#2B3440` |
| 操作とリンク | `#24418F` | `#9CB6FF` |
| 重要度の印 | `#FFD84A` | `#E9C13A` |
| 見出しに重ねる印 | `#FFE98A` | `#5C4B12` |
| 未確認 | `#8A5200` | `#F0B45C` |
| 選択中の行 | `#E8EDF7` | `#212B3A` |

- 書体は、一覧と操作がIBM Plex Sans JP、本文と記事の見出しがShippori Mincho。どちらも端末の書体を代替に指定する。
- 角の丸みは4px。影は使わない。一覧は罫線で区切り、記事ごとの枠では囲まない。
- 目立たせる色は重要度の印だけにする。重要度4は見出しの左の短い線、5は見出しに重ねた印で示す。
- `DESIGN.md` の形式は色を1列で持つので、暗い配色は名前の末尾に `-dark` を付けた別の値として書く。画面のCSSで、端末の設定に応じて入れ替える。

`DESIGN.md` の値からCSSを作る変換を `scripts/` に置き、その出力を `apps/web` に置いてTailwindから読む。出力したファイルはコミットし、`make verify` で `DESIGN.md` とのずれを検出する。
`designmd export` は使わない。書体の指定を1つの文字列として出力し、行間を出力しないため、文字のスタイルに使えなかった。形式の検査とコントラストの検査には `designmd lint` を使う。

### D12. テスト

- 画面のテストはVitest、Testing Library、jsdomで書く。APIの呼び出し先に、テストの中で作った実物のアプリ（メモリ上のDBつき）を渡す。偽の応答は書かない。
- 仕様のScenarioを、ほぼ1対1でテストにする。実装より先にテストを書く。
- jsdomでは配置と色を確かめられない。幅ごとの表示、横方向へのはみ出し、暗い配色、遷移元のURLの秘匿は、完成時に実際のブラウザーで確かめ、結果を記録する。
- 配色のコントラストは `designmd lint` が検査する。
- 完成した画面に `/impeccable audit` をかけ、指摘を直すか記録する。

### D13. ビルドと導入

リポジトリの直下に `pnpm build` を足し、画面をビルドする。READMEの手順に1行加える。
`make verify` とCIには、画面のテストとビルドを足す。`dist` はコミットしない。

## Risks / Trade-offs

- ブラウザーに保存したトークンが盗まれる → D3の3つの対策を取る。到達できるのは閉じたネットワークの中だけである。
- 書体の同梱でビルドの結果が大きくなる → 文字の範囲ごとに分かれたファイルを使い、ブラウザーは表示に要る範囲だけを読み込む。大きさを計って `design.md` に記録する。
- jsdomで確かめられない見た目の不具合が残る → 実際のブラウザーでの確認をタスクに入れ、確かめた幅と配色を記録する。
- 一覧の再取得と、読んだ記事を残す動きがぶつかる → 残す記事の番号を一覧ごとに持ち、再取得の結果と合わせてから表示する。この合成を1つの関数にしてテストする。
- 種別を指定しない一覧から終了したイベントを除くと、RSSを読むアプリ以外の利用者の表示が変わる → 利用者はまだ画面を持たないので影響はない。`includeEnded` を指定すれば従来どおり取得できる。
- Tailwind v4は新しいブラウザーを要する → 利用者の端末は自分で選べるので問題にしない。対象のブラウザーをREADMEに書く。

## Migration Plan

1. サーバーを更新し、`pnpm build` を実行する。
2. サーバーを再起動し、ブラウザーで `/` を開いてトークンを入力する。

DBの変更はない。元に戻すときは、以前のコミットに戻してサーバーを再起動する。

## 実装で分かったこと

### ビルドの大きさ

| 対象 | 大きさ | gzipのあと |
|---|---|---|
| スクリプト | 672KB | 202KB |
| スタイル | 433KB | 138KB |
| 書体（980ファイル） | 24MB | 圧縮しない |

書体は文字の範囲ごとに分かれていて、ブラウザーは表示に使う範囲だけを読み込む。スタイルの大半は、その範囲の定義である。
サーバーは、スクリプト、スタイル、HTMLをgzipで圧縮して返す。圧縮の結果はメモリに持つ。

### 実際のブラウザーでの確認

2026-10-10に、ビルドした画面をサーバーから配り、Chromiumを操作して確かめた。データは、実物のLLMで作ったニュースとイベントの記事である。

- 幅1280pxと390px、明るい配色と暗い配色の4通りで、7つの画面を表示した。28通りすべてで横方向へのはみ出しは0pxだった。
- Tabキーだけで項目の一覧から記事を開き、スターを付けられた。フォーカスのある部品には2pxの枠が出た。
- 出典のリンクを開いたとき、遷移先への要求に遷移元のURLは付かなかった。
- 画面の表示中に、外部のサーバーへの要求は発生しなかった。
- 不具合を1つ見つけて直した。小さい書体のファイルがdata URIとしてスタイルに埋め込まれ、Content-Security-Policyに止められていた。ビルドの設定で埋め込みをやめた。

### 監査の結果

`/impeccable audit` の観点で計測した。直したものは次の4つである。

- ボタンと入力欄の枠が、地に対して1.35対1しかなかった。枠の色を分け、3対1以上にした（WCAG 1.4.11）。
- 幅390pxで、ボタンが32px、単独のリンクが20px前後の高さだった。指で操作する端末では44px以上にした。
- 狭い画面で本文だけを表示すると、ページの見出しがなく、フォーカスも失われた。見出しを足し、記事の見出しへフォーカスを移すようにした。
- 項目の一覧を飛ばして内容へ移るリンクを、最初のTabで出すようにした。

文字のコントラストは、明るい配色で5.1対1以上、暗い配色で6.0対1以上だった。
検出器の指摘は2件で、どちらも直していない。読み手への影響の左の線は、grillingで確認した重要度の印と同じ見立てである。引用の左の線は、引用の一般的な表し方である。
残した点は1つある。スクリプトは1つのファイルで672KBあり、画面ごとに分けていない。利用者が1人でLANの中なので、分割は見送った。
