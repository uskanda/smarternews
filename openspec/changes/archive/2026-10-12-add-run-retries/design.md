# Design

## Context

実行は `RunQueue` が1件ずつ行う。順番は、プロセスの中の約束の連なりで持っていて、保存していない。
実行履歴の表には、カテゴリと定時の時刻の組に一意の索引がある。定時の時刻1つにつき、実行履歴は1件である。
起動のとき、`failInterruptedRuns` が、実行中と順番待ちの実行履歴をすべて「失敗」に変える。
スケジュールは、1分ごとに、定時の時刻が来たカテゴリを順番待ちに入れる。その回の実行履歴があるかどうかで、二重の実行を防いでいる。

## Goals / Non-Goals

**Goals:**

- やり直しの予定を保存し、再起動をまたいで保つ。
- 定時の時刻1つにつき実行履歴が1件、という索引と二重の防止を変えない。
- やり直しが無限に続かないことを、保存した値だけで保証する。

**Non-Goals:**

- 「一部失敗」の実行で、失敗した取得元だけをやり直すこと。
- やり直しの間隔を、設定で細かく変えられるようにすること。

## Decisions

### やり直しは、定時の時刻を持たない別の実行履歴にする

移行で、実行履歴の表に次の列を足す。

- `attempt`: 何回目のやり直しか。やり直しでない実行は0
- `retry_of`: 元の定時の実行のid。やり直しでない実行は空
- `retry_at`: この実行が失敗したあとの、次のやり直しの予定の時刻。予定がなければ空
- `retry_skipped`: 予定がない理由（`limit`、`superseded`、`disabled`、`manual`）。予定があるとき、失敗していないときは空

やり直しの実行履歴は、`trigger` を `schedule` のままにし、`slot` を空にする。一意の索引に当たらない。
元の実行履歴は残るので、スケジュールは、その回を実行済みと見なしたままになる。
`retry_of` は、何回目であっても最初の定時の実行を指す。画面が元の実行へ移るのに、たどる必要がない。

### 予定は失敗の時点で決め、1分ごとの確認で実行する

実行が「失敗」で終わったとき、`RunQueue` は、その実行が定時の実行かそのやり直しであれば、`attempt` と設定の回数を比べる。
残りがあれば `retry_at` に、失敗の時刻に待ち時間を足した値を入れる。なければ `retry_skipped` に `limit` を入れる。
待ち時間は、次のやり直しが1回目なら10分、2回目なら30分、3回目なら90分とする。
スケジュールの1分ごとの確認に、予定の時刻を過ぎた実行履歴を探す処理を足す。見つけたら、取りやめの条件を確かめる。
条件に当たらなければ、新しい実行履歴を作って順番待ちに入れ、元の行の `retry_at` を空にする。
プロセスの中で時間を待つ方式は、再起動で予定を失う。保存した時刻を確認する方式なら、停止中に過ぎた予定も、起動のあとの最初の確認で見つかる。

### 取りやめは、順番待ちに入れる直前に判定する

取りやめの条件は次のとおりである。

- 元の実行より新しい定時の実行履歴が、同じカテゴリにある（`superseded`）
- カテゴリが無効である、または有効なトピックがない（`disabled`）

カテゴリを削除すると、実行履歴も一緒に消えるので、予定も消える。
当たったときは、`retry_at` を空にし、`retry_skipped` に理由を入れる。

### 起動のときは、順番待ちを再開し、実行中だけを失敗にする

`failInterruptedRuns` を2つの処理に分ける。

- 状態が順番待ちの実行履歴は、そのまま、idの順に `RunQueue` へ入れ直す。新しい実行履歴は作らない。
- 状態が実行中の実行履歴は、いまと同じく「失敗」にし、理由に中断を書く。定時の実行かそのやり直しなら、`retry_at` に起動の時刻を入れる。回数が残っていなければ `retry_skipped` に `limit` を入れる。

実行中だったものを1回分と数えるのは、止まるたびに同じ実行が始まり直して、終わらなくなるのを防ぐためである。
`RunQueue` に、既存の実行履歴を順番待ちへ入れる入口を足す。いまの `enqueue` は、必ず新しい実行履歴を作る。

### 設定は `limits` の1項目にする

`config.yaml` の `limits` に `runRetries` を足す。0から3の整数で、既定は2とする。
上限を3にするのは、待ち時間の合計が約2時間（10分、30分、90分）で、多くのカテゴリの次の定時より前に収まるからである。

### 重複の防止は、いまの仕組みに任せる

実行は、判定済みのURLの記憶と、続報の判定で、同じ話題の記事を2度作らない。やり直しも同じ処理を通る。
失敗した実行が作った記事は、失敗のあとも残る。やり直しは、残りの候補だけを扱う。
記事を書く途中で失敗させるテストを足し、このことを確かめる。新しい仕組みは足さない。

## Risks / Trade-offs

- 原因が続く失敗（設定の誤り、プロバイダーの停止）で、LLMを3回分使う → 回数の上限と、1日の呼び出しの上限がある。「上限で停止」はやり直さない。
- やり直しが、ほかのカテゴリの定時の実行を待たせる → 実行は1件ずつなので、順番待ちの後ろに入るだけである。追い越さない。
- 再開した順番待ちの実行が、古い定時のものである → 逃した定時を補う範囲（6時間）より古い順番待ちは、再開せずに「失敗」にする。

## Migration Plan

- 移行は列を足すだけである。既存の実行履歴は、やり直しでない実行（0回目、予定なし）になる。
- 移行より前に失敗した実行は、やり直さない。
- 戻すときは、前の版に戻す。足した列は、前の版のコードが読まないので残してよい。
