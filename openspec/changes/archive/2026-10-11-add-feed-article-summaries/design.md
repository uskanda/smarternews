# Design

## Context

配信記事は、生成記事と同じ `articles` の表に入っている。内容は、保存の前にMarkdownへ変換してある。
購読フィードの取得は `FeedPoller` が直列に行い、LLMを呼ばない。仕様 `feed-subscriptions` と `AGENTS.md` が、これを規則にしている。
LLMの呼び出しは、タスクの定義とプロバイダーのアダプターを通す。呼び出しは `llm_calls` の表に、タスクの名前とともに記録している。
記事のページの取得には `PageFetcher` がある。`robots.txt` に従い、同じホストへの間隔を空ける。実行の中で本文を取り出す処理も、すでにある。

## Goals / Non-Goals

**Goals:**

- 取得と保存の速さと確かさを、いまのまま保つ。
- 要約の回数を、記事を書く実行と取り合わないようにする。
- 要約を、ほかのタスクと同じ仕組み（定義、検証、記録、割り当て）に載せる。

**Non-Goals:**

- 記事ごとに要約を頼む操作。
- 取得したページの本文を保存して、内容の代わりに表示すること。
- 生成記事の要約。

## Decisions

### 要約は、取得とは別の直列の処理にする

`packages/core/src/feeds` に、要約を待つ記事を1件ずつ処理する部品を足す。`FeedPoller` と同じく、一定の間隔で動き、前の1件が終わるまで次を始めない。
取得の中で要約すると、取得がLLMの遅さと失敗に左右される。仕様の「LLMを使わない取得」も保てなくなる。
実行の順番待ちに載せる方式は、要約が記事を書く実行を待たせるので採らない。

### 待っている記事は、列の値から問い合わせで求める

待ち行列の表は作らない。次の条件に当たる配信記事を、時刻の新しい順に1件取る。

- 購読フィードの自動の要約が有効である。
- 記事を保存した時刻が、自動の要約を有効にした時刻より後である。
- 要約がなく、未読で、失敗の回数が2回に満たない。
- ストップワードで隠れていない。

移行で次の列を足す。

- `feeds`: `auto_summarize`（0か1）、`auto_summarize_since`（有効にした時刻。無効のときは空）
- `articles`: `auto_summary`（要約の文章）、`auto_summary_source`（`page` か `feed`）、`auto_summary_at`
- `articles`: `auto_summary_attempts`（失敗の回数）、`auto_summary_skipped`（内容が短くて作らなかった印）

列を足すだけなので、表の作り直しは要らない。
記事には保存した時刻の列がないので、`created_at` を足し、既存の行には並びの時刻を入れる。有効にした時刻との比較は、この列で行う。
既存の `summary` の列は、一覧に出す抜粋として使っている。要約は別の列に置き、APIでも `autoSummary` という別の項目にする。

### 1日の上限は、呼び出しの記録から数える

`config.yaml` の `limits` に `summariesPerDay` を足す。既定は100とする。
その日の要約の回数は、`llm_calls` のタスクが `summarize` の行を、設定したタイムゾーンの0時から数える。
記事を書く実行の1日の上限は、`summarize` の行を数えから外す。いまの数え方がタスクを区別していないので、ここを直す。

### 要約のタスクは、ほかのタスクと同じ形で定義する

`packages/core/src/llm/tasks.ts` に `summarize` を足す。入力は見出しと本文、出力は `{ "summary": string }` とする。
指示には、本文にあることだけを書くこと、出力言語で書くこと、400文字以内にすることを入れる。
プロバイダーの割り当ては `tasks` の `summarize` で行う。割り当てがないときは `fast` を使う。既定の `default` に従わせると、高いモデルで大量に呼ぶことになる。

### 全文は、いまのページの取得と本文の取り出しを使う

要約の処理は、自分用の `PageFetcher` を1つ持つ。1件につき1ページだけを取得する。
本文の取り出しは、実行が候補のページから本文を取り出すのと同じ関数を使う。
取得できないとき、取り出した本文が200文字に満たないときは、保存済みの内容（`content_text`）を入力にし、`auto_summary_source` を `feed` にする。
それも200文字に満たなければ、`auto_summary_skipped` を立てて、LLMを呼ばない。

### 表示は、内容の前の区画にする

Webとアプリの本文の画面で、元のページを開く操作と内容の間に、要約の区画を置く。見出しは「AIによる要約」とする。
要約は文章として表示し、Markdownの画像は描かない。
要約を待っているかどうかは、サーバーが上の条件で判定してAPIで返す。画面は条件を持たない。

### `AGENTS.md` の規則を書き足す

「購読フィードの取得、配信記事の保存、ストップワードの判定ではLLMを呼ばない」は保つ。
続けて、要約は保存のあとの別の処理が行うこと、対象は利用者が選んだ購読フィードだけであることを書く。
「LLMを呼ぶのは仕様で定義したタスクだけ」の規則は、仕様にタスクを足すので、そのまま成り立つ。

## Risks / Trade-offs

- 記事の多い購読フィードで有効にすると、1日の上限まで毎日使う → 上限は要約だけのもので、既定を100回に抑える。切り替えのそばにLLMを使うことを書く。
- 配信元のサイトへ、記事ごとに1回の取得が増える → 取得の作法に従い、同じホストへの間隔を保つ。既読の記事は取得しない。
- 要約が本文にないことを書く → 指示で禁じ、区画の見出しでLLMが書いたものだと示す。元の内容はいつも下に残す。
- `claude` コマンドの利用枠に近づく → 記事を書く実行の上限とは別なので、合計は最大で両方の和になる。`docs/providers.md` に書く。

## Migration Plan

- 移行は列を足すだけである。既存の購読フィードは自動の要約が無効で、動きは変わらない。
- 戻すときは、前の版に戻す。足した列は、前の版のコードが読まないので残してよい。
