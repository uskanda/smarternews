# Design

## Context

記事の一覧は `packages/core/src/db/articles.ts` の `listArticles` が返す。並びは `updated_at DESC, id DESC` に固定で、続きの値は `[updated_at, id]` を符号化したものである。
配信記事の `updated_at` には並びの時刻が入る。並びの時刻は公開日時で、ないときと未来のときは取得の時刻である。このため「生成記事は最終更新、配信記事は並びの時刻」は、この1つの列で表せる。
種別がイベントの一覧（`kind=event`）は `event_starts_at ASC` で並ぶ。最近読んだ記事の一覧（`recentlyRead=true`）は `read_at DESC` で並び、別の関数が返す。検索の結果は `pageArticles` が `updated_at DESC` で返す。
`articles_updated` などの索引は `(…, updated_at, id)` の昇順で張ってあり、逆向きにも使える。

左のペインとアプリの引き出しの項目は、`packages/client/src/nav.ts` の `buildNav` が組み立てる。項目は次のとおりである。

- 固定の項目は、「未読」（`unread`）、「すべて」（`all`）、「スター」（`starred`）、「AI生成」（`generated`）、「最近読んだ記事」（`recentlyRead`）の5つ
- カテゴリ（`category-<id>`）。購読フィードを持つカテゴリの下には、「AI生成」（`category-<id>-generated`）と購読フィード（`feed-<id>`）が並ぶ
- 「未分類」（`uncategorized`）。カテゴリのない購読フィードがあるときだけ出る

`listKey` と `parseListKey` は、項目と短い文字列を行き来させる。`targetFilter` は項目から一覧の問い合わせを作る。
読んだ記事を一覧に残す `mergeKept`（`packages/client/src/merge.ts`）は、取得した記事と残す記事を新しい順で混ぜる。

一括の既読の時刻は、Webとアプリが同じ方法で作っている。場所は `apps/web/src/reader/ReaderPage.tsx` と `apps/mobile/src/reader/ListScreen.tsx` である。
画面にある記事のうち、最も新しい `updatedAt` に1ミリ秒を足した値である。
新しい順の一覧では、最も新しい記事は最初のページにあるので、この値が一覧を読み込んだ時刻の代わりになる。
古い順の一覧では、最も新しい記事がまだ読み込まれていないことがあり、代わりにならない。

全体設定は `settings` の表の1行で、値ごとの列として持っている。項目ごとの値を置く場所はない。
設定ファイルは、カテゴリを識別名、購読フィードをURLで指す。フィルターの範囲も同じ方法で指す。どこにもない対象を指すファイルは、全体を拒否する（`packages/core/src/settings-file.ts`）。

## Goals / Non-Goals

**Goals:**

- 項目ごとの表示の設定を1か所に置く。並び順のほかの設定（#49の表示形式を見込む）を、列を足すだけで加えられるようにする。
- 一覧の取得、続きの取得、再取得、読んだ記事を残す処理は、いまの仕組みに並びの向きを足すだけにする。
- 一括の既読の範囲が、並び順と読み込んだ件数で変わらないようにする。

**Non-Goals:**

- 表示形式（#49）の振る舞いそのもの。この変更は、保存の形をそれに備えるところまでを扱う。
- 関連度での並び（#60）。並び順の値は文字列の列挙にしておき、値を足せるようにするだけである。
- イベントの一覧、最近読んだ記事の一覧、検索の結果の並び順の選択。
- RSSの並び。RSSは生成記事だけを新しい順で出し、変えない。
- 並び順を変えるキー操作。grillingで決めていないので足さない。`?` のキー操作の一覧も変わらない。
- 通知する記事の選び方（`packages/client/src/notify.ts`）。一覧の並びとは別に、自分で問い合わせる。

## Decisions

### 項目ごとの表示の設定は、項目1つに1行の表に置く

移行で `list_views` の表を足す。番号は、実装の時点で空いている次の番号にする。同じ時期の別の変更も移行を足すからである。

```sql
CREATE TABLE list_views (
  id INTEGER PRIMARY KEY,
  list TEXT NOT NULL CHECK (list IN ('unread', 'all', 'starred', 'generated', 'uncategorized', 'category', 'category_generated', 'feed')),
  category_id INTEGER REFERENCES categories (id) ON DELETE CASCADE,
  feed_id INTEGER REFERENCES feeds (id) ON DELETE CASCADE,
  sort TEXT NOT NULL DEFAULT 'newest' CHECK (sort IN ('newest', 'oldest')),
  CHECK (
    (list IN ('category', 'category_generated') AND category_id IS NOT NULL AND feed_id IS NULL)
    OR (list = 'feed' AND feed_id IS NOT NULL AND category_id IS NULL)
    OR (list NOT IN ('category', 'category_generated', 'feed') AND category_id IS NULL AND feed_id IS NULL)
  )
);
CREATE UNIQUE INDEX list_views_target ON list_views (list, IFNULL(category_id, 0), IFNULL(feed_id, 0));
```

- 1行が1つの項目で、表示の設定の種類ごとに列を持つ。#49の表示形式は、既定値つきの列を1つ足せば同じ行に入る。
- 行がない項目は、すべての設定が既定値である。どの列も既定値に戻った行は消す。書き出しに既定値の項目を並べないためである。
- カテゴリと購読フィードを削除すると、外部キーの `ON DELETE CASCADE` が行を消す。
- カテゴリの削除では、そのカテゴリの行と、その下の「AI生成」の行が消える。カテゴリなしへ移る購読フィードの行は、購読フィードが残るので残る。
- 削除の処理には手を入れずに済み、消し忘れが起きない。
- 種別がイベントのカテゴリは、行を持てない。種別はあとから変えられないので、変更の操作で一度だけ確かめればよい。

採らなかった案は次のとおりである。

- 全体設定の表へ、JSONの列を1つ足して項目ごとの値を入れる案。カテゴリと購読フィードを削除する処理のそれぞれで、値を消す処理を書くことになる。
- カテゴリと購読フィードの表に `sort` の列を足す案。固定の項目とカテゴリの下の「AI生成」は、別の置き場所が要る。#49では、同じ列をさらに3か所へ足すことになる。
- 端末ごとに保存する案。grillingで、サーバーに保存してWebとアプリで共有すると決めた（第1ラウンドQ2）。

### 項目は、いまの `listKey` と同じ文字列で指す

APIでは、項目を文字列で指す。`unread`、`all`、`starred`、`generated`、`uncategorized`、`category-3`、`category-3-generated`、`feed-12` の形である。`packages/client` の `listKey` がすでに作っている形である。
この文字列の解釈は `packages/core/src/api.ts` に置く。表の `list`、`category_id`、`feed_id` との変換もそこで行う。
`packages/client` の `listKey` と `parseListKey` はそのまま使い、両者の文字列が一致することをテストで確かめる。
`recently-read` は解釈できるが、表示の設定を持てない項目として断る。検索の結果には鍵がない。

### APIは、表示の設定の一覧と、1項目の変更を提供する

- `GET /api/v1/list-views` は `{ "items": [{ "key": "feed-12", "sort": "oldest" }] }` を返す。行のある項目だけを返し、ない項目は既定値として扱う
- `PATCH /api/v1/list-views/:key` の本文は `{ "sort": "oldest" }` である。項目を省いた本文も受け付け、送った設定だけを変える。応答は、変えたあとのその項目の設定である
- 存在しないカテゴリと購読フィードは `not_found` で断る。イベントのカテゴリ、`recently-read`、解釈できない鍵は `invalid_input` で断る

全体設定（`/api/v1/settings`）に混ぜる案は採らない。全体設定は1つのオブジェクトを丸ごと返す形である。項目の数だけ増える値を入れると、変更のたびに全体を送り合うことになる。

### 記事の一覧は `order=oldest` で古い順にする

`GET /api/v1/articles` に `order` のパラメーター（`newest` か `oldest`）を足す。省くと `newest` で、いまと同じである。
サーバーは、一覧の要求へ項目の設定を自分で当てはめない。一覧の問い合わせは絞り込みの組み合わせで、項目と1対1ではないからである。画面が項目の設定を読み、`order` を付けて要求する。

- 古い順の並びは `ORDER BY a.updated_at ASC, a.id ASC` である。
- 古い順の続きの条件は `(a.updated_at > ? OR (a.updated_at = ? AND a.id > ?))` である。
- 続きの値には並びの向きを入れる（`[updated_at, id, "oldest"]`）。向きのない値は新しい順のものとして読むので、いま出ている値をそのまま使える。
- 向きが要求と違う続きの値は `invalid_input` で断る。向きを入れないと、新しい順の値で古い順の続きを求めたとき、黙って誤った記事を返すからである。
- `kind=event` と `recentlyRead=true` に `order` を付けた要求は、`newest` でも `invalid_input` で断る。この2つは並びが決まっている。受け付けると、並びを変えない指定を黙って捨てることになる。

### 一覧の応答に、読み出した時刻を含める

一覧の応答に `asOf` を足す。サーバーが一覧を読み出した時刻である。最近読んだ記事の一覧と検索の結果の応答も、同じ形にする。
Webとアプリの一括の既読は、最初のページの `asOf` を時刻として送る。並び順によらず、処理は1つである。

採らなかった案は次のとおりである。

- 画面の時計で、一覧を読み込んだ時刻を測る案。サーバーと時計がずれると、読み込んだあとで届いた記事まで既読にするか、読み込んだ記事を未読で残す。
- 絞り込みに当たる記事のうち、最も新しい `updated_at` を応答へ足す案。同じ役に立つが、問い合わせが1つ増える。`asOf` は時計を読むだけである。
- 古い順のときだけ、新しい順の最初の1件を別に取得する案。画面ごとに要求が増え、処理が並び順で分かれる。

再取得では最初のページも取得し直すので、`asOf` は、最後に取得し直した時刻である。新しい順の一覧でも、再取得で先頭へ増えた記事は一括の既読の対象になる。それと同じ扱いである。

### 画面は、表示の設定を1つの問い合わせで持つ

`packages/client` に、項目と表示の設定の一覧から並び順を返す関数を足す。設定のない項目、イベントのカテゴリ、最近読んだ記事では `newest` を返す。
`targetFilter` の結果には、`oldest` のときだけ `order` を足す。
Webとアプリは、`["list-views"]` の問い合わせで一覧を持つ。Webは画面の読み込みで取得する。アプリは、いまの `focusManager` の扱いのまま、前面に戻ったときも取得し直す。
60秒ごとの再取得には入れない。読んでいる一覧の並びを、ほかの端末での変更で勝手に変えないためである。

並び順を選んだときは、問い合わせの値をすぐに書き換え、保存を送る。一覧の問い合わせの鍵には `order` が入るので、並びを変えた一覧は先頭から取得される。
保存に失敗したときは、問い合わせの値を元に戻し、失敗を知らせる。
本文のペインの記事は、選び直さない。Webの記事の選択はURLの側にあり、一覧の取得とは別だからである。

### 読んだ記事を残す処理に並びの向きを渡す

`mergeKept` の並びの鍵に、向きを足す。古い順の一覧では、取得した記事と残す記事を古い順で混ぜる。最近読んだ記事の一覧は、いまのとおり既読の時刻の新しい順である。

### 新しく届いた記事は、いまの再取得のまま末尾に入る

いまの再取得は、読み込んだページを最初から取得し直す。Webは60秒ごと、アプリは前面に戻ったときと引いて更新したときである。古い順では、新しい記事は最後のページの後ろに付く。
末尾まで読み込んでいれば、再取得で末尾に現れる。途中までしか読み込んでいなければ、続きを読み込んだときに現れる。
どちらも上にある記事の位置は変わらないので、スクロールの位置と選択を保つための処理は要らない。

### メニューは、一覧の上部の操作と並べる

Webは、一覧のペインの上部にある「すべて既読にする」と切り替えの並びへ、ボタンを1つ置く。ボタンの名前には、いまの並び順を出す。押すと「新しい順」と「古い順」のメニューを開く。
見た目は `DESIGN.md` の項目のメニューにそろえる。足りない値があれば、先に `DESIGN.md` へ足す。キーボードでは、ボタンにフォーカスを移してEnterで開き、上下のキーで選ぶ。
アプリは、一覧の画面の上部の切り替えの並びへ、同じ選択肢のメニューを置く。
どちらも、イベントの一覧、最近読んだ記事、検索の結果では出さない。出すかどうかは、`hasListControls` と同じく `packages/client` の関数で項目から決める。

### 設定ファイルには、`listViews` の一覧として書く

```yaml
listViews:
  - list: unread
    sort: oldest
  - list: { category: tools }
    sort: oldest
  - list: { category: tools, generatedOnly: true }
    sort: oldest
  - list: { feed: https://example.com/feed.xml }
    sort: oldest
```

- 書き出しは、行のある項目だけを書く。既定値の設定は省く。どの項目もなければ `listViews` ごと省く。
- 読み込みは、カテゴリと購読フィードを保存したあとで、フィルターと同じく識別名とURLで結び付ける。
- 次のどれかがあれば、ファイル全体を拒否する。ファイルとサーバーのどちらにもない対象、イベントのカテゴリ、同じ項目の2回以上の記載である。
- 書いていない項目と、書いた項目の省いた設定は、保存済みの値を変えない。ほかの設定と同じく、読み込みで消すことはしない。
- 読み込みの結果には、設定した項目の数（`listViewsUpdated`）を足す。

カテゴリと購読フィードの記載の中に `sort` を書く案は採らない。固定の項目とカテゴリの下の「AI生成」には、別の書き場所が要る。#49の設定も、同じ3か所へ散ることになる。

## Risks / Trade-offs

- 古い順の一覧で一括の既読を選ぶと、まだ画面に出ていない新しい記事も既読になる → grillingの決定（第1ラウンドQ4）どおりである。いまの取り消しで戻せ、件数は知らせに出る
- 並びの時刻が過去の配信記事が読み込んだあとで届くと、`asOf` より前の時刻なので一括の既読の対象になる → いまの新しい順でも同じである。並びの時刻の決め方は、この変更の範囲に入れない
- 保存期間を過ぎた記事は消えるので、古い順の一覧の先頭が、ある日から変わる → 消えた記事が一覧にないだけで、並びの規則は変わらない
- ほかの端末で並び順を変えても、Webでは画面を読み込み直すまで反映しない → 読んでいる一覧の並びが勝手に変わらないことを優先した。アプリでは、前面に戻ったときの再取得で反映する
- 項目の鍵の文字列を、サーバーと `packages/client` の2か所が解釈する → 解釈はサーバーの側に1つ置く。`packages/client` の `listKey` が作る全種類の鍵を、サーバーの解釈に通すテストを置く

## Migration Plan

- 移行は表を足すだけで、既存の行を変えない。行がない間は、すべての項目が新しい順で、いまの振る舞いと同じである。
- 古いWebとアプリは `order` と `asOf` を使わない。新しいサーバーにつないでも、いまのとおり新しい順で動く。
- 戻すときは、サーバーを前の版に戻す。残った表は使われないだけで、害はない。
