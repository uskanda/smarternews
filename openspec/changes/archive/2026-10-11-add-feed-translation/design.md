# Design

## Context

配信記事の内容は、保存の前にHTMLからMarkdownへ変換し、`articles` の表に入れている。HTMLからMarkdownへ変換する処理は `packages/core/src/feeds/content.ts` にある。
購読フィードの取得はLLMを呼ばない。仕様 `feed-subscriptions` の「LLMを使わない取得」と `AGENTS.md` が、これを規則にしている。
LLMの呼び出しは、タスクの定義とプロバイダーのアダプターを通す。テストは外部のサービスを呼ばず、アダプターを差し替える。
この変更は、`add-feed-article-summaries` のあとに実装する。仕様 `llm-tasks` の「タスクの限定」は、要約を足したあとの文に翻訳を足す。

## Goals / Non-Goals

**Goals:**

- 取得がLLMに左右されない状態を保つ。
- Googleの翻訳のAPIで課金が起きないように、送る文字数をサーバーが自分で抑える。
- 翻訳の手段を、LLMのプロバイダーと同じく差し替えられる形にする。
- 訳と原文の段落の対応を、保存の時点で確定させる。

**Non-Goals:**

- 記事ごとの言語の判定。
- 生成記事の翻訳。
- 訳を一覧の検索やストップワードの対象にすること。

## Decisions

### 翻訳の手段は、アダプターの後ろに置く

`packages/core` に翻訳のアダプターの型を足す。文章の並びと訳す先の言語を受け取り、同じ数の訳を返す。
実装は2つ用意する。Googleの翻訳のAPIを呼ぶものと、LLMの翻訳のタスクを呼ぶものである。
どちらを使うかは、1つの関数が決める。APIキーがあり、月の文字数に余裕があればGoogleを、そうでなければLLMを選ぶ。
取得の中から呼ぶときは、LLMを選ばせない引数を渡す。これで「LLMを使わない取得」を保つ。
テストは、記録済みの応答を返すアダプターに差し替える。

### Googleの翻訳のAPIは、HTMLの形式で送る

Cloud Translationの基本の版（v2）を、APIキーで呼ぶ。宛先は `https://translation.googleapis.com/language/translate/v2` である。
段落のMarkdownをそのまま送ると、強調の記号やリンクの括弧を訳文の中で崩すことがある。
送る前にまとまりをHTMLへ変換し、`format` に `html` を指定して送る。返った訳のHTMLは、いまある変換の処理でMarkdownへ戻す。
この変換は、許可したタグだけを残すので、訳に紛れたタグも落ちる。
1回の要求は、128個までのまとまりと、合計5,000文字までに分ける。
このAPIの呼び出しは、クローラーの取得の制限（内部のアドレスの拒否）を通す。宛先は固定なので、利用者が与えたURLへは送らない。

### 設定は `config.yaml` に置く

```yaml
translation:
  google:
    apiKeyEnv: GOOGLE_TRANSLATE_API_KEY   # 環境変数の名前。キーそのものは書かない
  monthlyChars: 450000                    # この文字数を超えてGoogleへ送らない
  maxCharsPerArticle: 20000               # 1件の本文で翻訳する長さ
```

`google` を書かないとき、またはその環境変数が空のときは、APIキーなしとして扱う。
訳す先の言語は、全体設定の出力言語を使う。新しい設定は足さない。

### 文字数は、月ごとの1行で数える

移行で `translation_usage`（月、文字数）の表を足す。月は、設定したタイムゾーンでの `YYYY-MM` とする。
送る前に、その月の文字数と要求の文字数の和を上限と比べる。超えるなら送らず、呼び出し元にLLMを選ばせる。
送る分は、応答を待たず、先に数へ足す。失敗した要求も課金されうるので、足したままにする。
Googleの側の残りの枠は、APIで読めない。サーバーが送った分を数えるのが、課金を避ける唯一の確かな方法である。

### LLMの翻訳は、番号付きの並びを1回で訳す

`packages/core/src/llm/tasks.ts` に `translate` を足す。入力は `{ "items": [{ "n": 1, "text": "..." }] }`、出力も同じ形とする。
出力の数と番号が入力と合わないときは、検証で捨てる。段落の対応を取り違えた訳を保存しないためである。
1回の呼び出しには、合計8,000文字までのまとまりを入れる。超える本文は、複数回に分ける。
割り当てがないときは `fast` を使う。呼び出しは、いまの1日の上限に数える。

### 訳は、まとまりの並びとして保存する

移行で次を足す。

- `feeds`: `translate`（0か1）
- `articles`: `translated_title`（一覧で使う）、`source_language`（Googleが返した原文の言語。LLMのときは空）
- `article_translations`（記事のid、まとまりの並びのJSON、手段、翻訳していない残りの有無、作った時刻）

まとまりの並びは `[{ "original": "...", "translated": "..." | null }]` とする。どちらもMarkdownである。
本文のMarkdownは、空行で区切ったまとまりに分ける。コードのまとまりと、画像だけのまとまりは、訳を `null` にする。
画面は、この並びをそのまま上から描く。画面の側で段落を対応させる処理は持たない。
訳だけを1つのMarkdownとして保存する方式は、画面で原文と突き合わせる必要があり、数がずれると対応が崩れる。

### 本文の翻訳は、開いたときに画面が頼む

`POST /api/v1/articles/:id/translation` を足す。保存した訳があればそれを返し、なければ翻訳して保存してから返す。
同じ記事への要求が重なったときは、1つの翻訳を待たせて、結果を分け合う。
記事の詳細の取得に翻訳を含める方式は、取得が翻訳の時間だけ遅くなり、原文を先に表示できない。
翻訳の利用の状況は `GET /api/v1/translation` で返す。

### 表示は、訳の下に原文を小さく置く

Webとアプリの本文の画面で、まとまりごとに、訳を本文の書体で、原文をその下に小さな書体と弱い色で置く。
原文には、`source_language` を言語の属性として付ける。読み上げが、訳と原文を正しい言語で読むためである。
`source_language` が空のとき（LLMで訳したとき）は、属性を付けない。言語を推測して付けることはしない。
訳と原文が同じ文字列のまとまりは、1度だけ描く。出力言語と同じ言語の記事で、同じ文が2度並ぶのを避ける。

## Risks / Trade-offs

- 記事の内容がGoogleまたはLLMのプロバイダーへ送られる → 利用者が選んだ購読フィードだけを対象にする。切り替えのそばと `README.md` に書く。
- 文字数の数え方がGoogleの数え方とずれる → 既定の上限を、無料の50万文字より1割低い45万文字にする。HTMLのタグも数に入れて、多めに数える。
- LLMが段落の数を変える → 検証で捨て、翻訳できなかったことを返す。画面は原文を表示し、やり直せる。
- 長い記事で1日のLLMの上限を使う → 1件の本文で翻訳する長さを2万文字に抑える。
- タイトルの訳のない記事と訳のある記事が、一覧に混ざる → APIキーがないとき、枠が尽きたときに起きる。開けば訳される。設定の画面に状況を出す。

## Migration Plan

- 移行は列と表を足すだけである。既存の購読フィードは翻訳が無効で、動きは変わらない。
- APIキーは、サーバーを動かす環境の変数に置く。`examples/smarternews.service` に、変数を読む例を書き足す。
- 戻すときは、前の版に戻す。足した列と表は、前の版のコードが読まないので残してよい。

## Open Questions

- Googleの翻訳のAPIの1回の要求の上限は、実装のときに公式の文書で確かめる。設計の値（128個、5,000文字）より小さければ、小さいほうに合わせる。
