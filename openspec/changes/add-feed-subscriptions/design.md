# Design

## Context

動機と範囲は `proposal.md` の「Why」と「What Changes」に、決定の経緯は `grilling.md` に書いた。ここでは作り方だけを決める。

いまの作りのうち、この変更の形を決めるものは次のとおりである。

- 記事は1つの表に入り、整数の識別子を持つ。Webとアプリは、一覧、本文、既読、スター、隣の記事への移動を、この識別子だけで行う。
- 記事の表は、カテゴリと重要度を必須の列として持つ。カテゴリを削除すると、記事も一緒に消える。
- 一覧は、最終更新の時刻と識別子の組で並べ、続きの取得にもその組を使う。
- 実行は1本の待ち行列で直列に進む。LLMの呼び出しの上限と結び付いている。
- フィードの解析は、タイトル、URL、抜粋、公開日時だけを読む。内容、著者、識別子は読んでいない。
- 本文はMarkdownで保存し、WebとアプリがそれぞれMarkdownを描く。どちらも、画像の記法を文字として出している。
- 移行は、番号つきのSQLを1つずつ流す。1つのSQLは1回の書き込みで、外部キーの検査は有効なままである。

## Goals / Non-Goals

**Goals:**

- 生成記事と配信記事を、1つの一覧、1つの識別子の空間、同じ操作で扱う。
- 購読フィードの取得を、LLMの呼び出しの上限と実行の待ち行列から切り離す。
- 既存のデータを失わずに、表の形を変える。
- 配信元の内容を、スクリプトや埋め込みを通さずに表示する。

**Non-Goals:**

- 画像をサーバーが代わりに取得する仕組み。
- 元のページを取得して全文を表示すること。
- 記事の検索。
- 配信記事を候補としてAIの収集に使うこと。

## Decisions

### 1. 配信記事は記事の表に入れる

記事の表に、由来の列 `origin` と、購読フィードを指す列 `feed_id` を足す。由来の値は、生成記事と配信記事の2つである。
配信記事も、生成記事と同じ表の1行になる。

別の表に分ける案も考えた。その場合、混ぜた一覧は2つの表を合わせて並べることになり、識別子も2系統になる。
Webとアプリでは、識別子で記事を開く経路、既読とスターの変更、隣の記事への移動を、すべて2系統へ書き直すことになる。
1つの表にすれば、これらはほぼそのまま動く。

代わりに、生成記事だけを対象にする問い合わせには、由来の条件を必ず足す。対象は次のとおりである。

- 続報の判定のために最近の生成記事を読む処理
- イベントの重複の判定
- RSSの出力
- 180日の保存期間による削除

漏れを防ぐために、生成記事だけを読む問い合わせは1か所の条件の定数を使い、配信記事が混ざらないことをテストで確かめる。

### 2. 表を作り直す移行と、その安全策

配信記事はカテゴリなしになり得て、重要度を持たない。どちらの列もいまは必須なので、記事の表を作り直す。
SQLiteは、列の必須の指定をあとから外せないためである。

外部キーの検査が有効なまま表を削除すると、出典やトピックとの対応の行が連動して消える。
そこで、移行の仕組みを次のように広げる。

- 移行のSQLの1行目に決まった注釈があるとき、その移行は外部キーの検査を止めて流す。
- 流したあと、外部キーの整合を検査し、違反があれば全体を取り消す。
- 検査を止める移行の前に、データベースのファイルを、移行の番号を付けた名前で同じ場所に複製する。

移行 `002_feeds.sql` は、新しい形の表を作り、既存の行を由来が生成記事のものとして写し、古い表を消して名前を付け替える。
テストでは、記事、出典、トピックとの対応、候補からの参照を入れた古い形のデータベースを移行し、すべて残ることを確かめる。

### 3. 配信記事にもカテゴリを写して持つ

配信記事のカテゴリは購読フィードのカテゴリで決まるが、記事の行にも同じ値を持たせる。
カテゴリでの絞り込みと件数の集計を、いまの問い合わせと索引のまま使えるようにするためである。

値がずれないように、次の2つの操作は1回の書き込みの中で両方を書き換える。

- 購読フィードのカテゴリを変えるとき、その配信記事のカテゴリも変える。
- カテゴリを削除するとき、先に、その購読フィードと配信記事をカテゴリなしに変える。そのあとでカテゴリを消す。

### 4. 内容はMarkdownに変換して保存する

項目の内容のHTMLは、取得のときにサーバーでMarkdownへ変換し、本文の列に保存する。
変換は、導入済みのHTMLの解析のライブラリーで木を作り、許した要素だけをMarkdownに書き出す小さな処理として書く。
許す要素は、段落、見出し、リスト、引用、強調、整形済みの文章、リンク、画像である。それ以外は、中の文章だけを残す。

消毒したHTMLをそのまま渡す案は採らない。アプリはHTMLを描く部品を持たず、Webも本文のHTMLを解釈しない方針で作っている。
Markdownにすれば、両方の既存の描画をそのまま使え、「HTMLを解釈しない」という今の要件も変えずに済む。

画像は、Markdownの画像の記法として残す。保存する時点で、HTTPSでないURLの画像は取り除く。
表は、1行を1段落の文章にして残す。表の形は失われるが、フィードの内容に表が出ることは少ない。

内容の長さは10万文字で切り、切ったことが分かる1文を末尾に足す。

### 5. 画像は配信記事の本文でだけ描く

WebとアプリのMarkdownの描画に、画像を描くかどうかの指定を足す。配信記事の本文でだけ有効にする。
生成記事の本文はモデルが書いたものなので、画像の記法があっても今までどおり文字として出す。

- Webは、画像に遷移元のURLを送らない指定と、遅れて読み込む指定を付ける。応答のContent-Security-Policyでは、`img-src` にHTTPSを足す。
- アプリは、HTTPSのURLの画像だけを描く。読み込んだあとで縦横の比を得て、高さを幅から決める。
- どちらも、読み込めなかった画像の位置には、説明の文を出す。

`DESIGN.md` に、本文の中の画像の決まり（幅の上限、角の丸み、上下の間隔、説明の文の書体）を先に足す。

### 6. 購読フィードの取得は、実行の待ち行列と分ける

購読フィードの取得は、実行の待ち行列とは別の1本の列で進める。スケジュールの確認と同じ周期の合図で動かす。

- 次に取得する時刻は保存せず、最後の取得の時刻と取得周期から、合図のたびに計算する。基本の取得周期を変えると、その場で全体に反映される。
- 待つ時間は「取得周期×2の失敗回数乗」で、24時間を上限にする。失敗の回数は購読フィードに保存し、成功で0に戻す。
- 合図のたびに、待つ時間を過ぎた有効な購読フィードを古い順に取り、1つずつ取得する。
- 即時の取得と、新しい購読の登録のための取得も、同じ列に並べる。定期の取得と重ならないようにするためである。

実行の待ち行列に入れる案は採らない。LLMを待つ実行の後ろに並ぶと、30分の周期を守れない。
同じホストへの間隔は、取得の部品が実行と共通で数えるので、2本の列が同時に動いても守られる。

取得の部品には、応答のヘッダーを返すことと、304の応答を失敗にしないことを足す。
条件付きの要求には、前回の応答の `ETag` と `Last-Modified` を使う。

### 7. 項目の識別子を別の表に覚える

配信記事を保存期間で消したあとも、フィードが同じ項目を配信し続けることがある。
そこで、購読フィードごとに、見た項目の識別子と最後に見た時刻を、表 `feed_items_seen` に覚える。
取得のたびに、文書にある項目の時刻を更新する。90日見ていない識別子は消す。

識別子は、RSSの `guid`、Atomの `id` の順に使い、どちらもなければ正規化した元のページのURLを使う。

### 8. 並びの時刻は、最終更新の列を使う

配信記事の並びの時刻（公開日時。なければ取得の時刻）を、記事の最終更新の列に入れる。
一覧の並びと続きの取得の仕組みを、変えずに使うためである。内容が書き換えられても、この列は変えない。

配信記事の90日の保存期間も、この列で数える。

### 9. ストップワードの判定は、記事の行に結果を持つ

配信記事の行に、当たったストップワードを指す列 `stop_word_id` を持つ。
一覧、件数、一括の既読は、「この列に値があり、スターがない」行を除く。
スターの有無を条件に入れるので、スターを付け外ししても列を書き換えなくてよい。

照合のために、内容から書式とURLを除いた文章を、列 `content_text` に保存する。
タイトルと文章は、照合の直前に、互換の正規化と小文字化をして比べる。

列を計算し直すのは、次のときである。

- 配信記事を保存するとき、内容が書き換えられたとき（その1件だけ）
- ストップワードを足したとき（まだ隠れていない配信記事だけ）
- ストップワードを変えたとき、消したとき（そのストップワードが指されている配信記事だけ）

計算は1回の書き込みの中で行う。90日分の配信記事が10万件あっても、文字列の比較だけなので数秒で終わる見込みである。

語ごとの隠している件数は、この列で数える。複数の語に当たる配信記事は、登録の古い語の件数に入る。

### 10. APIの形

記事の応答に、由来、購読フィードの識別子、著者を足す。配信記事では、カテゴリと重要度が値なしになり得る。
記事の一覧の絞り込みに、由来、購読フィード、カテゴリなしを足す。一括の既読にも同じ3つを足す。
件数の応答に、生成記事の未読数（全体とカテゴリごと）、購読フィードごとの未読数、カテゴリなしの未読数を足す。

新しい操作は次のとおりである。

| 操作 | 場所 |
|---|---|
| 購読フィードの一覧、登録、変更、削除、即時の取得 | `/api/v1/feeds` とその配下 |
| フィードを探す | `/api/v1/feeds/discover` |
| OPMLの書き出しと読み込み | `/api/v1/feeds/opml` |
| ストップワードの一覧、登録、変更、削除 | `/api/v1/stop-words` とその配下 |

登録は、その場で取得して確かめるので、数秒かかることがある。OPMLと設定ファイルの読み込みは、取得を待たずに登録だけを行う。
OPMLの解析には、フィードの解析と同じXMLのライブラリーを使う。
コマンドには `opml-import` と `opml-export` を足す。

設定ファイルには、全体設定に `feedIntervalMinutes`、カテゴリの下とファイルの最上位に `subscriptions`、最上位に `stopWords` を足す。
トピックの取得元にある `feeds` と名前が重ならないようにした。どれも省略できるので、設定ファイルの版は1のままにする。

### 11. 画面の構成

左のペインと引き出しは、同じ規則で項目を作る。規則は `packages/client` に置き、Webとアプリで共有する。
入力はカテゴリ、購読フィード、件数で、出力は「上段の4項目、カテゴリとその下の項目、未分類とその下の項目」の並びである。

選んでいる項目は、いまと同じく、WebではURLに、アプリでは画面の経路の鍵に持つ。鍵は次の形にする。

| 項目 | 鍵 |
|---|---|
| 上段の「AI生成」 | `generated` |
| カテゴリの下の「AI生成」 | `category-<id>-generated` |
| 購読フィード | `feed-<id>` |
| 「未分類」 | `uncategorized` |

カテゴリの下の項目は、字下げの間隔を1段だけ付ける。その値は `DESIGN.md` に足す。
Webの設定には、「購読フィード」と「ストップワード」の2つの画面を足す。アプリの設定は変えない。

アプリの定期的な確認は、由来に生成記事を指定して一覧を取る。

### 12. トピックのないカテゴリ

スケジュールの確認で、有効なトピックを持たないカテゴリを飛ばす。手動の実行は今までどおり受け付ける。
OPMLの読み込みで作るカテゴリは、既定のスケジュールを持つが、トピックがないので実行されない。

### 13. 上限

購読フィードは500件まで、1回の取得で保存する項目は新しい順に200件までとする。
どちらも、誤ったOPMLや項目を際限なく返すフィードでデータベースが膨らむのを防ぐための値で、設定にはしない。

### 14. 実装の中で決めた点

- 一覧と件数のために、索引を4つ足した。未読の一覧、カテゴリごとの未読の一覧、由来ごとの一覧、件数の集計のためのものである。件数は、集計用の索引だけを1回たどって求める。
- 件数の応答に、カテゴリごとの生成記事の総数を足した。カテゴリの削除の確認で、消える記事の件数を正しく示すためである。
- 書き込みのまとまりは、入れ子で呼べる形へ改めた。設定ファイルの読み込みが、購読フィードとストップワードの登録を1回の書き込みにまとめるためである。
- アプリの一覧の鍵は、カテゴリを識別名ではなく識別子で書く。決定11の表の形である。
- ストップワードは、照合に使う形（正規化した文字列）も保存する。同じ語の二重登録を、書き方の違いにかかわらず防ぐためである。

## Risks / Trade-offs

| リスク | 対策 |
|---|---|
| 表の作り直しで既存の記事を失う | 移行の前にファイルを複製する。古い形のデータを移すテストを先に書く。本番に入れる前に、本番のデータベースの複製で移行を試す |
| 古い版のアプリが新しいサーバーの一覧を受け取る | 古い版は配信記事を重要度なしの行として表示し、通知の設定がすべての新着のときは配信記事も通知する。サーバーとアプリを同じ日に更新する。利用者は1人なので、互換のための経路は足さない |
| 生成記事だけを読むべき処理に配信記事が混ざる | 決定1の定数とテストで防ぐ |
| 配信記事の件数で、一覧と件数の問い合わせが遅くなる | 購読フィードと並びの時刻の索引、由来とカテゴリの索引を足す。10万件の配信記事を入れた状態で、応答の時間を測る |
| 画像の読み込みで、配信元に端末のアドレスと読んだ時刻が伝わる | 利用者が選んだ方式である。READMEに書く。遷移元のURLは送らない |
| 配信元の変わったHTMLで、内容の変換が崩れる | 許した要素以外は文章だけを残すので、崩れても文章は読める。実在の形に近い記録済みのフィードをテストに使う |
| 取得が増えて、相手のサイトに負荷をかける | 最短5分、条件付きの要求、ホストごとの間隔、失敗時の間隔の延長で抑える |
| ストップワードの追加で10万件を読み直す間、書き込みが止まる | 1回の書き込みで数秒の見込みである。測って長ければ、分けて処理する |

## Migration Plan

1. サーバーを更新すると、起動のときに移行が流れる。その前に、データベースのファイルが同じ場所に複製される。
2. 既存の記事は、すべて生成記事として残る。購読フィードは0件から始まるので、画面の見え方は変わらない。
3. アプリは、新しい版のAPKを入れる。古い版でも生成記事は読める。
4. 戻すときは、サーバーを前の版に戻し、複製したファイルを元の名前に戻す。更新のあとに足した購読フィードと配信記事は失われる。
