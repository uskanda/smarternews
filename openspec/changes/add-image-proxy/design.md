# Design

## Context

配信記事の内容は、`packages/core/src/feeds/content.ts` がHTMLからMarkdownへ変換して保存する。画像は `![説明](URL)` の形で書き出し、`https:` 以外の画像はこのときに捨てている。
APIの記事の詳細は、`packages/core/src/db/articles.ts` の `toArticle` が、保存した本文から `bodyHtml` を作って返す。画像を出すのは配信記事だけで、`packages/core/src/markdown.ts` は `https:` の画像だけを `img` の要素にする。
アプリは `apps/mobile/src/reader/Markdown.tsx` で本文を描き、`https:` の画像だけを、取得先のサイトから直接読み込む。
画面のContent-Security-Policyは `apps/server/src/web.ts` にあり、`img-src 'self' data: https:` である。
外部への要求は、すべて `packages/core/src/fetch/http.ts` の `Fetcher` が送る。方式とアドレスの制限、リダイレクト先の検査、時間と大きさの上限、User-Agentを、ここで適用している。ただし応答は文字列にして返す。
APIのトークンは `apps/server/src/tokens.ts` が初回の起動で作り、設定のディレクトリに置く。

## Goals / Non-Goals

**Goals:**

- 画面とアプリが読み込む画像の宛先を、接続しているサーバーだけにする。
- 中継を、誰でも使える公開のプロキシにしない。
- 画像の中継で、データベースの表と移行を増やさない。並行して進む変更と、移行の番号がぶつからないようにするためである。

**Non-Goals:**

- 画像の縮小や形式の変換。届いた画像をそのまま返す。
- 生成記事の本文の画像の表示。今と同じく、どこからも読み込まない。
- 全文の取得（#52）、表示形式のサムネイル（#49）、ニュースレター（#62）の画像の扱い。それぞれの変更が、ここで足す書き換えを通す。
- 取得に失敗した画像を覚えておくこと。失敗した画像は、次に表示したときにもう一度取得する。

## Decisions

### 中継のURLは、元のURLと署名をパスに持つ

中継のURLは `/api/v1/image-proxy/<署名>/<元のURL>` とする。元のURLはbase64urlで符号にする。署名は、署名の鍵で元のURLの文字列から求めたHMAC-SHA256を、base64urlにしたものである。
検査は、求め直した署名と、時間の差の出ない比較で突き合わせる。期限の情報は入れない（grilling round 2 Q3）。
APIの応答には、オリジンを含まないパスで返す。Webは同じオリジンなのでそのまま使える。アプリは、接続しているサーバーのURLを前に付けて読み込む。サーバーは、外から見た自分のオリジンを知らないためである。

採らなかった案は次のとおりである。

- 元のURLを `?url=` のパラメーターで渡す案。パスの方が、途中の中継やキャッシュでの扱いが揃う。
- 署名に期限を入れる案。grillingで退けた。

### 署名の鍵は、データのディレクトリの1つのファイルに置く

鍵は32バイトの乱数で、`<データのディレクトリ>/image-proxy.key` に、所有者だけが読み書きできる権限で置く。作り方は `ensureToken` と同じにする。
APIのトークンは設定のディレクトリにあるが、鍵はgrillingの決定（round 2 Q2）に従ってデータのディレクトリに置く。`paths.ts` に場所を足す。
鍵を作り直すには、ファイルを消して起動し直す。保存した内容は元のURLのままなので、APIの応答は新しい鍵の中継のURLになり、画面は次の再取得から画像を出せる。

### 画像のURLは、APIの応答を作るときに書き換える

書き換えは `apps/server` のAPIの層で行う。`getArticle` は、ほかの処理（要約、翻訳）も使うので、元のURLのまま返させる。
配信記事について、次の3か所の画像のURLを書き換える。

- `body`
- `bodyHtml`（書き換えたあとの `body` から作り直す）
- `translation` の各まとまりの原文と訳

書き換えの対象は、Markdownの中の `![説明](URL)` と `![説明](<URL>)` の形だけである。内容の変換が書き出すのはこの形だけである。
訳にモデルが別の形を書いた場合、その画像は元のURLのまま残る。画面とアプリは中継のURLの画像しか読み込まないので、その画像は説明の文字になるだけで、取得先への要求は起きない。書き換えの漏れは、表示されない方へ倒れる。
生成記事の本文は書き換えない（http-apiの「生成記事の本文の画像の扱い」）。

保存のときに書き換える案は採らない。鍵を作り直すと保存済みの内容がすべて無効になるので、grillingで退けた（round 2 Q4）。

### 画面とアプリは、中継のURLの画像だけを読み込む

`markdown.ts` の画像の判定を、`https:` から中継のURLのパスに変える。翻訳のアダプター（`translation/google.ts`）は元のURLを含むMarkdownを扱うので、中継のURLに限らない別の指定にする。`http:` の画像も消さずに送り返す。
アプリの `Markdown.tsx` も、中継のURLのパスで始まる画像だけを、サーバーのURLを前に付けて読み込む。それ以外の画像は説明の文字を出す。
WebのContent-Security-Policyは `img-src 'self'` にする。`data:` も外す。今の画面は `data:` の画像を使っていない。

### 画像の取得は `Fetcher` に足す経路を通す

`Fetcher` に、応答をバイト列のまま返す取得を足す。方式とアドレスの制限、リダイレクト先の検査と段数、許可するホスト、時間の上限、User-Agentは、今の `get` と同じ処理を通す。
大きさの上限は呼び出す側が渡す値とし、画像では10MB（10,000,000バイト）を渡す。`config.yaml` の `fetch.maxBytes` は使わない。grillingで1枚の上限を10MBと決めたためである（round 2 Q6）。
要求のヘッダーは、User-Agentと、受け付ける形式（`Accept`）だけにする。`Accept` にはSVGを含めない。端末から受け取ったヘッダーは渡さない。
robots.txtは確かめない（round 2 Q7）。robots.txtの確認は `Fetcher` の外にあるので、中継の経路から呼ばなければよい。

### 画像の形式は中身の先頭で判定する

応答のContent-Typeは信じない。中身の先頭のバイト列で、JPEG、PNG、GIF、WebP、AVIFのどれかを判定し、どれでもなければ拒否する。
SVGは、先頭の判定に入れないので、この判定で拒否される。Content-Typeが `image/svg+xml` の応答は、中身を読む前に拒否する。
返す応答のContent-Typeは、判定した形式にする。
あわせて `X-Content-Type-Options: nosniff` と `Content-Security-Policy: default-src 'none'; sandbox` を付ける。
`Cache-Control` は `private` にし、`max-age` を置く期間にする。署名付きのURLは同じ元のURLを指し続けるので、端末で置いておいても問題ない。

### 失敗の応答

| 状況 | HTTPステータス |
|---|---|
| 署名が合わない、形が崩れている | 403 |
| 取得先の制限で拒否、時間切れ、10MB超、2xxでない応答、画像でない、SVG | 502 |

どの失敗でも本文は短い英語の文字列にし、画像の中身は返さない。画面とアプリは、読み込みの失敗として説明の文字を出す。

### 置いた画像はファイルだけで管理する

置いた画像は `<データのディレクトリ>/image-cache/` に、元のURLのSHA-256の16進の名前で置く。置いた時刻はファイルの更新時刻で表す。形式は返すたびに先頭から判定し直す。
書き込みは一時のファイルに書いてから名前を変え、途中で止まっても、書きかけのファイルが残らないようにする。
同じ元のURLの取得が同時に来たときは、1回の取得を共有する。
期間を過ぎたファイルは、読むときに無いものとして扱い、取得し直して上書きする。
合計の大きさは、起動のときにディレクトリを走査して求め、以後は書き込みと削除のたびに足し引きする。書き込みで上限を超えたら、更新時刻の古い順に消す。
掃除は、起動のときと、スケジュールの確認のうち `purgeExpired` と同じ間隔で行い、期間を過ぎたファイルを消す。
1枚の画像が上限より大きいときは、返すが置かない。

データベースの表にしないのは、移行が増え、並行する変更と番号がぶつかるからである。置いた画像は消えても困らないので、ファイルの更新時刻で十分である。

### 設定

`config.yaml` に次を足す。

```yaml
images:
  cacheDays: 7              # 置く期間（日）
  cacheMaxBytes: 1000000000 # 置く量の上限（バイト）
```

`cacheDays` は1以上、`cacheMaxBytes` は1以上の整数とする。中継を無効にする設定は置かない（round 1 Q7）。

### トークンの扱い

APIのトークンの検査で、`/api/v1/image-proxy/` で始まるパスを、稼働の確認と同じく除外する。代わりに署名を検査する。

## Risks / Trade-offs

- 署名に期限がないので、漏れた中継のURLは鍵を作り直すまで使える → 中継できるのは、そのURLが指す1枚の画像だけである。ほかのURLの中継には使えない。鍵のファイルを消して起動し直せば、すべて無効にできる。
- 表示のたびに、取得先にはサーバーのアドレスから要求が届く → 利用者の端末のアドレスと遷移元は伝わらない。開封の事実と時刻は、置いていない画像についてだけ伝わる。
- 1枚目の表示が、サーバーを経由する分だけ遅くなる → 2回目からはディスクから返す。端末も `Cache-Control` で置いておける。
- JPEG、PNG、GIF、WebP、AVIF以外の形式（BMP、ICO、HEICなど）は表示されなくなる → 説明の文字を出す。配信記事の画像の大半は5つの形式に収まる。
- 取得に失敗する画像を表示するたびに、取得先へ要求が飛ぶ → 同時の取得は共有する。失敗を覚える仕組みは、必要になってから足す。
- `http:` の画像を、サーバーが取得先から暗号化せずに取得する → 経路の途中で中身を書き換えられた場合も、画像の形式の判定と `nosniff` があるので、端末が画像以外として扱うことはない。

## Migration Plan

- データベースの移行はない。
- 保存済みの配信記事には `http:` の画像が残っていない。表示されるのは、この変更のあとに取得した項目と、書き換えられた項目だけである。保存済みの内容を取得し直す処理は足さない。
- 鍵は初回の起動で作られる。置いた画像のディレクトリは、初めて中継したときに作る。
- 戻すときは、前の版で起動すればよい。鍵のファイルと置いた画像のディレクトリは、前の版の動作に影響しないので、消すか残すかは問わない。前の版は保存済みの `http:` の画像を表示しない。

## Open Questions

- **ホストごとの間隔を、画像の取得に適用するか。** grillingで適用を決めた「今の取得の制限」は、round 1 Q3の問いではプライベートのアドレスの拒否と、大きさと時間の上限を挙げていた。`fetch.hostIntervalMs`（既定1秒）を画像にも適用すると、同じホストの画像が10枚ある記事は、全部が出るまで約10秒かかる。クロールの `Fetcher` と同じインスタンスを使えば、実行中のクロールとも待ち時間を共有する。適用しないなら、中継の取得には間隔を0にした別の `Fetcher` を作る。どちらでも仕様の文と作業の分け方は変わらない。実装の前に利用者へ確かめる。
