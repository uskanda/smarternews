# Tasks

どの作業も、失敗するテストを先に書いてから実装する。テストは外部のサイトを呼ばない。取得は差し替えた `fetchImpl` と記録済みの応答で動かす。
確認のために起動したサーバーは、作業用のデータのディレクトリと空いているポートを使い、PIDかポートで特定して止める。`AGENTS.md` の規則に従う。
実装の前に、design.mdのOpen Questions（ホストごとの間隔）を利用者に確かめる。

## 1. 取得と設定

- [ ] 1.1 `packages/core/src/fetch/http.ts` の `Fetcher` に、応答をバイト列のまま返す取得を足す。大きさの上限を呼び出す側が渡せること、方式とアドレスの制限、リダイレクト先の検査と段数、許可するホスト、時間の上限、User-Agentが `get` と同じく働くことをテストで確かめる
- [ ] 1.2 `packages/core/src/config.ts` に `images.cacheDays` と `images.cacheMaxBytes` を足す。既定が7日と1,000,000,000バイトであること、1未満の値を拒否することをテストで確かめる
- [ ] 1.3 `packages/core/src/paths.ts` に、署名の鍵のファイルと、置いた画像のディレクトリの場所を足す。どちらもデータのディレクトリの下になることをテストで確かめる
- [ ] 1.4 `docs/` の設定の説明と `examples/config.example.yaml` に `images` の設定を足す。例のファイルが `parseConfig` を通ることをテストで確かめる

## 2. 署名

- [ ] 2.1 `packages/core` に署名の処理を足す。中継のURLを作る処理と、署名を検査して元のURLを取り出す処理である。元のURLの書き換え、空の署名、別の鍵の署名、崩れた符号を拒否することをテストで確かめる
- [ ] 2.2 `apps/server` で、起動のときに署名の鍵を読み、なければ32バイトの乱数で作って所有者だけが読み書きできる権限で保存する。権限、2回目の起動で同じ鍵を使うこと、ログに鍵の値が出ないことをテストで確かめる
- [ ] 2.3 APIの応答と設定ファイルの書き出しに、鍵の値が現れないことをテストで確かめる

## 3. 中継とディスクに置く画像

- [ ] 3.1 `packages/core` に、中身の先頭で画像の形式を判定する処理を足す。JPEG、PNG、GIF、WebP、AVIFを受け付け、HTML、SVG、空の中身を拒否することをテストで確かめる
- [ ] 3.2 `packages/core` に、置いた画像の読み書きを足す。元のURLのSHA-256の名前、一時のファイルからの名前の変更、期間を過ぎたファイルを無いものとして扱うことをテストで確かめる。上限を超えたら更新時刻の古い順に消すこと、上限より大きい1枚を置かないこと、起動のときの合計の算出も確かめる
- [ ] 3.3 `packages/core` に中継の処理を足す。置いた画像があればそれを返し、なければ1.1の取得で10MBを上限に取得して形式を判定し、置いてから返す。同じ元のURLの同時の取得を1回に共有すること、2xxでない応答、10MB超、画像でない中身、SVGのContent-Type、robots.txtを要求しないことをテストで確かめる
- [ ] 3.4 Open Questionsの答えに従い、中継の取得に使う `Fetcher` を決めて組み立てる。ホストごとの間隔の扱いが答えのとおりであることをテストで確かめる
- [ ] 3.5 `packages/core/src/runs/scheduler.ts` の掃除の間隔と起動のときに、期間を過ぎた画像を消す処理を足す。テストで確かめる

## 4. APIとContent-Security-Policy

- [ ] 4.1 `apps/server` に `/api/v1/image-proxy/<署名>/<元のURL>` の入口を足し、トークンの検査から外す。署名の合う要求で画像を返すこと、合わない要求で403を返して取得しないこと、取得の失敗で502を返すことをテストで確かめる。応答のContent-Type、`X-Content-Type-Options`、`Content-Security-Policy`、`Cache-Control` も確かめる。ほかのパスがいままでどおり401を返すことも確かめる
- [ ] 4.2 `fetchImpl` に届いた要求を調べ、中継の取得に、端末から受け取った `Cookie`、`Referer`、アドレスを渡すヘッダーが含まれないことをテストで確かめる
- [ ] 4.3 `apps/server` の記事の詳細の応答で、配信記事の `body`、`bodyHtml`、`translation` の画像のURLを中継のURLに書き換える。`http:` と `https:` の画像、`<URL>` の形の画像、訳の中の画像、生成記事の本文を書き換えないこと、保存した内容が元のURLのままであることをテストで確かめる
- [ ] 4.4 `packages/core/src/markdown.ts` で、画像を出すときは中継のURLのパスのものだけを `img` の要素にする。翻訳のアダプター（`packages/core/src/translation/google.ts`）は元のURLの `http:` と `https:` の画像を、消さずに送り返す。両方をテストで確かめる
- [ ] 4.5 `apps/server/src/web.ts` のContent-Security-Policyの `img-src` を `'self'` にする。応答のヘッダーをテストで確かめる
- [ ] 4.6 `docs/api.md` に、中継の入口、署名、トークンが要らないこと、失敗のHTTPステータスを書く

## 5. 内容の変換

- [ ] 5.1 `packages/core/src/feeds/content.ts` で、`http:` の画像を取り除かずに残す。`http:` と `https:` の画像が元のURLのまま保存されること、1ピクセルの画像を今までどおり捨てることをテストで確かめる

## 6. 画面とアプリ

- [ ] 6.1 `apps/web` の本文と訳の表示で、中継のURLの画像が表示されること、読み込みに失敗した画像の位置に説明の文が出ることをテストで確かめる。テストは実物のAPIに対して動かす
- [ ] 6.2 `apps/mobile/src/reader/Markdown.tsx` で、中継のURLのパスで始まる画像だけを、接続しているサーバーのURLを前に付けて読み込む。それ以外の画像は読み込まずに説明の文を出すことをテストで確かめる
- [ ] 6.3 `packages/client` に、中継のURLのパスをサーバーのURLで解決する処理を置く。DOMとNodeの機能に依存せず、Webとアプリの両方から使えることをテストで確かめる

## 7. 結合の確認

- [ ] 7.1 Webの画面で結合を確かめる。作業用のデータのディレクトリと空いているポートでサーバーを起動し、`http:` の画像を含む配信記事をWebで開く。画像が中継のURLから読み込まれ、ブラウザーから他のサイトへの画像の要求がないことを確かめる。サーバーはPIDで止める
- [ ] 7.2 `make verify` が通ることを確かめる
