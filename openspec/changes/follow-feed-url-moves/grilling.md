# grilling 記録: follow-feed-url-moves

GitHubのissueの124番のコメントで、2ラウンドの質問（Q1〜Q8）に答えた記録である。
issueは、購読フィードのURLを変更できず、恒久的な転送（301、308）を受けても保存したURLが変わらないという、Web UIの監査の項目（R-01）である。
httpsへの移行やドメインの移転のたびに、削除して登録し直すしかなく、そのときスター、注釈、既読の記録が消える。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 変更の範囲 | サーバー、API、`docs/api.md` に加えて、Webの設定の編集の欄でURLを変えられるようにし、自動で書き換えたURLと日時を取得の状況の欄に出す。Androidアプリは変えない（B） | 第1ラウンド Q1 |
| 自動で書き換える時機 | 同じ転送先への恒久的な転送が、続けて3回の取得で起きたら書き換える。途中で転送が止まるか、転送先が変わったら、数え直す。転送先として扱うのは、最初から続く301と308の行き先とし、302、303、307が挟まったらその手前で止める。書き換えるのは転送先から読めたときだけにする（B） | 第1ラウンド Q2 |
| 転送先が登録済みのとき | 書き換えず、今までどおり転送をたどって取得を続ける。転送の数は数えない（A） | 第1ラウンド Q3 |
| 手動でURLを変えたときの保存 | 登録と同じ検査をし、取得した項目をその場で保存する。ETag、Last-Modified、失敗の記録、配信終了の記録は消す（A） | 第1ラウンド Q4 |
| 自動で書き換えたことの見せ方 | 取得の状況に「転送によりURLを変更 日時（元: 元のURL）」を文で出す。次にURLが変わる（手動か自動）まで出し続ける。問題のある購読フィードの判定には入れない（A） | 第2ラウンド Q5 |
| URLの欄と保存の流れ | 編集の欄の先頭に「URL」の欄を足し、ほかの値と一緒に保存する。URLが変わったときだけ送る。検査に通らなければ何も保存せず、理由をURLの欄の下に出す。待つ間はボタンを「確かめています…」にする（A） | 第2ラウンド Q6 |
| 取得に失敗したときの数 | 数は変えない。数えも、数え直しもしない（A） | 第2ラウンド Q7 |
| Webページの購読フィード | 対象にする。転送先のページでセレクターが記事を取り出せた取得だけを数える（A） | 第2ラウンド Q8 |

## 計画で決めたこと

承認を求めた計画（issueのコメント）で、次を決めた。利用者は変更なしで承認した（`/ok`）。

| 決定 | 選択 |
|---|---|
| 変更の名前 | `follow-feed-url-moves` |
| 取得の結果 | `HttpResponse` と `BytesResponse` に `permanentUrl`（恒久的な転送の行き先。無ければnull）を足す。Webページの取得の結果にも渡す |
| スキーマの変更 | `044_feed_url_moves.sql` で、`feeds` に4列を足す。数えている行き先とその数、書き換え前の元のURLと書き換えた日時 |
| APIの値 | `Feed` に `movedFrom` と `movedAt` を足す |
| 304の扱い | 転送先が答えた成功の取得として数える |
| 書き換えのトランザクション | 項目の保存と同じトランザクションで行う |
| 手動の変更の入口 | `PATCH /feeds/:id` は、要求に今と違う `url` があるときだけ `changeFeedUrl` を通す。それ以外は今までどおり `updateFeed` を呼ぶ |
| 手動の変更で消すもの | ETag、Last-Modified、失敗の記録、配信終了の記録、転送の数、書き換えの記録 |
| 設定ファイルの読み込み | 手を入れない。転送先が登録済みになるので、元のURLの購読フィードは書き換わらずに取得を続ける |
