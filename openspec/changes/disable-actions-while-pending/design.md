# Design

## Context

購読フィードの登録の解除（`FeedDeletionDialog` の `removing`）だけが、要求の間にボタンを無効にし、処理の入口で二重の呼び出しを捨てていた。
ほかの操作は、ボタンを押すたびに要求を送る。対象の一覧と線引きは、proposal.mdとspecs/web-shell/spec.mdのとおりである。

## Goals / Non-Goals

**Goals:**

- 対象のどの操作も、同じ1つの作りで、要求の間の二重の送信を止める。
- ボタンを止めても止まらない入口（キーと右クリックのメニュー）も止める。

**Non-Goals:**

- すでに自前の状態で守られている所を書き換えること。差分を小さく保つ。
- 守られている所は、購読フィードの追加、フィルターのフォーム、トピックを足すダイアログ、購読フィードの設定のダイアログである。
- メモのダイアログ、登録の解除、「いま取得」「解釈し直す」「試す」「今すぐ作る」も守られている。
- ハイライトを消す操作。押すとすぐにダイアログが閉じるので、二重に送れない。
- 要求の間にボタンの名前を変えること、進み具合の表示を足すこと。

## Decisions

### 共通のフック `usePending`

`apps/web/src/lib/pending.ts` に `const [pending, run] = usePending()` を置く。
`run(task)` は、要求の間なら何もしない。そうでなければ `task` を待ち、成否によらず `pending` を戻す。

- 要求の間かどうかは `ref` で判定する。`pending` の状態が描画へ届く前に2回呼ばれても、要求は1回だけ送る。描画用の `pending` は別の状態として持つ。
- 各画面の部品に `useState` を足し、手本と同じ形に書く案もあった。場所が20を超え、`if (busy) return` の書き忘れが次の欠陥になるので、1つのフックにまとめた。
- React Queryの `useMutation` の `isPending` を使う案は採らない。`mutate` を二重に呼ぶと2回送るので、入口で捨てる仕組みを別に要する。既存の処理も `async` 関数で書かれている。

### フォームは送信の入口で包む

フォームの `onSubmit` で `event.preventDefault()` を呼び、`run(save)` に渡す。入力の確かめ（`problemsOf` など）も `run` の中で行う。
確かめで止まったときも、`pending` はすぐ戻る。Enterでの送信は、送信ボタンが無効なら起きない。起きても `run` が捨てる。

### 1つの `pending` を共にする範囲

- 1つのダイアログや1つの行の中で、要求を送る操作は1つの `pending` を共にする。
  - カテゴリの削除の「削除する」と「無効にする」。
  - トピックの編集の保存と削除。
  - フィルターの行の切り替えと削除。
- 語の削除は、語ごとに `pending` を持つ。押した語のボタンだけを止め、ほかの語は応答を待たずに削除できる（mainのテストが、2つの語を続けて削除できることを求めている）。
- 語のまとまりの「上へ」と「下へ」は止めない。mainで、押した直後に画面を変え、要求を1つずつ順に送り、失敗したら読み直す作りになった。続けて押しても、それぞれが別の並べ替えとして正しく働くので、楽観的な更新の側に入れる。
- トピックの版に戻す操作は、確認のダイアログを閉じてから要求を送る。そこで、要求の間は履歴のすべての「この版に戻す」を止める。
- 設定ファイルの読み込みも、確認のダイアログを閉じてから要求を送る。要求の間は、フォームの「読み込む」を止め、確認を開かない。

### キーとメニュー

- 「すべて既読にする」のボタンとShift+Aは、同じ `run` を通す。要求の間のキーは `run` が捨てる。
- ハイライトの作成では、選んだ文字列の下のボタン、右クリックのメニューの項目、Hのキーが同じ `run` を通す。
- そのボタンとメニューの項目には `disabled` を付ける。メモを書いてハイライトするダイアログは、すでに自前の `saving` で守られているので変えない。

### テスト

`testing/harness.tsx` の `renderApp` に `hold(match)` を足す。一致した要求は、`requests` に記録したうえで、`release()` を呼ぶまで応答を止める。
アプリのテストでは、応答を止めた間に2回押し、要求が1回だけ届くことと、ボタンが無効であることを確かめる。応答を流したあとの知らせも確かめる。

## Risks / Trade-offs

- 押したボタンが無効になると、フォーカスが外れる → 手本の登録の解除と同じ振る舞いである。多くのボタンは、応答のあとに閉じるか、別の場所へフォーカスを移す。
- 応答が返らないと、ボタンが無効のまま残る → APIの呼び出しは失敗でも例外で終わるので、`finally` で戻る。サーバーが応答しないままのときは、ページを開き直せば戻る。
- jsdomでは、ボタンを押すと選んだ文字列が消える → ハイライトのテストでは、キーとメニューを試す前に文字列を選び直す。ブラウザーでは選択は残る。
