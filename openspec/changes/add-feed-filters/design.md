# Design

## Context

動機は、`proposal.md` のWhyを参照する。

いまのストップワードは `packages/core/src/db/stop-words.ts` にある。判定の結果は、記事の行の `stop_word_id` に持つ。一覧、件数、一括の既読、自動の要約の対象からは、語が当たり、スターのない行を除く。その式は `packages/core/src/db/articles.ts` の `HIDDEN` にある。照合は、NFKCで正規化して小文字にした文字列の部分一致である。内容は、記号とリンクのURLを除いた `content_text` に照合する。取得と書き換えのたびに `applyStopWords` が1件を判定し、語の登録、変更、削除のたびに保存済みの配信記事を判定し直す。

配信記事の行は `category_id` を持ち、購読フィードを別のカテゴリへ移すと、その配信記事の `category_id` も書き換わる（`packages/core/src/db/feeds.ts`）。カテゴリを削除すると、配信記事の `category_id` は空になる。配信記事のリンク先のURLは、`article_refs` の先頭の行に、正規化して保存している。

この変更は、範囲（全体、カテゴリ、購読フィード）と2つの種類（隠す、残す）を足す。範囲は表示のときの所属で判定する（#56 round 2 Q9）。照合が正規表現になると、1件あたりの照合の費用が増える。

## Goals / Non-Goals

**Goals:**

- 一覧と件数の問い合わせは、今と同じく、記事の行の1つの列と索引で、隠れた記事を除ける。
- 購読フィードの移動、カテゴリの削除、フィルターの有効と無効の切り替えでは、正規表現の照合をやり直さない。
- 「隠れている」の判定を1か所の式にまとめ、記事の検索（#47）や最近読んだ記事（#51）からも同じ式を使える。

**Non-Goals:**

- 否定の条件と、1つのフィルターの中のOR（#56 round 1 Q5、round 2 Q2）。
- 生成記事への適用（#56 round 1 Q6、#57 round 1 Q5）。
- アプリの設定の画面でのフィルターの編集。アプリは今もストップワードを扱っていない。
- ルール（#59）。条件の形を共有する見込みはあるが、この変更では作らない。

## Decisions

### 能力の改名：`feed-filters` を新しく作り、`stop-words` を廃止する

要件は新しい能力 `feed-filters` に `## ADDED Requirements` として書く。`stop-words` の差分では、10の要件をすべて `## REMOVED Requirements` にし、ReasonとMigrationに引き継ぐ先の要件を書く。`.openspec.yaml` に `retire_capabilities: true` を置き、archiveのときに `openspec/specs/stop-words/spec.md` を消させる。

`feed-subscriptions`、`http-api`、`settings` には、名前に「ストップワード」を含む要件がある。これらは `## RENAMED Requirements` で名前を改め、同じ差分の `## MODIFIED Requirements` で本文を改める。Webの設定の画面の4つの要件は、操作の中身が変わるため、REMOVEDとADDEDで置き換える。

- 採らなかった案：`stop-words` の能力の名前を残し、要件をMODIFIEDで書き換える。能力の名前とPurposeに古い用語が残り、用語集の改名と食い違う。
- 採らなかった案：能力のディレクトリを手で `feed-filters` へ移す。差分で表せず、`openspec validate --strict` とarchiveの手順から外れる。

### 条件の欄は複数を選べ、どれかに合えば条件に合う

条件は `{ fields: ("title" | "content" | "author" | "url")[], match: "contains" | "regex", value }` とする。`fields` は1つ以上で、選んだ欄のどれかが値に合えば、その条件に合う。

今の「タイトルと内容」のストップワードは、タイトルか内容のどちらかに語を含めば隠す。1つのフィルターの中の条件はANDなので（#56 round 1 Q5）、欄を1つしか選べない形では、この語を1つのフィルターに移せない。欄を複数選べる形なら、1つの語を1つのフィルターへそのまま移せ、隠している件数も語ごとに引き継げる（#56 round 1 Q1）。

- 採らなかった案：欄の選択肢に「タイトルと内容」を足す。著者とURLの組み合わせに広げにくい。
- 採らなかった案：「タイトルと内容」の語を、タイトルのフィルターと内容のフィルターの2つに分ける。登録数と件数が移行の前と合わなくなる。

### 正規化と正規表現

部分一致は、今と同じく、値と欄の文章の両方をNFKCで正規化し、小文字にして `includes` で照合する。

正規表現は、値をNFKCで正規化し、フラグ `iu` で `RegExp` にする。欄の文章もNFKCで正規化する。値を小文字にはしない。小文字にすると、`\D`、`\S`、`\W` のような書き方の意味が変わるためである。大文字と小文字の違いは `i` フラグで無視する。登録と変更と確認のたびに `RegExp` を作り、例外が出た条件を400で拒否する（`http-api` の「フィルターの入力の拒否」）。

正規化の関数 `normalizeForMatch` は、語の色付け（#54）も使う。どちらが先に入っても、関数は1つに保つ。

値の長さの上限は200文字、1つのフィルターの条件は10個までとする。

### 照合の結果を表に持ち、隠れているかは記事の列にまとめる

移行で次の表と列を作る。

- `filters`：`id`、`action`（`hide` か `keep`）、`scope`（`all`、`category`、`feed`）、`category_id`、`feed_id`、`enabled`、`created_at`。`action = 'keep'` で `scope = 'all'` の行は `CHECK` で拒む。`category_id` と `feed_id` は `ON DELETE CASCADE` とする。
- `filter_conditions`：`filter_id`、`position`、`fields`（JSONの配列）、`match`、`value`、`normalized`。
- `filter_matches`：`(filter_id, article_id)`。フィルターの条件をすべて満たす配信記事の組を持つ。両方とも `ON DELETE CASCADE` とする。
- `articles.filtered`：有効なフィルターで隠れている配信記事を1にする。スターは見ない。一覧と件数は `filtered = 1 AND starred = 0` の行を除く。

`filter_matches` は、範囲や有効と無効の別に関係なく、すべての配信記事について持つ。照合の結果は、所属にも有効と無効の別にもよらない。そのため、購読フィードの移動、カテゴリの削除、有効と無効の切り替え、範囲と種類の変更では、正規表現を走らせずに `filtered` だけを計算し直せる。

`filtered` は、次の式を1つのSQLの断片にして計算する。

- 隠す：記事に合う有効な隠すフィルターのうち、範囲が全体、記事の `category_id`、記事の `feed_id` のどれかに当たるものがある。
- 残す（カテゴリ）：記事の `category_id` を範囲とする有効な残すフィルターがあり、そのどれにも合わない。
- 残す（購読フィード）：記事の `feed_id` を範囲とする有効な残すフィルターがあり、そのどれにも合わない。

3つのどれかが真なら1にする。対象は `origin = 'feed'` の行だけで、生成記事の `filtered` は常に0である。

計算し直す時点は次のとおりである。

| 契機 | 照合 | `filtered` の計算 |
|---|---|---|
| 配信記事の保存、項目の書き換え | その記事とすべてのフィルター | その記事 |
| フィルターの登録、条件の変更 | そのフィルターとすべての配信記事 | すべての配信記事 |
| 範囲、種類、有効と無効の変更、削除 | しない | すべての配信記事 |
| 購読フィードの移動 | しない | その購読フィードの配信記事 |
| カテゴリの削除 | しない | 属していた購読フィードの配信記事 |

- 採らなかった案：今と同じく、隠しているフィルターの番号を記事の列に1つだけ持つ。残すフィルターでは「どのフィルターが隠したか」が1つに決まらない。所属が変わるたびに照合をやり直す必要もある。
- 採らなかった案：一覧の問い合わせのたびに `filter_matches` を引いて判定する。件数の問い合わせが全件を走査し、索引で答えられなくなる。

### 隠している件数と、隠した配信記事の一覧

件数と一覧は、`filter_matches` と範囲から、問い合わせのときに数える（`feed-filters` の「隠している件数の提供」）。

- 隠すフィルター：範囲に入り、そのフィルターに合い、スターのない配信記事。
- 残すフィルター：範囲に入り、その範囲の有効な残すフィルターのどれにも合わず、スターのない配信記事。同じ範囲の残すフィルターは、同じ件数になる。

ほかのフィルターでも隠れる記事は、それぞれで数える。今のストップワードは、隠した記事を古い語だけに数えていた。正規表現が意図どおりに働くかを確かめる用途（#56 round 2 Q7）では、フィルターごとに、そのフィルターが当たる記事をすべて見せるほうが役に立つ。

削除と無効化の応答の「一覧に戻った件数」は、対象の配信記事の `filtered` を計算し直す前と後で比べ、1から0に変わったスターのない記事を数える。

### 保存の前の確認

`POST /api/v1/filters/preview` は、登録と同じ形の本文と、変更のときは対象の `id` を受け取る。照合はメモリーの上で行い、`filter_matches` と `filtered` には書かない。件数の定義は「隠している件数の提供」と同じである。変更の確認では、対象のフィルターの変更前の内容を除き、確認する内容で置き換えて数える。照合は、示された範囲に入る配信記事だけで行う。

### APIの形

| 操作 | パス |
|---|---|
| 一覧 | `GET /api/v1/filters` |
| 登録 | `POST /api/v1/filters`（201） |
| 変更、有効と無効の切り替え | `PATCH /api/v1/filters/:id` |
| 削除 | `DELETE /api/v1/filters/:id`（`{ restored }` を返す） |
| 隠した配信記事の一覧 | `GET /api/v1/filters/:id/articles`（記事の一覧と同じ形と `cursor`） |
| 保存の前の確認 | `POST /api/v1/filters/preview`（`{ hiddenCount }` を返す） |

範囲は `{ "type": "all" }`、`{ "type": "category", "categoryId": 1 }`、`{ "type": "feed", "feedId": 2 }` で表す。`/api/v1/stop-words` は外す。アプリはストップワードのAPIを使っておらず、Webは同じ版で入れ替わる。

同じフィルターかどうかは、種類、範囲、条件の並び（欄の集合、方法、正規化した値）で判定する。登録では409を返し、設定ファイルの読み込みでは登録を飛ばす。

### 設定ファイルの形

```yaml
filters:
  - action: hide
    scope: all
    conditions:
      - fields: [title, content]
        match: contains
        value: sponsored
  - action: keep
    scope: { feed: https://example.com/feed.xml }
    enabled: false
    conditions:
      - fields: [title]
        match: regex
        value: "release|announce"
```

範囲のカテゴリは `{ category: <識別名> }`、購読フィードは `{ feed: <URL> }` で書く。`enabled` は有効のときに省く。読み込みは、カテゴリと購読フィードを登録したあとにフィルターを登録し、範囲を結び付ける。書き出しは `filters` だけを書く。

`stopWords` の鍵も受け付け、各語を全体の隠すフィルターに変換してから、同じ処理に渡す。`stopWords` と `filters` の両方があれば両方を読む。読み込みの結果の `stopWordsCreated` は `filtersCreated` に改める。

### Webの画面

`/settings/stop-words` を `/settings/filters` に置き換え、設定の画面の項目名を「フィルター」にする。フィルターの一覧、追加と編集の入力、保存の前の確認、隠した配信記事の一覧を、この画面に置く。条件の入力は、欄のチェックボックス、方法の選択、値の欄を1行にし、行を足し引きする。色と間隔は `DESIGN.md` の値を使う。新しい値が要るときは、先に `DESIGN.md` へ足す。

隠した配信記事は、どの一覧にも出ない。一覧から本文を開く道筋は、実装のときに読む画面の作りを見て決める。読む画面が、一覧にない記事をIDで開けるならそれを使い、開けないなら設定の画面の中に本文を出す。

## Risks / Trade-offs

- ［正規表現の照合で、サーバーの処理が長く止まる］→値の長さと条件の数に上限を置く。登録と確認は利用者本人だけが行う。それでも止まる書き方が見つかったら、V8の線形時間の正規表現の機能を検討する。
- ［フィルターの登録のたびに、すべての配信記事を照合する］→今のストップワードも同じ量を照合している。件数が増えて遅くなったら、範囲に入る記事だけを先に照合し、残りをあとで照合する形に分ける。
- ［`filter_matches` の行が増える］→当たる記事だけを持つ。「URLに `https` を含む」のように全件に当たる条件では配信記事の数だけ増えるが、1行は整数2つである。
- ［記事の表を作り直す移行］→`stop_word_id` は外部キーなので `DROP COLUMN` で外せない。`002_feeds.sql` と同じく `-- foreign_keys: off` の移行で表を作り直す。ほかの変更（#58、#52など）が先に列を足していることがあるため、移行は実装のときの表の定義から書き、番号は空いている次の番号にする。
- ［ほかの変更の文言］→記事の検索（#47）と最近読んだ記事（#51）の仕様は「ストップワードで隠した配信記事」を除くと書いている。全文（#52）の仕様には「全文とストップワードの判定」がある。後からarchiveする側で、文言をフィルターに合わせる。実装では、隠れているかの判定に `articles.ts` の同じ断片を使う。
- ［重複の除去（#58）との重なり］→重複として隠した記事は購読フィードの一覧に出るが、フィルターで隠した記事は出ない。残した側の記事がフィルターで隠れると、重複として隠れた側も全体の一覧に出ない。2つの変更が両方入ったあとで、この組み合わせを確かめる。

## Migration Plan

1. 移行で `filters`、`filter_conditions`、`filter_matches` を作る。
2. `stop_words` の各行を、全体の隠すフィルターと1つの条件に移す。照合の対象が `title` の語は欄を `[title]`、`title_and_content` の語は `[title, content]` にし、方法は部分一致、`created_at` はそのまま移す。
3. 記事の表を作り直して `stop_word_id` を外し、`filtered` を足す。`articles_stop_word` の索引を消し、`articles_counts` の索引の `stop_word_id` を `filtered` に替える。
4. `stop_words` を消す。
5. 移行のあとの最初の起動で、すべてのフィルターとすべての配信記事を照合し、`filter_matches` と `filtered` を作る。移行のSQLでは部分一致の照合を正しく書けないため、起動の処理で行う。照合が済んでいないことは、`filter_matches` の作成済みの印で見分ける。
6. 戻すときは、移行の前のデータベースの写しを使う。移行は戻す処理を持たない。

## Open Questions

- 購読フィードやカテゴリを削除すると、それを範囲とするフィルターも消える（`feed-filters` の「範囲の対象の削除」）。削除の確認の中で、消えるフィルターの数を知らせるかは、grillingで決めていない。知らせるなら、`web-settings` に要件を足す。
- 隠している件数は、ほかのフィルターでも隠れる記事をそれぞれで数え、同じ範囲の残すフィルターは同じ件数を出す。grillingで決めたのは「フィルターごとに件数を出す」までで、数え方はこの設計で選んだ。
