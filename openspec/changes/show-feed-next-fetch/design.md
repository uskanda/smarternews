# Design

## Context

動機は `proposal.md` のWhyに書いた。

- 行の取得の状況は `FeedsPage.tsx` の `FetchState` が描く。最後の成功、直近30日の件数、最後の新着、失敗の理由と、いくつかの印を並べる。
- APIの購読フィードは `failureCount` と `nextFetchAt` を持つ。`failureCount` は失敗のたびに1増え、成功すると0に戻る。
- 一時停止している購読フィードの `nextFetchAt` は `null` である。まだ取得していない購読フィードでは登録の時刻を返す。定期の取得が遅れている間は過去の時刻のままである。

## Goals / Non-Goals

**Goals:**

- 次の取得の時刻と、続いている失敗の回数を、購読フィードの行で読めるようにする。

**Non-Goals:**

- APIとサーバーの変更。
- 時刻が過ぎたときに、画面を開いたまま表示を書き換えること。

## Decisions

### 続けて失敗した回数

`failureCount` が2以上のとき、「取得に失敗」の印の後ろに「{n}回続けて失敗」と出す。1回目は今の印と理由で伝わるので、回数は出さない（grilling.md Q1）。
配信終了の印が出ている行でも、回数は同じ条件で出す。配信終了も取得の失敗として数えるからである。

### 次の取得

`nextFetchAt` が `null` でないとき、「次の取得」に続けて日時を出す。日時の形式は、最後の成功と同じく日付と時刻で、`tabular-nums` を付ける。
アプリの `now()` で描いた時刻と比べ、過ぎていれば（同じ時刻を含む）、日時の代わりに「まもなく」とする（grilling.md Q2）。
一時停止している行には値がなく、一時停止を示す印で伝わるので、何も出さない（grilling.md Q3）。

比べる時刻は、描くたびに `now()` で取る。購読フィードの一覧は取得のあとに読み直されるので、表示もそのとき新しくなる。時刻の経過に合わせて描き直す仕組みは置かない。

## Risks / Trade-offs

- 画面を開いたまま時刻を過ぎても、一覧を読み直すまで日時のまま残る → 取得が終わると一覧は読み直されるので、長くは残らない。
