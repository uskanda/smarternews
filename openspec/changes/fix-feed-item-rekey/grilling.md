# grilling 記録: fix-feed-item-rekey

Issue #214「購読フィードが識別子を付け替えると、読んだ記事が新着として戻る」で、計画についての質問に答えてもらった。
Issueの案は、識別子が初めての項目でも、同じ購読フィードに同じURLの記事が保存済みで、その記事の識別子が取得した文書にもう載っていなければ、新着にせず識別子を付け替えるというもの。
URLはスキームの違いを無視して比べ、LLMは使わない。

この変更は、add-feed-dedupの第3ラウンド Q7「同じ購読フィードの項目同士は比べない」を、識別子の付け替えの場合に限って見直す。
当時の理由は、同じタイトルで別の記事を出すフィードがあることだった。
URLが同じで、古い識別子が文書から消え、タイトルも同じ場合には、その理由は当たらない。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 付け替えとみなす条件にタイトルを足すか | B：URLの一致と古い識別子の消失に加えて、タイトルの一致も求める。大文字と小文字、全角と半角、空白、記号の違いは無視する | Issue #214 第1ラウンド Q1 |
| 候補が1つに決まらないとき | A：付け替えず、いまと同じく新着として保存する。1対1に決まるときだけ付け替える | Issue #214 第1ラウンド Q2 |
| 記事が消えたあとの項目 | A：対象にしない。保存済みの記事がある項目だけを対象にし、`feed_items_seen` に列を足すマイグレーションもしない | Issue #214 第1ラウンド Q3 |
| 付け替えた記事のその後の扱い | 保存済みの項目の経路を通す。URLのスキームが変われば参照のURLと重複の判定の値を直し、既読の状態は変えない | Issue #214 計画の前提（質問にしなかったこと） |
| 付け替えた項目を新しい項目と数えるか | 数えない。最後に新しい項目が現れた時刻を更新せず、1回の取得で保存する新着の上限にも数えない | Issue #214 計画の前提（質問にしなかったこと） |
| add-feed-dedup 第3ラウンド Q7 の見直し | 同じ購読フィードの項目同士を比べるのは、この付け替えの場合だけにする | Issue #214 の案と計画 |
| 計画の承認 | 上の答えに沿った計画を承認 | Issue #214への返答（`/ok`） |
