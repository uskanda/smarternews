# Design

## Context

取得した文書の保存は `packages/core/src/feeds/ingest.ts` の `storeItems` が担う。
項目は `item_key`（識別子。なければ元のページのURL）だけで保存済みの配信記事と突き合わせる。
合わなければ、`feed_items_seen`（フィードが載せたことのある識別子の表）にない限り新しい項目として扱い、最大200件（`MAX_NEW_ITEMS`）を保存する。
`articles` には `(feed_id, item_key)` の一意の索引があり、元のページのURLは `article_refs` の先頭の行に、`normalizeUrl` でならした形で入っている。
`feed_items_seen` はURLを持たない。

動機は proposal.md の Why を、決定は grilling.md を参照。

## Goals / Non-Goals

**Goals:**

- 識別子だけを付け替えた項目を、保存済みの配信記事として扱い、既読の状態と最後に新しい項目が現れた時刻を保つ。
- 付け替えとみなす条件を満たさない場合は、いまと同じく新しい配信記事にする。

**Non-Goals:**

- 保存期間で配信記事を削除したあとの項目（grilling.md Q3）。
- 表の変更とマイグレーション。
- 購読フィードをまたぐ重複の判定の変更。

## Decisions

### 付け替えは文書の項目を処理する前にまとめて決める

古い識別子が文書から消えたかどうかは、文書の全体を見ないと分からない。
そのため、項目を順に処理する前に、文書の項目の識別子とURLを集め、付け替えを決めて `item_key` を書き換える。
書き換えたあとは保存済みの配信記事の索引も新しい識別子で引けるようにし、項目の処理はいまの「保存済みの項目」の経路をそのまま通す。
付け替えた項目は既知になるので、`foundNew`（最後に新しい項目が現れた時刻を動かす印）も立たず、新着の上限にも数えない。

ほかの案として、項目の処理の途中で付け替えを判定する方法がある。
ただし、後ろの項目に古い識別子が残っているかを途中では判定できず、結局は文書の識別子を先に集める必要があるため採らない。

### 比べる値

- URL：項目のURL（`normalizeUrl` でならしたもの）と、配信記事の参照の先頭のURLを、先頭の `http:` または `https:` を除いて比べる。URLのない項目と配信記事は比べない。
- タイトル：`normalizeTitle` と同じならし方（NFKC、小文字、空白と記号の除去）をし、10文字の下限は設けない。ならした結果が空なら一致とみなさない。そのため、ならし方を `url.ts` の下限のない関数に切り出し、`normalizeTitle` はそれを使う。項目のタイトルは文書のタイトルそのものを使い、内容から作る代わりのタイトルは比べない。
- 1対1：同じURLの保存済みの配信記事が1件だけで、その配信記事の識別子が文書になく、タイトルが一致する初めての項目が1つだけのときに限る（grilling.md Q2）。

### 古い識別子の `feed_items_seen` の行は残す

古い識別子は文書から消えているので、これまでと同じく保存期間が過ぎれば忘れられる。
付け替えた直後に古い識別子がまた現れても、`feed_items_seen` にあるため新しい項目にはならない。

## Risks / Trade-offs

- [配信元が識別子と一緒にタイトルも変えた] → いまと同じく新しい配信記事として戻る。タイトルの一致を求めた結果で、grilling.md Q1 で受け入れた。
- [同じURLを使い回すフィードで、タイトルも同じ新しい項目が届く] → 保存済みの配信記事の書き換えとして扱われ、新着にならない。告知のページで同じタイトルを繰り返す場合に限られ、古い項目が文書から消えていることも条件のため、起きにくい。
- [1回の取得で保存済みの配信記事を全件読む] → いまも全件を読んでおり、付け替えの判定はその結果を使うので、問い合わせは増えない。

## Migration Plan

マイグレーションはない。配布後の最初の取得から効く。戻すときは `ingest.ts` を戻せばよく、付け替え済みの `item_key` はそのまま使える。
