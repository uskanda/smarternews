# Design

## Context

動機は `proposal.md` の「Why」を見よ。ここでは、設計を決める今の作りだけを書く。

- 生成記事と配信記事は、どちらも `articles` の表に入っている。生成記事の本文は `body`（Markdown）にある。配信記事の配信された内容は `body` にあり、語だけの文字列は `content_text` にある。全文（#52）は `full_content` と `full_content_text` にあり、移行 `013_full_content.sql` で足した。
- 検索の索引（#47）は、移行 `012_article_search.sql` が作ったFTS5の表 `article_search` である。行の識別子は記事の識別子と同じで、1つの記事に1行、照合する欄を正規化して1つの文字列に入れている。`articles` の追加、更新、削除のトリガーが、`openDatabase` で登録するSQLの関数 `sn_search_text` を呼んで行を作り直す。検索語の照合は `packages/core/src/db/articles.ts` にある。3文字以上の語は `article_search MATCH ?` で、2文字以下の語は `LIKE` で照合し、語ごとに条件を重ねる。どの語も、同じ行の文字列のどこかに含まれればよい。
- フィルターで隠れているかは、`packages/core/src/db/articles.ts` の `hiddenByFilters(alias)` が決める。条件は `filtered = 1 AND starred = 0` である。列 `filtered` はスターを考えずにフィルターの照合で決め、スターは読み出すときに見る。記事の一覧、件数、一括の既読、自動の要約と全文の取得を待つ記事、ほかに配信した購読フィード、検索がこの条件を使う。フィルターごとの件数、隠した配信記事の一覧、保存の前の件数の確認、削除で戻った件数は、`packages/core/src/db/filters.ts` で別に `starred = 0` を見ている。
- 購読フィードの一覧の応答は、購読フィードごとに `articleCount` と `starredCount` を持つ。Webの購読フィードの削除の確認は、設定の画面（`FeedsPage.tsx`）と左のペインのメニュー（`Shell.tsx`）の2か所にあり、どちらもこの2つの数を使う。
- 保存期間の削除は、`packages/core/src/db/articles.ts` の2つの問い合わせである。生成記事は `GENERATED AND starred = 0 AND updated_at < ?` で消す。配信記事は `origin = 'feed' AND starred = 0 AND updated_at < ?` で消す。
- Webの本文は `apps/web/src/reader/Markdown.tsx` が `react-markdown` で描く。検索の強調と語の色付けは、`apps/web/src/reader/highlight.tsx` の `rehypeHighlights` が、HTMLの木の文字の節を区間に分けて `mark` で包む。本文の訳は `ArticleView.tsx` の `TranslatedBody` が、まとまりごとに訳と原文の `Markdown` を並べて描く。全文と配信された内容の切り替えは `FullContentControl` が持つ。
- アプリの本文は `apps/mobile/src/reader/Markdown.tsx` が `marked` の字句を入れ子の `Text` に描く。色付けは `apps/mobile/src/reader/highlight.tsx` にある。
- `packages/client` は、Webとアプリが共有する処理を置く場所で、画面の部品とNodeの機能には依存させない。語の色付けの区間の計算（`highlight.ts`）もここにある。
- 左のペインの上部の項目は、`packages/client/src/nav.ts` の `ListTarget` で表す。「最近読んだ記事」は `recentlyRead` で、パスは `/recently-read` である。
- 移行は001から014まである。古い移行は書き換えない。

## Goals / Non-Goals

**Goals:**

- ハイライトを、本文が変わっても同じ文字列に付け直せる形で保存する。Webとアプリが、同じ規則で本文から探す。
- 注釈を検索の索引に、どの書き込みの経路からでも漏れなく入れる。注釈を書くコードが索引を気にしなくてよい形にする。
- 注釈の描画を、検索の強調と語の色付けと同じ木の上の処理に載せ、Markdownの構造、リンク、HTMLを文字として出す安全の扱いを変えない。

**Non-Goals:**

- 注釈の書き出し（grillingで後回し）。
- 設定ファイルの書き出しと読み込みに注釈を含めること。設定ファイルが持つのは設定であり、注釈は利用者の記録である。
- アプリでの注釈の作成、変更、削除（grillingの決定）。
- 1つの文字に2つのハイライトを重ねること。仕様 `web-reader` の「ハイライトと重なる範囲」で作らせない。
- 記事の一覧の行に、注釈があることの印を出すこと。決定に含まれない。
- アプリの引き出しに「注釈」の一覧を置くこと（round 3 Q4）。アプリでの注釈は、本文の画面での表示だけにする。決定の「アプリは表示だけ」をそう読み、利用者に確かめた。
- `g` に続くキーで「注釈」へ移る操作（round 3 Q8）。「注釈」へは、左のペインの項目と `Shift+J`、`Shift+K` で移る。
- 全文を検索の対象にすること。全文（#52）の設計で対象にしないと決めた。注釈のハイライトした文字列は、全文の中のものでも照合する。

## Decisions

### 注釈は1つの表に、種類の列を付けて置く

新しい移行（`<015_annotations.sql>`。番号は実装の時点で取り込み済みの最後の移行の次に付け直す）で、表 `annotations` を足す。

| 列 | 内容 |
|---|---|
| `id` | 識別子 |
| `article_id` | `articles` の識別子。記事の削除に連動して消える（`ON DELETE CASCADE`） |
| `kind` | `highlight` または `note`（記事全体へのメモ） |
| `quote` | ハイライトした文字列。`note` では値なし |
| `prefix`、`suffix` | ハイライトの前と後の、それぞれ最大32文字。`note` では値なし |
| `position` | ハイライトの始まりの位置。空白を除いた本文の文字列の上で数える。`note` では値なし |
| `note` | メモ。ハイライトでは値なしにできる。`note` では必ず値を持つ |
| `created_at`、`updated_at` | 付けた時刻と、最後に変えた時刻 |

`CHECK` で、種類ごとの値の有無を縛る。`note` の行は、部分の一意の索引（`WHERE kind = 'note'`）で、1つの記事に1行だけとする。索引は、一覧の並びのための `(created_at DESC, id DESC)` と、記事の詳細のための `article_id` を置く。

ハイライトの表と記事全体へのメモの表を分ける案は採らない。注釈の一覧は2種類を1つの並びで分割して返すので、2つの表を合わせて並べ直すことになる。

メモを変えても `created_at` は変えない。一覧の並びは `created_at` で決める（仕様 `annotations` の「注釈を付けた時刻の保持」）。記事全体へのメモの置き換えも、行を作り直さずに `note` と `updated_at` だけを変える。

### ハイライトの位置は、文字列と前後の文字で表す

ハイライトは、ハイライトした文字列（`quote`）、前と後の文字（`prefix`、`suffix`）、始まりの位置（`position`）で表す。W3CのWeb Annotationの「TextQuoteSelector」と「TextPositionSelector」に当たる。

次の案は採らない。

- DOMの範囲（要素の経路と文字の位置）。本文を描き直すと経路が変わる。Webとアプリで木の形が違うので、アプリで使えない。
- Markdownの文字列の上の位置。描いた文字と記法の位置の対応を、WebとアプリのMarkdownの処理がそれぞれ持っていない。続報や書き換えで、位置はすぐずれる。
- サーバーで探して範囲を返す方法。範囲は描いたあとの文字の上でしか使えない（語の色付けの設計と同じ理由）。

位置は、同じ文字列が本文に複数あるときの見分けにだけ使う。本文が変わっていなくても、表示のたびに文字列で探す。本文の版を控えて、変わったときだけ探し直す案は採らない。控える値が増え、全文の取得と書き換えのたびに版を合わせる手間が増える。

### 本文の中でハイライトを探す処理は、`packages/client` に1つだけ置く

`packages/client/src/annotations.ts` に、次の純粋な関数を置く。

- `anchorOf(text, start, end)`: 描いた本文の文字列と選んだ範囲から、`quote`、`prefix`、`suffix`、`position` を作る。Webが選んだ範囲を保存するときに使う。
- `locateHighlights(text, highlights)`: 描いた本文の文字列の上で、各ハイライトの範囲を求める。見つかったものの範囲と、見つからなかったものの一覧を返す。

探す規則は次のとおりである（仕様 `annotations` の「同じ文字列の見分け」「空白の違いの無視」）。

1. 本文の文字列と `quote` から空白と改行を除いて比べる。除いた文字列の各文字が元のどの位置から来たかを控え、見つかった範囲を元の位置に戻す。全文検索の `normalizeWithMap` と同じ考え方である。
2. `quote` の出現をすべて探す。1つもなければ、見つからないハイライトとする。
3. 複数あれば、前の32文字と後の32文字が `prefix`、`suffix` と末尾から（後は先頭から）何文字一致するかを数え、その合計の最も大きい出現を選ぶ。同じならば、`position` に最も近い出現を選ぶ。
4. 本文が変わったあとに、2つのハイライトが重なる範囲に見つかることがある。重なった文字は、付けた時刻の古いハイライトのものとして描く。

大文字と小文字、全角と半角は区別する。ハイライトは利用者が選んだ文字列そのものであり、検索の語のように表記の揺れを吸収する理由がない。

WebとアプリのMarkdownの処理が別なので、同じ本文から作る文字列は細かく違いうる。空白を除いて比べるのは、段落の区切りの改行の入り方の違いを吸収するためでもある。どちらの処理でも同じ文字列になることを、共通の例の本文でテストする（「Risks / Trade-offs」を見よ）。

### 対象の文字列は、描いた原文の文字の節だけからつなげる

ハイライトの対象の文字列は、描いた原文の木の文字の節を、文書の順につなげたものである。画像の説明、リンクのURL、訳のまとまり、要約の区画、タイトル、読み手への影響は含めない。

- Webの `Markdown.tsx` の文字の節は、`react-markdown` がHTMLの木に作る文字の節である。画像の説明は属性なので入らない。画像を読めずに説明を文字で出すときは、その要素に印の属性を付け、選んだ範囲の計算でも飛ばす。
- 生成記事では本文を、配信記事では全文があれば全文を、なければ配信された内容を対象にする。全文のある記事で配信された内容を出している間は、対象の文字列を作らず、ハイライトを描かない。仕様 `web-reader` と `mobile-reader` の「配信された内容を表示している間のハイライト」に当たる。
- 本文の訳を出している間は、原文のまとまりだけをつなげて対象の文字列にする。まとまりをまたぐハイライトも、つなげた文字列の上で探せる。

### Webは、描いた木の文字を親が集めてから、範囲を配る

訳のない本文は1つの `Markdown` で描くが、訳のある本文は原文のまとまりごとに別の `Markdown` で描く。ハイライトはまとまりをまたぎうるので、全体の文字列で探してから、まとまりごとの範囲に分ける。

1. `Markdown` に、描く前の木の文字を親へ知らせる口を足す。`rehypeHighlights` と同じ処理の中で、文字の節をつなげた文字列を渡す。
2. 本文の部品（`ArticleView.tsx` に足す `AnnotatedBody`）は、原文のまとまりの文字列をすべて受け取ったら、つなげて `locateHighlights` を呼ぶ。範囲を、まとまりごとの始まりからの位置に直して配る。
3. `rehypeHighlights` は、検索の語とまとまりの語に加えて、注釈の範囲を受け取る。注釈の範囲で文字の節を分け、`mark` の要素で包む。注釈の `mark` は、語の色付けと検索の強調の `mark` の外側に置く。

ハイライトのある記事は、最初の描画で範囲が決まらないので、描き直しが1回増える。ハイライトのない記事では、この往復をしない。
Markdownの木の作り方を、画面の外でもう一度まねて文字列を作る案は採らない。描く処理と別の処理で作ると、文字列がずれたときに範囲が狂う。

ハイライトの `mark` には `data-annotation` の属性でハイライトの識別子を付ける。1つのハイライトが複数の文字の節に分かれるときは、最初の `mark` にだけ `tabindex="0"` を付け、Tabキーで止まる位置を1つにする。仕様 `web-shell` の「キーボードだけでの注釈の操作」に当たる。読み上げの名前は「ハイライト」と、メモがあれば「メモあり」にする。メモのあるハイライトの最後の `mark` のあとに、メモの印のアイコンを置く。

### Webで範囲を選んでハイライトを付ける

本文の部品は、`selectionchange` を見て、選んだ範囲が対象の文字列の中に収まるかを調べる。収まるのは、範囲の両端の文字の節が原文の `Markdown` の根の中にあり、印の属性で飛ばす要素の外にあるときである。

- 収まり、既存のハイライトと重ならないとき、選んだ範囲の矩形の下に、小さなメニュー（`role="toolbar"`）を出す。ボタンは「ハイライト」と「メモを書く」である。メニューは自前で作り、依存を増やさない。
- 「メモを書く」は、既存の `@radix-ui/react-dialog` のダイアログで入力欄を出す。保存すると、メモ付きのハイライトを1回の要求で作る。
- `h` のキーは、`apps/web/src/lib/keys.ts` のキーの処理に足す。同じ判定を通り、メニューの「ハイライト」と同じ処理を呼ぶ。入力欄にフォーカスがある間は、既存の規則で無効になる。`apps/web/src/shell/Shell.tsx` の `KEYS` に `["h", "選んだ文字列をハイライトする"]` を足し、`?` の一覧に出す。
- 選んだ範囲の両端は、対象の文字列の上の位置に直してから `anchorOf` に渡す。ブラウザーが返す選んだ範囲の文字列は使わない。ブラウザーが段落の境目に入れる改行が、対象の文字列と合わないためである。

ハイライトを押す（またはフォーカスして `Enter`）と、ダイアログを出す。ダイアログは、ハイライトした文字列、メモの入力欄、保存、ハイライトを消すボタンを持つ。メモのあるハイライトを消すときは、既存の `ConfirmDialog` で確かめる。閉じたら、フォーカスをハイライトの最初の `mark` に戻す。

記事全体へのメモは、本文の上部の操作の並びに「メモ」のボタンを置き、本文の上に入力欄を開く。保存は `PUT`、空にして保存したときは `DELETE` を呼ぶ。

保存したあとは、記事の詳細と注釈の一覧のキャッシュを更新する。検索の結果のキャッシュも古くするが、読み直すのは結果の画面を開いたときにする。

### 見つからないハイライトの区画

`locateHighlights` が見つからないと返したハイライトを、本文の最後（出典の前）に「元の本文にあった箇所」の見出しの区画として並べる。各項目は、ハイライトした文字列を引用の形で、メモをその下に出す。Webでは本文のハイライトと同じダイアログを開ける。
区画は、ハイライトの見た目では描かない。本文の中にある箇所と見分けるためである。

### 注釈の一覧の画面

`ListTarget` に `annotations` を足し、パスを `/annotations` にする。左のペインの「最近読んだ記事」の下に置き、数字を付けず、ドラッグの対象から外す。
一覧の画面は記事の一覧の部品を使わず、`apps/web/src/reader/<AnnotationList.tsx>` を足す。行の単位が記事ではなく注釈であり、同じ記事が複数の行に出るためである。

- 行は、記事のタイトル（訳したタイトルがあれば訳）、ハイライトした文字列（2行まで）、メモ（2行まで）、付けた時刻を出す。記事全体へのメモの行は、ハイライトした文字列の位置に「記事へのメモ」の印を出す。
- 行を選ぶと、本文のペインに記事を出し、URLを `/annotations/<記事の識別子>?annotation=<注釈の識別子>` にする。本文の部品は、そのハイライトの `mark`（見つからないときは区画）までスクロールし、フォーカスを当てる。
- `j` と `k` は行を移る。一括の既読、既読を含める切り替え、重要度4以上の切り替えは出さない。
- 続きは、記事の一覧と同じく、スクロールの末尾で取得する。

### 検索の索引へは、注釈の表のトリガーで入れる

注釈の文字列を、記事の索引の行の文字列の末尾に足す。1つの記事に1行という索引の形を変えない。
語ごとに「同じ行のどこかに含む」で照合しているので、本文の語とメモの語を組み合わせた検索（仕様 `article-search` の「本文の語とメモの語」）が、問い合わせを変えずに通る。

注釈のための別のFTS5の表を作る案は採らない。複数の語が記事の欄と注釈に分かれて含まれるとき、語ごとに2つの表を合わせる問い合わせが要る。短い語の `LIKE` の照合も、2つの表に向けて書くことになる。

新しい移行で次を行う。

1. `openDatabase` で、SQLの関数 `sn_annotation_text(quote, note)` を登録する。ハイライトした文字列とメモを、`sn_search_text` と同じ正規化（`normalizeForMatch`）で1行ずつにした文字列を返す。メモはMarkdownとして扱わず、そのまま正規化する。
2. `VIEW` の `article_search_source(id, text)` を作る。`sn_search_text` の値の後ろに、その記事の注釈の `sn_annotation_text` を `group_concat` で改行でつないだものを足す。注釈のない記事では、`sn_search_text` の値と同じになる。
3. `articles_search_update` のトリガーを消して作り直す。新しいトリガーは、索引の行の文字列を `article_search_source` から取る。続報や書き換えで記事が変わっても、注釈の文字列が索引から落ちない。
4. `annotations` の追加、更新、削除のトリガーを足す。どれも、その記事の索引の行を `article_search_source` から作り直す。
5. `articles_search_insert` と `articles_search_delete` は変えない。新しい記事に注釈はなく、削除では行ごと消えるためである。

記事が消えるとき、注釈は連動して消え、注釈の削除のトリガーも動く。そのとき記事の行はもうないので、トリガーは `EXISTS (SELECT 1 FROM articles WHERE id = OLD.article_id)` のときだけ索引を書き直す。この順をテストで確かめる。

`sn_search_text` の引数を増やす案は採らない。移行012のトリガーと埋め戻しが9つの引数で呼んでいるので、新しいデータベースを作るときに、012の時点で引数の数が合わなくなる。

ハイライトした文字列は、本文に見つからなくなったものも索引に残る（仕様 `article-search` の「照合する欄」）。注釈の行は本文が変わっても消えないので、何もしなくてもこうなる。

### メモにだけ一致した記事は、メモから抜粋を作る

仕様 `article-search` の「一致した箇所の抜粋」を変える（round 3 Q5）。要約、本文、読み手への影響、会場のどれにも語がないとき、注釈のメモから抜粋を作る。メモにだけ語を含む記事の行に要約が出ても、なぜ結果に入ったかが分からないためである。

- `packages/core/src/search/text.ts` の `excerptOf` の欄の並びの後ろに、メモを足す。記事全体へのメモを先に見る。続けて、ハイライトへのメモを付けた時刻の古い順に見る。メモはMarkdownとして扱わず、空白をまとめるだけにする。
- 検索の結果の各記事に `excerptFromNote`（真偽値）を足す。メモから作った抜粋のときだけ真にする。抜粋が値なしのときと、ほかの欄から作ったときは偽である。`packages/core/src/api.ts` の検索の結果のスキーマと `docs/api.md` に足す。
- Webとアプリは、`excerptFromNote` が真の行で、抜粋の前に `label-sm` の「メモ」を置く。仕様 `web-reader` の「メモからの抜粋の明示」と、`mobile-reader` の「アプリでのメモからの抜粋の明示」に当たる。検索語の強調は、ほかの抜粋と同じく付ける。
- メモは、記事の欄の読み出しと同じ問い合わせで、結果の記事の識別子ごとにまとめて読む。1件ずつ問い合わせない。
- ハイライトした文字列にしか語がない記事（本文から消えたハイライト）では、抜粋を値なしにする。ハイライトした文字列は利用者が書いた文ではなく、本文の写しである。メモだけを抜粋に使うという決定の範囲にとどめる。

ほかの欄とメモの両方に語があるときは、ほかの欄から作る。要約と本文の抜粋のほうが、記事の中身を伝えるためである。

### 保存期間の削除の問い合わせに、注釈の有無を足す

`packages/core/src/db/articles.ts` の2つの削除の問い合わせに、注釈のない記事だけを選ぶ条件を足す。条件は `NOT EXISTS (SELECT 1 FROM annotations n WHERE n.article_id = articles.id)` である。生成記事の問い合わせの由来の条件（`GENERATED`）は残す。
注釈をすべて消した記事は、この条件から外れるので、次の削除で対象に戻る。別の印の列（`annotated` のようなフラグ）を記事に持つ案は採らない。注釈の追加と削除のたびに、列を合わせ直す手間が増える。

購読フィードの削除は、仕様 `feed-subscriptions` の「購読フィードの削除」のとおり、注釈のある配信記事も消す。注釈は連動して消える。

### 購読フィードの削除の確認に、注釈のある配信記事の件数を出す

削除の確認で、注釈のある配信記事の件数も示す（round 3 Q6）。スターと違い、注釈は利用者が書いた文を持つので、黙って消すと取り戻せない。

- 購読フィードの一覧の問い合わせ（`packages/core/src/db/feeds.ts`）に、`starred_count` と並べて `annotated_count` を足す。式は、その購読フィードの配信記事のうち `hasAnnotation` に当たるものを `count(*)` で数える。1つの配信記事に注釈が複数あっても1件と数える（仕様 `http-api` の「購読フィードの一覧での注釈のある配信記事の件数」）。
- 応答の購読フィードに `annotatedCount` を足し、`packages/core/src/api.ts` のスキーマと `docs/api.md` に書く。
- `FeedsPage.tsx` と `Shell.tsx` の確認の文では、スターの件数の文の後ろに1文を足す。その文は、注釈のある件数と、注釈も消えることを伝える。文の言い回しは実装のときに決める。0件のときは足さない。仕様 `web-shell` の「メニューからの登録解除」は、確認のダイアログが設定の画面の削除と同じ内容を伝えると定めている。そのため、要件は `web-settings` の「削除で消える注釈のある配信記事の件数の表示」だけに足し、2か所の確認の文は1つの関数で作る。フィルターの数の表示（#56）と同じやり方である。

確認を開くときに件数を別のAPIで取る案は採らない。スターの件数がすでに一覧の応答にあり、同じ場所に置けば確認の文を作る処理が1か所で済む。

### 注釈のある配信記事は、フィルターで隠さない

スターのある配信記事と同じく、注釈のある配信記事をフィルターで隠さない（round 3 Q7）。決定の「スターと同じ扱い」の範囲を、保存期間からフィルターにも広げた。注釈を付けた記事が一覧から消えると、利用者の残した記録も見えなくなる。

隠れているかの条件に、注釈の有無を足す。列 `filtered` は変えず、読み出すときに見る。スターと同じやり方である。

- `packages/core/src/db/articles.ts` に `hasAnnotation(alias)` を置く。式は `EXISTS (SELECT 1 FROM annotations n WHERE n.article_id = <alias>.id)` である。保存期間の削除の条件もこれを使う。
- `hiddenByFilters(alias)` の式に、`NOT hasAnnotation(alias)` を足す。式は `filtered = 1 AND starred = 0 AND NOT hasAnnotation` になる。この条件を使う箇所は、そのまま注釈のある配信記事を隠さなくなる。記事の一覧、件数（未読数と記事の総数）、一括の既読、自動の要約と全文の取得を待つ記事、ほかに配信した購読フィード、検索である。
- `packages/core/src/db/filters.ts` でスターを見る4か所にも、`NOT hasAnnotation` を足す。1つ目はフィルターごとの件数（`HIDDEN_COUNT`）、2つ目は隠した配信記事の一覧が使う判定（`hiddenByFilter`）である。3つ目は保存の前の件数の確認（`previewFilter`）、4つ目は削除と無効化で戻った件数（`refreshFiltered` の戻り値）である。どれも「隠している件数」の数え方にそろえる（仕様 `feed-filters` の「隠している件数の提供」）。
- スターと注釈の条件を合わせた式を1つにまとめ、`articles.ts` と `filters.ts` の両方から使う。条件を足すたびに、数える箇所と隠す箇所がずれないようにする。

最後の注釈を消した配信記事は、フィルターに合えば再び隠れる。スターを外したときと同じである（仕様 `feed-filters` の「スターのある配信記事の保護」）。注釈の削除の要求は、記事の一覧と件数のキャッシュも古くする。

記事に `annotated` のような列を足して `filtered` の計算に含める案は採らない。保存期間の削除で採らなかった理由と同じく、注釈の追加と削除のたびに列を合わせ直すことになる。

### API

`packages/core/src/api.ts` にスキーマを足し、`apps/server/src/app.ts` にルートを足す。パスは既存のAPIと同じく `/api/v1` の下である。

| 操作 | パス | 本文と応答 |
|---|---|---|
| 注釈の一覧 | `GET /annotations?limit=&cursor=` | 注釈の並びと、続きの値。各注釈は、種類、識別子、記事の識別子、記事の由来、タイトル、訳したタイトル、`quote`、`note`、`createdAt` を持つ |
| ハイライトの追加 | `POST /articles/:id/highlights` | `{ quote, prefix, suffix, position, note? }` を受け、201でハイライトを返す |
| ハイライトのメモの変更 | `PATCH /highlights/:id` | `{ note: string \| null }` を受け、ハイライトを返す |
| ハイライトの削除 | `DELETE /highlights/:id` | 204を返す |
| 記事全体へのメモの保存 | `PUT /articles/:id/note` | `{ text }` を受け、メモを返す |
| 記事全体へのメモの削除 | `DELETE /articles/:id/note` | 204を返す。メモがなくても204にする |

記事の詳細（`GET /articles/:id`）に `annotations: { note, highlights }` を足す。`highlights` は付けた時刻の古い順である。記事の一覧の応答には足さない。一覧の行は注釈を使わず、応答が重くなるためである。

入力の上限は、`quote` とメモが5000文字、`prefix` と `suffix` が32文字、`position` が0以上の整数である。メモは前後の空白を除いて保存し、空になったハイライトのメモは値なしにする。記事全体へのメモが空白だけのときは400にする（仕様 `http-api` の「注釈の入力の拒否」）。
サーバーは、`quote` が本文に含まれるかを調べない。サーバーの持つ本文の文字列（`markdownToText`）は、画面が描いた文字列と細かく違うので、正しい選択を拒むおそれがある。

一覧の続きの値は、最近読んだ記事の一覧と同じく、最後の行の `(created_at, id)` から作る。
重複として記録した配信記事の注釈も一覧に返す（仕様 `http-api` の「注釈の一覧での隠れた記事」）。利用者が自分で付けた注釈は、記事の一覧の絞り込みより優先する。注釈のある配信記事はフィルターで隠れないので、一覧の問い合わせにフィルターの条件は付けない。

`docs/api.md` に、これらの操作を足す。

### アプリは、字句の文字を分ける処理に注釈の範囲を足す

`apps/mobile/src/reader/Markdown.tsx` が字句から `Text` を作る処理で、文字の字句をつなげた対象の文字列を先に作る。字句から描く処理は同期なので、Webのような描き直しは要らない。
訳のある記事では、原文のまとまりの字句だけをつなげる。`locateHighlights` の範囲で文字の字句を分け、地を `annotation-fill` にした入れ子の `Text` にする。

メモのあるハイライトは、最後の区間のあとにメモの印のアイコンを置き、ハイライトの `Text` に `onPress` を付ける。押すと、既存の `apps/mobile/src/ui/Sheet.tsx` でハイライトした文字列とメモを出す。メモのないハイライトは押しても何もしない。
読み上げの名前は、Webと同じく「ハイライト」「メモあり」にする。

記事全体へのメモは、本文の画面の本文の上に、`label-sm` の見出し「メモ」と本文を区画として出す。アプリには、注釈を作る操作、変える操作、消す操作を置かない。本文の長押しの操作にも足さない。

### 色は1色にし、線を引かない地の塗りで見分ける

`DESIGN.md` の `colors` に、`annotation-fill` と `annotation-fill-darkblue` を足す。メモの印のアイコンの色として `annotation` と `annotation-darkblue` も足す。「ダーク」の値は定義せず、「ダークブルー」の値を使う。意味を持つ色は暗い配色の間で変えないという規則に従う。

色以外の手がかりは、線の有無にする。語の色付けと検索の強調は、地の塗りに加えて2pxの実線の下線を引く。ハイライトは下線を引かず、地の塗りだけにする。重要度の印（`headline-mark`）は見出しにしか出ないので、本文の中で重ならない。
点線の下線で見分ける案は採らない。Androidの `Text` は下線の形を変えられないので、Webとアプリで手がかりがそろわない。

値は実装のときに、次を満たすように決める。grillingでも、値は実装のときに決めると確かめた。

- 色相は、重要度の黄色、検索の青みのある緑、語の色付けの4色（緑、紫、桃色、橙色）から離す。リンクの藍色の文字とも見分けられるようにする。候補は空色である。
- `on-surface` と `on-surface-muted` の文字と `annotation-fill` の地のコントラストが、3つの配色のそれぞれで4.5対1以上である。
- `annotation` と `surface` のコントラストが3対1以上である。
- 本文の中で文字を選んでいる間の色とも見分けられる。必要なら、本文の中の `::selection` の色を `DESIGN.md` に足して決める。

`DESIGN.md` の文章には、目立つ色の方針の例外にハイライトを足し、「Components」に `annotation-mark` を足す。色を足したあと、`pnpm run tokens` でCSSとアプリの定数を作り直す。

### 実装で決めた細部

- Webの本文の部品（`AnnotatedBody`）は、`apps/web/src/reader/Annotations.tsx` に置いた。選んだ範囲のメニュー、ハイライトのダイアログ、記事全体へのメモの区画も同じ場所にある。`ArticleView.tsx` はそれを使う。
- まとまりごとに範囲を分ける処理（`rangesByPart`）と、文字の並びを範囲で切る処理（`cutByRanges`）は、`packages/client/src/annotations.ts` に置いた。Webとアプリが同じ処理を使う。
- 検索の抜粋は、`excerptOf` を変えずに、メモを見る `searchExcerpt` を隣に足した。
- 選んだ範囲が既存のハイライトと重なるときは、メニューそのものを出さない。「メモを書く」もハイライトを作るので、1つの文字に2つのハイライトが重なるためである。
- 本文の中で文字を選んでいる間の色として、`DESIGN.md` に `text-selection` を足した。ブラウザーの既定の選択の色は青く、ハイライトの空色と見分けにくいためである。
- アプリのメモの印のアイコンは、最初から押せる部品にした。入れ子の `Text` の `onPress` だけでは、読み上げで押しにくいためである。

## Risks / Trade-offs

- WebとアプリのMarkdownの処理が違い、同じ本文から作る文字列がずれる。Webで付けたハイライトが、アプリでは見つからない区画に出る → 空白を除いて比べる。共通の例の本文を `packages/client` のテストの資料に置く。例は、段落、リスト、表、リンク、強調、コード、生のHTMLを含む。Webの木とアプリの字句から作った文字列が空白を除いて一致することを、両方のテストで確かめる。
- 短い文字列（1、2文字）のハイライトが、本文の書き換えのあとに別の箇所に付く → 前後の文字と位置で選ぶ。同じ語が多い本文では誤ることがあると受け入れる。見つからない区画へ回すより、近い箇所に出すほうが読み返しに役立つ。
- 注釈の多い記事で、記事の更新のたびに索引の文字列を作り直す手間が増える → 注釈は利用者が手で付けるもので、1つの記事に数十を超えることは少ない。100のハイライトを持つ記事の更新の時間を測るテストを置く。
- 古い版のサーバーは `sn_annotation_text` を登録しないので、移行のあとは記事を更新できない → 版を戻すときは、移行の前の写しに戻す。`docs` の更新の手順に、移行の前に写しを取ると書いてあるかを確かめる。なければ足す。
- ハイライトのある記事の初回の描画で、Webの描き直しが1回増える → ハイライトのない記事では増やさない。範囲が決まるまでの描画も、文字の位置は変わらないので、表示は動かない。
- Androidの入れ子の `Text` の `onPress` は、読み上げで押しにくい → エミュレーターの読み上げで、メモのあるハイライトに触れて開けることを確かめる。開けないときは、メモの印のアイコンを押せる部品にする。
- ハイライトの地の塗りと、語の色付けの地の塗りが重なると、重なった文字ではハイライトの色が見えない → 語の色付けの `mark` には下線があるので、重なった文字でも語の色付けだと分かる。ハイライトの範囲は普通、語より長いので、範囲の残りでハイライトだと分かる。

- 隠れているかの条件に `EXISTS` が加わり、記事の一覧と件数の問い合わせが重くなる → `annotations` の `article_id` の索引で引く。`filtered = 1 AND starred = 0` の行にだけ評価されるので、隠れていない記事では調べない。1万件の配信記事のうち千件が隠れている資料で、件数の要求の時間を変更の前後で測る。

## Migration Plan

1. 新しい版を入れる前に、データベースの写しを取る。
2. 起動のときに、新しい移行が `annotations` の表、`article_search_source`、トリガーを作り、`articles_search_update` を作り直す。注釈はまだないので、索引の埋め戻しは要らない。列 `filtered` も変えないので、隠れているかの計算のやり直しも要らない。
3. 戻すときは、写しのデータベースと古い版に戻す。移行のあとに付けた注釈は失われる。
