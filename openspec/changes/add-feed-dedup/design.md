# Design

## Context

動機はproposal.mdの「Why」を参照する。決定の出どころはgrilling.mdにある。

- 配信記事の保存は`packages/core/src/feeds/ingest.ts`の`storeItems`が、取得した文書ごとに1つのトランザクションで行う。購読フィードの取得は直列で、同時に2つの文書を保存することはない。
- 元のページのURLは、保存の前に`packages/core/src/fetch/url.ts`の`normalizeUrl`で正規化し、`article_refs`の先頭の行に入れている。sourcesの仕様の「URLの正規化」と同じ関数である。
- 一覧と件数の問い合わせは`packages/core/src/db/articles.ts`にある。ストップワードで隠した配信記事は、`HIDDEN`の条件で一覧、件数、一括の既読から外している。
- 全体設定は`settings`の表の1行で持ち、`packages/core/src/api.ts`のスキーマで検証する。設定ファイルの読み書きは`packages/core/src/settings-file.ts`にある。
- 配信記事と生成記事は同じ`articles`の表に入っている。生成記事だけの問い合わせには`GENERATED`の条件を付ける規則がある。

## Goals / Non-Goals

**Goals:**

- 保存のときに1度だけ、プログラムで重複を判定し、結果を記事の行に記録する。
- 一覧と件数の問い合わせは、記録された値を条件に足すだけで済ませる。

**Non-Goals:**

- よく似たタイトルでの判定（後回し。grilling.mdを参照）。
- 比べる期間や比べ方を利用者が選べるようにすること。期間は7日に固定する。
- 生成記事との比較と、生成記事の重複排除の変更。
- 機能を入れる前に保存した記事の判定し直し。

## Decisions

### 判定に使う値を列として保存する

`articles`に3つの列を足す。

- `dedup_url`:正規化したURL。`article_refs`の先頭の行と同じ値である。
- `dedup_title`:正規化したタイトル。正規化したあとで10文字未満ならNULLにする。
- `duplicate_of`:残した配信記事の識別子。重複でなければNULLにする。

`(dedup_url, created_at)`と`(dedup_title, created_at)`に索引を張る。`duplicate_of`にも、値のある行だけの索引を張る。削除のときのトリガー、既読の連動、ほかに配信した購読フィードの問い合わせが使う。

代わりの案は、比べるたびに`article_refs`とタイトルから値を作る方法だった。SQLiteには全角と半角をそろえる関数がなく、タイトルの正規化をSQLで書けない。そのため、保存のときにプログラムで作った値を列に持たせる。

機能を入れる前の配信記事は、`dedup_url`と`dedup_title`がNULLのままになる。比べる相手は2つの列のどちらかが一致する行なので、古い記事は自然に比べる相手から外れる。値を埋め直す処理は書かない。これが「機能を入れる前の記事の除外」の実装である。

### タイトルの正規化

`normalizeUrl`の隣に、タイトルの正規化の関数を置く。手順は次のとおりである。

1. UnicodeのNFKCで全角と半角をそろえる。
2. 小文字にする。
3. 空白（`\s`）と、句読点と記号（`\p{P}`、`\p{S}`）を取り除く。
4. 残った文字を符号位置で数え、10文字未満なら値なしを返す。

比べるのは、配信されたままのタイトルである。取得のときに訳したタイトルは使わない。

### 判定の手順

`storeItems`は、新しい項目を1件ずつ入れる。重複の除去が有効なら、入れる前に次の行を探す。

- `origin = 'feed'`で、保存しようとしている購読フィードとは別の`feed_id`の行
- `created_at`が保存の時刻の7日前以降の行
- `dedup_url`が同じか、`dedup_title`が同じ行

見つかった行は、それぞれ`coalesce(duplicate_of, id)`で残した記事に置き換える。そのうち`created_at`と識別子が最も小さいものを、`duplicate_of`に入れる。重複に一致した場合も、記録するのは残した記事である。

期間は保存の時刻（`created_at`）で測る。公開日時は、ない項目と未来の日時の項目があり、比べる基準に向かないからである。

ストップワードで隠した配信記事も、比べる相手に含める。判定は保存の時点で固まるので、あとでストップワードを消すと、隠していた記事と新しい記事の両方が一覧に並ぶ。この食い違いは小さいので受け入れる。

重複の除去が無効の間も、`dedup_url`と`dedup_title`は保存する。記録しないのは`duplicate_of`だけである。有効に戻したあとに届いた記事は、無効の間に保存した記事とも比べる。

書き換えられた項目は判定し直さない。ただし、`dedup_title`と`dedup_url`は新しい値に置き換え、あとから届く記事がいまのタイトルと比べられるようにする。2つの値がどちらもNULLの記事は置き換えない。機能を入れる前に保存した記事を、書き換えで比べる相手にしないためである。

### 比べる相手をほかの購読フィードに限る

同じ購読フィードの項目同士は比べない（round 3 Q7）。同じ購読フィードの中では、いまも項目の識別子で同じ記事を見分けている。識別子が違えば、配信元が別の記事として出したものとみなす。定期の告知のように、同じタイトルで別の記事を出す購読フィードもある。判定の手順の「別の`feed_id`の行」が、この決定の実装である。

### 隠した重複

この文書の「隠した重複」は、`duplicate_of`が入っていて、全体設定で重複の除去が有効な配信記事を指す。一覧と件数での隠し方、既読の連動、要約と翻訳の除外は、どれもこの条件で判定する。

`articles.ts`に、この条件を定数として置く。全体設定は1行なので、条件の中で`settings`の行を読む。

### 一覧と件数での隠し方

一覧と件数は、隠した重複の条件で判定する。

- 記事の一覧は、購読フィードの指定がなく、スターの指定（`starred=true`）もないときに、この条件の否定を足す。「未読」「すべて」、カテゴリ、カテゴリなしの一覧がこれに当たる。
- 件数は、いまの集計の行に、重複の未読数と総数を足して数える。全体の未読数、カテゴリの未読数と総数、カテゴリなしの未読数からは、その分を引く。購読フィードごとの未読数とスターの数は、重複を含めたままにする。
- `duplicate_of`を入れるのは配信記事だけなので、生成記事だけの問い合わせは変わらない。`GENERATED`の条件はそのまま付ける。

結果として、カテゴリの未読数は、その下の購読フィードの未読数の合計より小さくなることがある。grillingの決定どおりの振る舞いである。docs/api.mdに書いておく。

スターの一覧に重複を出すのは、grillingの決定が隠す先を「全体とカテゴリの一覧」に限ったからである。

重複の除去が無効の間は、記録済みの重複も隠さない（round 3 Q9）。一覧と件数には、ほかの配信記事と同じように含める。`duplicate_of`は消さないので、有効に戻すと、記録済みの重複はまた隠れる。記録を消さないのは、判定を保存のときに1度だけ行うからである。記録を消すと、無効の前の重複は、有効へ戻しても隠れない。

### 既読の連動

残した記事が既読になったとき、その記事を`duplicate_of`に持つ未読の行も既読にする（round 3 Q8）。既読になる経路は、記事ごとの既読の変更（`setArticleFlags`）と一括の既読（`markArticlesRead`）の2つである。どちらも、残した記事を既読にする更新と同じトランザクションで、重複を既読にする。

一括の既読が返す識別子には、連動して既読にした重複も含める。画面はこの識別子で表示を直し、取り消しの操作では、この識別子を名指しで未読に戻す。そのため、一括の既読を取り消すと、連動して既読にした重複も未読に戻る。

連動は、重複の除去が有効な間だけ行う。無効の間は、記録済みの重複も一覧に並ぶので、ほかの記事と同じに扱う。ストップワードで隠した重複は既読にしない。一括の既読がストップワードで隠した記事を既読にしないのと同じで、ストップワードを消したときに未読のまま戻す。

残した記事を未読に戻しても、重複は未読に戻さない。理由は2つある。

- 重複は全体の一覧に出ない。未読に戻しても全体の一覧には並ばず、購読フィードの未読数が増えるだけである。あとで全体の一覧から読むなら、残した記事だけを未読に戻せば足りる。
- 利用者が重複を購読フィードの一覧で読んでいたとき、その既読まで取り消してしまう。

連動は、残した記事から重複への一方向とする。round 3で決めたのは残した記事からの連動だけである。購読フィードの一覧で重複を既読にしても、残した記事は変えない。

### 隠した重複の要約と翻訳

隠した重複は、自動の要約と、取得のときのタイトルの翻訳の対象から外す（round 3 Q10）。同じ記事の要約と訳は残した記事が持つので、LLMの利用枠と翻訳の課金を、重複の分だけ使わずに済む。

外すためには、重複の判定が要約と翻訳より先に終わっている必要がある。順序は次のとおりである。

1. `storeItems`は、行を入れる前に重複を判定し、`duplicate_of`を同じ挿入で書く。
2. タイトルの翻訳は、`storeItems`が返す`titled`を、保存のあとで訳す。`titled`から隠した重複を外す。書き換えられた重複も外す。
3. 要約の処理は、要約を待つ記事を`WAITING_FOR_SUMMARY`の条件で問い合わせる。記録は挿入と同じトランザクションで書くので、要約の処理が次の記事を選ぶ時点で、記録はすでにある。

`WAITING_FOR_SUMMARY`の「未読である」の側に、「隠した重複でない」を足す。「開いて要約を頼んだ」の側（`auto_summary_requested_at`）と、`CAN_BE_SUMMARIZED`には足さない。こうすると、購読フィードの一覧から開いた重複は、画面がいまの記事ごとの要約の依頼をしたときに、要約の対象になる。

取得のときに訳さなかった重複のタイトルは、利用者が開いたとき、いまの規則のまま訳す。翻訳を有効にした時点で保存済みだった記事と同じ扱いである。

重複の除去を無効にすると、記録済みの重複は隠した重複でなくなる。未読で要約のない重複は、要約を待つ記事に戻る。要約は1件ずつ行い、1日の上限もあるので、利用枠を一度に使い切ることはない。

### 残した記事が消えたとき

`articles`の削除のあとに動くトリガーを足す。消えた行を`duplicate_of`に持つ行のうち、`created_at`と識別子が最も小さいものの`duplicate_of`をNULLにする。残りの行の`duplicate_of`は、その行の識別子に書き換える。

コードの削除の箇所（購読フィードの削除、保存期間での削除）ごとに書く案もあった。購読フィードの削除は外部キーの`ON DELETE CASCADE`で配信記事を消すので、トリガーなら漏れない。SQLiteは外部キーの連鎖で消した行にもトリガーを動かす。このことはテストで確かめる。

### APIの形

- 記事の詳細に、ほかに配信した購読フィードの配列を足す。要素は、重複の配信記事の識別子、購読フィードの識別子、購読フィードの名前である。保存した順に並べ、重複がなければ空の配列にする。項目の名前は`otherFeeds`とし、要素は`articleId`、`feedId`、`feedTitle`とする。フィルターで隠した重複は含めない。購読フィードの一覧に出ない記事へ移らないためである。
- 全体設定のスキーマに、重複の除去の真偽値`removeDuplicates`を足す。既定は`true`とする。設定ファイルでも同じ名前を使う。

### 画面

- Webの本文のペインは、`ArticleView.tsx`の元のページを開く操作の下に、名前を並べる。名前は購読フィードの一覧を開くリンクとし、その記事を選んだ状態のURLへ移る。URLの形は`apps/web/src/lib/paths.ts`の購読フィードの一覧のものを使う。
- 移った先の一覧は、既読の記事も含める（`?read=1`）。残した記事を開いた時点で重複も既読になっているので、未読だけの一覧では、開いた重複が一覧に並ばないからである。
- アプリの本文の画面は、同じ位置に名前を並べる。押すと、その記事の本文の画面を、購読フィードの一覧（既読を含める）を文脈として積む。戻る操作で元の記事に戻る。
- 色、大きさ、間隔は`DESIGN.md`の既存の値を使う。新しい値が要るときは、先に`DESIGN.md`へ足す。

## Risks / Trade-offs

- 10文字以上の決まり文句のタイトルは、別の記事なのに一致しうる。購読フィードの一覧には出るので、記事は失われない。全体設定で無効にできる。誤判定の様子を見て、よく似たタイトルの判定と合わせて見直す。
- カテゴリの未読数と、購読フィードの未読数の合計は合わなくなる。決定どおりの振る舞いである。docs/api.mdに書く。
- 残した記事を全体の一覧で読むと、ほかの購読フィードの同じ記事も既読になる。購読フィードの一覧でその購読フィードの記事を順に追う利用者には、読んでいない記事が既読に見える。同じ記事なので、round 3の決定どおりに受け入れる。
- 判定の問い合わせは、保存する項目ごとに1回増える。7日の範囲と索引で、読む行数を抑える。1回の取得で保存する項目の数には、すでに上限がある。
- 並行して作るほかの変更も、移行の番号を使う。移行の番号は、実装のときに空いている次の番号にする。

## Migration Plan

1. 移行で`articles`に3つの列と2つの索引を足し、`settings`に重複の除去の列を既定値1で足す。トリガーも同じ移行で作る。
2. 既存の配信記事の値は埋めない。更新の直後から、新しく保存する記事だけが判定の対象になる。
3. 元の版に戻すときは、足した列は読まれないだけで、記事の表示は元に戻る。トリガーは元の版でも動くが、`duplicate_of`を書き換えるだけで、元の版の振る舞いには影響しない。
