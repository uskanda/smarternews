# Design

## Context

動機は `proposal.md` の「Why」を見よ。ここでは、設計を決める今の作りだけを書く。

- トピックを追加するのは `apps/web/src/settings/CategoryPage.tsx` の `Topics` である。呼ぶ関数は `api.createTopic(categoryId, { text })` である。
- 追加のあとは `["topics", categoryId]` の問い合わせを読み直させ、知らせを出す。文言は `次の実行で解釈されます` で終わる。
- 解釈は次の実行で既存のタスクが行う。
- トピックの文章は、APIで前後の空白を除いて1〜2000文字に限られる。サーバーは同じ文章のトピックを拒まない。
- トピックの編集を開いたURLは `topicEditPath(categoryId, topicId)`（`/settings/categories/<id>#topic-<id>`）である。
- 名前の記事の一覧は `ReaderPage.tsx` の `view === "mention"` で、`/mentions/:articleId?name=…` の形である。本文のペインには元の記事が残り、`useArticle(articleId)` で読まれている。
- 本文の選択は `Annotations.tsx` の `AnnotatedBody` が見ている。`selectionIn` が、ハイライトの位置と、隠すフィルターを作れるかを返す。どちらもできないときはnullを返し、メニューを出さない。配信された内容の表示中で、かつ生成記事のときは、選択を見ていない。
- 左のペインのカテゴリは、`api.categories()` の並びのうち、有効なものを並べている（`buildNav`）。

## Goals / Non-Goals

**Goals:**

- 名前と選んだ文字列から、設定の画面と同じ検証と既定値でトピックを足す。
- ハイライトと隠すフィルターの操作の出し方は変えない。

**Non-Goals:**

- Androidアプリでの操作（grillingのQ6）。
- API、サーバー、coreの変更。トピックの解釈や実行の開始。

## Decisions

### ダイアログを1つの部品にする

`AddTopicDialog` を新しく作り、名前の記事の一覧と選択のメニューの両方から使う。
propsは4つで、下書き、開いている記事のカテゴリ、開閉の制御、開く操作のボタン（省略可）である。
見た目と開閉は `FormDialog` を使う。選択のメニューからは、メニューの外に開く操作のボタンがないので、`FormDialog` の `trigger` を省けるようにする。
ダイアログの中身は開くたびに作り直し、下書きと初期値を入れ直す。

カテゴリの選択肢は、種類がニュースかイベントのカテゴリを `api.categories()` の並びで出す。
初期値は、開いている記事の `categoryId` が選択肢にあればそれ、なければ有効なもののうち先頭、それもなければ選択肢の先頭である。
選択肢が1つもないときは、開く操作を出さない。判定は `useTopicCategories` にまとめ、2つの入口で共有する。

### 同じ文章の判定はWebで行う

選んだカテゴリのトピックを `useTopics` で読み、文章の欄と比べる。比べる前に、両方をNFKCで正規化し、小文字にし、前後の空白を除く。
一致すれば、ダイアログに知らせとリンクを出す。追加のボタンは止めない。
サーバーで拒む案もあった。設定の画面の追加の規則を変えることになるので、Webで知らせるだけにした。

### 追加のあと

`createTopic` が成功したら、`["topics", categoryId]` を読み直させ、ダイアログを閉じる。
知らせは設定の画面と同じ文言にし、「編集する」の操作で `topicEditPath` へ移る。
失敗したときは、ダイアログを閉じずに、設定の画面と同じく欄のエラーか全体のエラーを出す。

### 選択の判定にトピックの下書きを足す

`Selected` に `topicDraft: string | null` を足す。`selectionIn` は、次をすべて満たすとき、改行の並びを1つの空白に置き換えた値を返す。

- トピックを持てるカテゴリがある
- 選択の両端が、記事の要素（`scope`）の中にある
- 両端が、入力欄と表示しない要素の中にない
- 前後の空白を除いた値が1〜200文字である

ハイライト、隠すフィルター、トピックのどれもできないときだけnullを返す。
配信された内容の表示中で、かつ生成記事のときも、トピックのために選択を見る。

200文字は、隠すフィルターの値の上限と同じ長さである。それより長い選択は、トピックの種というより引用である。

下書きの文字列は、範囲の `toString` ではなく選択の `toString` から取る。範囲の文字列は段落の境目に改行を入れないが、選択の文字列はコピーと同じく改行を入れるので、境目が空白になる。
フォーカスが入力欄にあるときも、トピックの下書きを作らない。入力欄の中の選択は、範囲の両端が入力欄の外になり、ブラウザーによっては欄の文字列を選択の文字列として返すためである。

### 既存のテストの期待値

選択のメニューの操作を厳密に比べる既存のテストのうち、記事のカテゴリがトピックを持てるものは、「トピックを足す…」が加わる形に直す。
生成記事のタイトルの選択では、これまでメニューが出なかったが、トピックの操作だけが出る形に直す。
カテゴリのない記事のテストは、トピックの操作が出ないので、そのまま通る。

## Risks / Trade-offs

- 選択のメニューに出る操作が増え、ハイライトだけを使う人には1つ多く見える → カテゴリのない環境では出さない。並びはハイライトの操作の後ろにする。
- 同じ文章の判定は、読み込み済みのトピックに対して行う → ダイアログを開くと選んだカテゴリのトピックを読むので、ほかの画面で足したトピックも見える。
