# Design

## Context

Webの `apps/web/src/shell/order.tsx` とアプリの `apps/mobile/src/shell/order.tsx` に、同じ内容の `useNavMoves` がある。移動を先に `["categories"]` と `["feeds"]` のキャッシュへ書き、そのあとでAPIを呼ぶ。
移動は互いに待たずに送られ、応答は届いた順にキャッシュへ上書きされる。`["feeds"]` は60秒ごとに再取得され、移動の前に実行中の取得を取り消す処理はない。失敗のときは、その移動を始めた時点の並びを書き戻すため、あとの移動の表示も消える。
移動のAPIは移動後の一覧を返すだけで、版の番号を持たない。`packages/client` はReactにもTanStack Queryにも依存しない。

## Goals / Non-Goals

**Goals:**

- 続けた移動の応答が逆の順に届いても、最後の移動のあとの並びを残す。
- 移動の前に始まっていた一覧の再取得で、移動の前の並びに戻さない。
- 続けた移動の途中が失敗したら、保存済みの並びを表示し、知らせを1回だけ出す。

**Non-Goals:**

- サーバーの並びの版の番号と、別の端末からの変更との前後の比較
- APIとサーバーの変更

## Decisions

- `packages/client/src/order.ts` に、素のTypeScriptで `createMoveQueue` を足す。`push(send)` は送信の関数を列の最後に入れ、前の送信が終わってから次を呼ぶ。列が空になったとき、`onSettled` を1回だけ呼ぶ。送信が1つ失敗したら、待っている送信を呼ばずに捨て、`onFailed` を1回だけ呼ぶ。`busy()` は送信中か待ちがあるかを返す。
- カテゴリとフィードの移動は応答の種類が違う。列の各送信は `{ categories }` か `{ feeds }` のどちらかを返し、列は空になるまでの応答を種類ごとに最後のものだけ残す。`onSettled` には、残った応答をまとめて渡す。途中の応答は画面に出さないので、応答の逆転は表示に出ない。
- 購読フィードが別のカテゴリへ移ったかは、列が空になるまでの移動について覚えておき、`onSettled` で `counts` と `articles` を取り直す。
- フックは移動のたびに、まず `cancelQueries` で `["categories"]` と `["feeds"]` の実行中の取得を取り消し、それから楽観的な並びをキャッシュに書く。
- 列が動いている間に始まった取得も取り消す。フックは `getQueryCache().subscribe` で、2つのキーの取得が始まった（`fetchStatus` が `fetching` になった）ことを見て、列が `busy()` なら取り消す。60秒ごとの再取得は、列が空になったあとの次の回で動く。
- 失敗のときは、失敗した移動の前の並びを書き戻さない。2つの一覧を `invalidateQueries` で取り直し、知らせ「並べ替えられませんでした。もう一度試してください。」を1回だけ出す。待っている移動は捨てるので、表示はサーバーの並びに合う。
- 列はフックの中に `useRef` で1つだけ持つ。フックの呼び出し元は、Webもアプリも1か所である。
- Webのテストの土台に `hold` を足す。指定した要求について、サーバーには届けたうえで応答を止めておき、あとで流すか、失敗として返す。応答の逆転と、再取得の応答の遅れを再現するためである。

## Risks / Trade-offs

- 移動は1つずつ送るので、続けて素早く移動すると、保存の完了は遅れる。画面は楽観的に先に変わるので、操作の感じは変わらない。
- 列が動いている間は一覧の再取得を取り消すため、その間に別の端末で起きた変更は、列が空になってから反映される。
- 失敗のあと、取り直しが届くまでの短い間は、楽観的な並びが残る。
