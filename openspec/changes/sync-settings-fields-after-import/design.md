# Design

## Context

動機は `proposal.md` の「Why」を見よ。ここでは、設計を決める今の作りだけを書く。

- `ReaderInfo` と `GlobalSettings` は、設定の値を `useState` の初期値にだけ使う。
- 設定ファイルの読み込みは `settings` の問い合わせを無効にして取り直す。欄の保存は `setQueryData` で新しい値を入れる。どちらも欄を作り直さない。
- `CategoryPage.tsx` の `CategoryForm` は、`key` に値のJSONを入れて作り直す。この書き方では、保存のたびにも作り直しが起き、フォーカスが「保存する」のボタンから外れる。

## Goals / Non-Goals

**Goals:**

- 届いた設定の値を、読み手情報と全体設定の入力欄に表示する。
- 保存のあともフォーカスを「保存する」のボタンに残す。

**Non-Goals:**

- 基本の取得周期の欄（`FeedsPage.tsx` の `BaseInterval`）。grillingのQ3で範囲から外した。
- 読み込みの確認のダイアログの文の変更（grillingのQ2）。
- サーバー、API、Androidアプリの変更。

## Decisions

### 描画の中で、値の変化に合わせて入力値を置き換える

各欄は、最後に受け取った設定の値を `useState` で覚える。描画のときに届いた値が覚えた値と違えば、その場で入力値、覚えた値、入力の誤りの表示、保存の失敗の表示を新しくする。値が変わったときに状態を描画の中で直す、Reactの書き方である。

- `ReaderInfo` は `readerInfo` を比べる。
- `GlobalSettings` は、出力言語、タイムゾーン、検索の言語と地域、ダイジェストの時刻、すべて既読のあとに進む、重複を除く、更新が止まったとみなす日数の7項目を比べる。1項目でも違えば、すべての入力値を新しい値にする。

比べるのはその欄が表示する項目だけなので、カテゴリや読み手情報だけが変わっても、全体設定の入力は消えない。

`key` で作り直す案（grillingのQ1のB）は、保存のたびにフォーカスを失う。変えた項目だけを送る案（Q1のC）は、画面に古い値が残る。

### 自分の保存での置き換え

欄の保存で `setQueryData` が新しい値を入れたときも、置き換えが起きる。値は保存した入力と同じなので、表示は変わらない。

全体設定の保存のあとに、ダイジェストの時刻をサーバーの並べ方に揃える処理は残す。計画ではこの置き換えにまとめるとした。
しかし、並べ替えた結果と保存済みの値が同じときは、値が変わらず、置き換えも起きない。たとえば、保存済みが `06:30, 18:30` で、`18:30, 06:30` と入力したときである。

## Risks / Trade-offs

- 置き換えは保存していない入力を黙って捨てる → 読み込みの確認のダイアログがすでに上書きを知らせている（grillingのQ2）。別の端末の変更があとから届く場合も、届いた値を見せるほうが、古い値で上書きするより安全である。
