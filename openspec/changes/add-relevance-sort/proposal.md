# Proposal

## Why

記事の一覧は時刻の順にしか並ばず、関心に近い記事を上に出せない。Inoreaderから乗り換えるには、その「Magic sorting」に当たる並び順が要る（Issue #60）。
生成記事には重要度があるが、配信記事には関連度に当たる値がなく、2種類が混ざる「未読」やカテゴリの一覧では使える値がない。

## What Changes

- 並び順のメニュー（#48）に「関連度順」を足す。APIは `order=relevance`、表示の設定と設定ファイルは `sort: relevance` で表す。
- 関連度は0から1の値で、生成記事と配信記事で同じ尺度にそろえる。
  - 生成記事は重要度から決める（重要度1は0、重要度5は1）。
  - 配信記事は、購読フィードごとの利用者の行動（直近30日に保存した記事のうち、開いたかスターを付けた割合）と、見出しと要約が色付けの語に一致するかどうかを半分ずつ合わせる。
- 関連度順の並びの値は「記事の時刻＋関連度×48時間」とし、記事ごとに持って索引を張る。古い記事が上に居続けない。
- 語の一致は、配信記事の保存、見出しの翻訳の保存、色付けの語の変更のときに調べ直す。行動の値は、サーバーの起動直後と、そのあと1日に1回計算し直す。
- 関連度の値と理由は画面に出さない。LLMは呼ばない。

## Capabilities

### New Capabilities

なし。

### Modified Capabilities

- `http-api`: 記事の一覧で関連度順を受け付け、続きの取得の値と、並びが固定の一覧での拒否を定める。表示の設定に関連度順を足す。
- `settings`: 項目ごとの並び順に関連度順を保存し、設定ファイルで読み書きする。
- `web-reader`: 並び順のメニューに「関連度順」を足す。
- `mobile-reader`: 並び順のメニューに「関連度順」を足す。
- `term-highlights`: 色付けの語を、関連度順の並びの手がかりとしてサーバーでも照合する。記事の内容と一覧に含まれるかどうかは変えない。

## Impact

- データベース：移行032で、`articles` に `feed_score`、`term_match`、仮想の生成列 `rank_at` と、その索引を足す。`feeds` に `relevance_score` を足す。`list_views` を作り直して `relevance` を許す。
- `packages/core`：一覧の型と `listArticles` に関連度順を足す。関連度の計算の関数を足し、配信記事の保存、見出しの翻訳の保存、色付けの語の操作、スケジューラーから呼ぶ。設定ファイルは型の変更で `relevance` を読み書きする。
- `packages/client`：`mergeKept`、`targetFilter`。
- `apps/web`、`apps/mobile`：並び順のメニュー。
- 文書：`docs/api.md`、`README.md`、`README.ja.md`。
- LLMの利用枠は使わない。
