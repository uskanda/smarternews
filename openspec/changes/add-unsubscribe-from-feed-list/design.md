# Design

## Context

登録解除の確認は、左のペインのメニュー（`Shell.tsx`）と設定の画面（`FeedsPage.tsx`）に、別々に書かれている。
どちらも `ConfirmDialog` に、同じタイトル、`feedDeletionText`、`ScopedFiltersNote`、一時停止の案内、2つのボタンを渡す。
違うのは3点だけである。一時停止の案内の文面（左のペインは「設定の購読フィードで」、設定の画面は「編集で」）、解除のあとの移動、フォーカスを戻す先である。

「購読フィードの設定」のダイアログ（`FeedOptionsDialog.tsx`）について、#79（add-feed-from-category）で決めたことがある。
変えられるのは、自動の要約・翻訳・全文の取得の3つの切り替えだけである。

## Goals / Non-Goals

**Goals:**

- 確認の文面と解除の処理を1つの部品にまとめ、3か所の入口で同じものを使う。
- 既存の2か所の見た目、文面、振る舞いを変えない。

**Non-Goals:**

- Androidアプリでの登録解除。
- 削除のAPIやサーバーの変更。

## Decisions

### 共有の部品 `FeedDeletionDialog`

`apps/web/src/settings/FeedDeletionDialog.tsx` に、確認のダイアログと解除の処理をまとめる。
受け取るのは次の5つである。

- 対象の購読フィード（無いときは閉じている）
- 閉じたときに呼ぶ `onDone`
- 解除できたときに呼ぶ `onDeleted`
- フォーカスを戻す先の `returnFocus`
- 一時停止の案内で示す場所の `pauseWhere`

解除の処理は、`api.deleteFeed`、4つの問い合わせの読み直し、成功と失敗の知らせ、二重送信の防止を持つ。
入口ごとの違いはpropsで渡すので、各入口は開くかどうかの状態だけを持つ。

代わりに、`feedDeletionText` のような文面の関数だけを共有する案もあった。
確認の文面は複数の段落と部品から成り、解除の処理と知らせの文言も3か所で同じである。部品ごと共有すれば、3か所の食い違いは起きにくい。

### 設定のダイアログからの開き方

「登録を解除」のボタンは、設定のダイアログの下端の「ほかの設定」の並びに置く。
危険の色は確認の側の「登録を解除する」だけに付け、設定のダイアログのボタンは通常の見た目にする。
選ぶと、設定のダイアログを閉じてから確認のダイアログを開く。ダイアログを重ねないので、Escapeやフォーカスの扱いは単純になる。
保存していない切り替えは、「ほかの設定」へ移るときと同じく捨てる。
確認のダイアログの開閉の状態は、設定のダイアログの外（`FeedOptionsDialog` の中）で持つ。
取りやめたときは、フォーカスを「購読フィードの設定」のボタンへ戻す。解除できたときは「未読」の一覧を開く。

### #79の決定との関係

#79の「3つの切り替えだけ」は、このダイアログで変えられる設定についての決定である。
登録の解除は設定の変更ではなく、そのフィードへの操作であり、その外にある。ダイアログで保存する値は、引き続き3つの切り替えだけである。

## Risks / Trade-offs

- 共有化により、既存の2か所の振る舞いを変えてしまうおそれがある。左のペインと設定の画面の登録解除の既存のテストを、そのまま通すことで防ぐ。
- 設定のダイアログで切り替えたまま「登録を解除」を選ぶと、切り替えは捨てられる。解除すればフィードごと消え、取りやめても「ほかの設定」と同じ扱いなので、保存していないことは明らかである。
