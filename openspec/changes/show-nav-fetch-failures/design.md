# Design

## Context

動機は `proposal.md` のWhyに書いた。

- `useCategories`、`useFeeds`、`useCounts` は `useQuery` の問い合わせで、失敗しても自動では繰り返さない。
- 左のペインを組み立てる `useNavModels` は、3つの問い合わせの `.data` だけを読み、失敗の状態を捨てている。
- 本文側は、カテゴリや購読フィードが分かるまで `target` が `null` で、記事の一覧の問い合わせが動かない。そのため `読み込み中…` が出続ける。
- `refresh`（「読み直す」と `r` の処理）は、`["articles"]` と `["counts"]`、注釈の一覧では `["annotations"]` を無効にする。

## Goals / Non-Goals

**Goals:**

- 左のペインと本文側の両方で、何を読み込めなかったかと、再試行の手段を見せる。
- 「読み直す」で、失敗から立ち直れるようにする。

**Non-Goals:**

- 取り直しの一度の失敗を知らせること。前のデータで左のペインが使えている間は何も出さない。
- 自動の再試行の回数や間隔を変えること。

## Decisions

### 左のペインの1行は、失敗していてデータもないときだけ出す

問い合わせが `isError` で、`data` が `undefined` のときを失敗とする。60秒ごとの取り直しが一度失敗しても、前のデータがあれば出さない。
サーバーが一瞬止まるたびに行が出たり消えたりするのを避けるためである。Issueの症状も「カテゴリが出ない」ことである。

### 1行の文と部品

文は、失敗したものの名前を「カテゴリ」「購読フィード」「件数」の順に並べる。2つなら「と」でつなぎ、3つなら読点で区切る。例：「カテゴリと件数を読み込めませんでした」。
ボタンは1つで「もう一度試す」とし、失敗している問い合わせをまとめて `refetch` する。
`ErrorNotice` の余白の大きい囲みは左のペインには大きすぎるので、`role="alert"` の小さな部品 `NavFetchFailure` を `Shell.tsx` に置く。文字は `type-label-sm text-error`、ボタンは `size="sm"` である。

### 本文側は、開いている一覧が待つ問い合わせだけを見る

カテゴリの一覧のURLではカテゴリの問い合わせ、購読フィードの一覧のURLでは購読フィードの問い合わせを見る。それが失敗していてデータもないとき、`読み込み中…` の代わりに `ErrorNotice` を出し、再試行でその問い合わせを取り直す。
件数の失敗は本文側の表示に関わらないので、本文側には出さない。

### 「読み直す」は状態が `error` のものだけ取り直す

`refresh` は、`["categories"]` と `["feeds"]` を `predicate: query => query.state.status === "error"` で無効にする。データを持ったまま失敗しているものも、ついでに取り直す。
毎回取り直す案は採らない（grilling.md）。

### まだ反映していない変更の文を含める

web-shellの「キーボードでの一覧の再取得」と「失敗の表示」は、ほかの変更も書き換えている。
まだ本体の仕様に反映していない `notify-list-refresh`、`fix-annotation-list-refresh`、`unify-remaining-ui-wording` である。
どの順に反映しても文が抜けないように、この変更の差分にはそれらの文も含めた。

## Risks / Trade-offs

- 危うさ：前のデータを持ったまま失敗している間、左のペインは古い内容を何も言わずに見せる。
  - 手当て：60秒ごとの取り直しと「読み直す」で直る。古さは、本文の一覧の取得の失敗で別に伝わる
