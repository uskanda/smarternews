# Design

## Context

動機はproposal.mdの「Why」にある。決定はgrilling.mdにあり、ここでは作り方だけを決める。

- 生成記事と配信記事は、どちらも `articles` の表にある。配信記事の `body` はMarkdownに変換した内容で、`content_text` はその内容からMarkdownの記法とリンク先を除いた文字列である。フィルターの照合は `content_text` を使う。
- 生成記事の `body` は、LLMが書いたMarkdownである。リンクを含むことがある。
- フィルターの「含む」の照合は、`normalizeForMatch`（NFKCで正規化して小文字にする）を使う。検索も同じ規則にする（round 2 Q1）。
- 保存は `node:sqlite` で、版はSQLite 3.53である。FTS5の `trigram` が使える。`DatabaseSync` の `function()` で、JavaScriptの関数をSQLの関数として登録できる。
- `trigram` は3文字以上の語にしか索引を使えない。2文字以下の語の `LIKE` は、表の中身を順に読む。
- 記事の削除は3つの経路で起きる。生成記事の180日の削除、配信記事の保存期間の削除、購読フィードの削除による `ON DELETE CASCADE` である。
- Webの画面の経路は、react-routerのパスで表す（`/c/:slug`、`/f/:feedId` など）。1文字のキーは `useHotkeys` が扱い、入力欄にフォーカスがある間は無視する。
- 本文の描画は、Webが `react-markdown`、アプリが `marked` の字句を自前の部品で描く形である。
- `DESIGN.md` の `mark` と `mark-fill` は、重要度の印だけに使う決まりがある。

## Goals / Non-Goals

**Goals:**

- 記事の保存と更新の経路をどれも書き換えずに、検索の索引を記事の表に追従させる。
- 照合、抜粋、強調で、一致の判断を1つの規則にそろえる。
- 1文字と2文字の語を含む検索を、FTS5の索引と同じ問い合わせの中で扱う。

**Non-Goals:**

- 一致の度合いでの並べ替え（round 1 Q5）。
- 検索の保存（round 1 Q9）。
- 注釈（#55）の欄の照合。#55を実装するときに、索引に入れる文字列へ欄を足す。
- 配信記事の本文の訳（`article_translations`）の照合。決定で照合する欄に入っていない。

## Decisions

### D1：索引はFTS5の表を1つにし、正規化した文字列を入れる

`article_search` という仮想表を `fts5(text, tokenize = 'trigram')` で作る。`rowid` は記事の識別子と同じにする。
`text` には、照合する欄を改行でつないで、正規化した文字列を入れる。

- 欄は、タイトル、訳したタイトル、要約（`summary`）、自動の要約（`auto_summary`）、本文、読み手への影響（`impact`）、イベントの会場（`event_venue`）である。
- 本文は、配信記事なら `content_text` を使う。生成記事なら `body` からMarkdownの記法とリンク先を除いた文字列を使う。どちらもリンク先のURLを含まない。出典のURLは `article_refs` にあり、索引に入れない。
- 欄の間を改行で区切るため、欄の境をまたいだ語は一致しない。検索語は空白で区切るので、改行を含む語はない。
- 欄ごとの列にしない理由：照合は欄を区別しない。列を分けても、問い合わせと保守が増えるだけである。

正規化は `normalizeForMatch` と同じNFKCと小文字化である。`trigram` の `case_sensitive` の設定は全角と半角をそろえない。このため、文字列は正規化してから索引へ入れる。
ひらがなとカタカナはNFKCで変わらないため、区別したままになる（round 2 Q1）。`remove_diacritics` は使わない。

### D2：索引の追従はトリガーと、登録したSQLの関数で行う

データベースを開くときに、`<sn_search_text>` という決定的な関数を登録する。この関数は、記事の欄を受け取り、D1の文字列を返す。
記事の表に次のトリガーを置く。

- 挿入のあと：`article_search` に行を入れる。
- D1の欄のどれかを更新したあと：その行の `text` を作り直す。`UPDATE OF` には、D1の欄の列だけを並べる。
- 削除のあと：その行を消す。外部キーの `ON DELETE CASCADE` による削除でもトリガーは動く。

検討した別案：保存と更新をする各関数（`insertArticle`、`reviseArticle`、配信記事の保存と書き換え、自動の要約の保存、訳したタイトルの保存）から、索引を書き直す関数を呼ぶ。
この案は、SQLの外で正規化できる利点がある。一方で、記事の欄を書き換える経路が増えるたびに呼び忘れが起き、検索の結果が黙って古くなる。
トリガーなら、どの経路の書き込みも索引に届く。この利点を取る。

関数の登録は `openDatabase` で、移行より前に行う。移行の中の埋め戻しも、この関数を使うためである。

### D3：移行で表とトリガーを作り、既存の記事を埋め戻す

新しい移行のファイル（番号は実装のときに空いている次の番号）で、表、トリガー、埋め戻しを行う。
埋め戻しは、`<sn_search_text>` を使う `INSERT ... SELECT` の1文で、記事の表の全行を `article_search` へ入れる。保存済みの記事は、この移行で検索の対象になる。
同じ時期に別の変更も移行を足すため、番号の衝突は実装のときに解消する。

### D4：検索語の解釈

1. 検索語の前後の空白を除き、空なら入力の誤りにする。200文字を超えたら入力の誤りにする。
2. `normalizeForMatch` で正規化する。NFKCは全角の空白を半角の空白にするため、全角の空白も区切りになる。
3. 空白で分けて語の一覧にし、同じ語の重なりを除く。
4. 3文字以上の語（絵文字のようにUTF-16で2単位になる文字も1文字と数える）は、FTS5の句として照合する。語の中の `"` は2つ重ねて句の中に入れる。`OR`、`NOT`、`*` などは句の中では文字として扱われる。
5. 2文字以下の語は、`article_search.text LIKE ? ESCAPE '\'` で照合する。語の中の `%`、`_`、`\` は逃がす。

3文字以上の語が1つ以上あるときは、`article_search MATCH` に句を並べて、FTS5の暗黙のANDで照合する。2文字以下の語の `LIKE` は、同じ `WHERE` に並べる。
3文字以上の語がないときは、`MATCH` を使わず、`LIKE` だけで照合する。

### D5：問い合わせの形と並び

```sql
SELECT <一覧の列> FROM articles a
WHERE [a.id IN (SELECT rowid FROM article_search WHERE article_search MATCH ?)]
  [AND (SELECT s.text FROM article_search s WHERE s.rowid = a.id) LIKE ? ESCAPE '\' ...]
  AND NOT <hiddenByFilters(a)>
  [AND NOT <hiddenDuplicate(a)>]
  [AND a.category_id = ?] [AND a.feed_id = ?] [AND a.is_read = 0]
  [AND (a.updated_at < ? OR (a.updated_at = ? AND a.id < ?))]
ORDER BY a.updated_at DESC, a.id DESC LIMIT ?
```

- 由来の条件は付けない。生成記事と配信記事の両方が対象だからである（round 1 Q1）。AGENTS.mdの「生成記事だけを対象にする問い合わせ」には当たらない。
- 隠した配信記事の条件は、記事の一覧と同じ式（`hiddenByFilters`）を使う。スターのある配信記事は隠れないので、結果に出る。
- 隠した重複の条件（`hiddenDuplicate`）は、購読フィードを指定しないときだけ付ける。記事の一覧の、購読フィードを指定しない一覧と同じ扱いである。
- 記事の一覧の続きの取得は `pageArticles` が受け持つ。検索はこの関数に条件を渡す。
- 実装では、`MATCH` と `LIKE` を記事の表との結合でなく副問い合わせに置いた。条件の意味は結合と同じである。
- 続きの値は、記事の一覧と同じ（最終更新の時刻と識別子）にする。
- 終了したイベントの記事も結果に含める。記事の一覧が終了したイベントを除くのは、未読を読み終えるための既定である。検索は過去の記事を探す操作であり、既読を含める決定（round 1 Q6）と同じ考え方を取る。

### D6：APIの形

`GET /api/v1/search` を足す。パラメーターは `q`、`category`、`feed`、`unread`、`cursor`、`limit` である。`category` と `feed` は識別子で受ける。
応答は `{ items, nextCursor, terms }` とする。`items` の各記事は、記事の一覧の各記事と同じ項目に `excerpt`（文字列または `null`）を加える。`terms` は、D4で正規化した語の一覧である。
`/api/v1/articles` に `q` を足す案は採らない。終了したイベントの扱い、重要度の下限、抜粋の有無が一覧と違い、1つの操作の中で条件が分かれるからである。

### D7：一致の範囲を求める処理を1つにする

元の文字列と語の一覧から、一致した範囲を元の文字列の位置で返す関数を、Nodeの機能に依存しないモジュールとして `packages/core` に置く。`@smarternews/core/api` から使えるようにする。
置き場所は `packages/core/src/search/` である。`text.ts` は正規化、語の分け方、一致の範囲、抜粋を持ち、`@smarternews/core/api` から使える。`plain.ts` はMarkdownの記法を除く処理と索引の文字列を持ち、`marked` を使うのでサーバーだけが使う。
サーバーは抜粋を作るときに、WebとアプリはD9の強調に、同じ関数を使う。`normalizeForMatch` もこのモジュールへ移し、フィルターの処理はそこから使う。

元の文字列を、基本の文字と、それに続く結合文字（`\p{M}`）と半角の濁点と半濁点（U+FF9E、U+FF9F）のまとまりに分ける。まとまりごとにNFKCと小文字化をして、正規化した文字列と、元の位置への対応表を作る。
まとまりごとに正規化するのは、半角のカタカナの「カ」と半角の濁点の並びのように、文字ごとに正規化すると結果が変わる並びを1つにするためである。
1つのまとまりが複数の文字に広がるとき（「㍿」が4文字になるなど）、その中の一部に一致しても、まとまり全体を一致の範囲にする。

### D8：抜粋の作り方

結果の各記事について、要約、自動の要約、本文（D1と同じMarkdownの記法のない文字列）、読み手への影響、イベントの会場の順に、D7の関数で最初の一致を探す。
見つかったら、その位置の前に約40文字、全体で約120文字を切り出す。切った端には「…」を付ける。どの欄にも一致しなければ `null` にする。
抜粋は、結果のページの記事（多くても `limit` 件）についてだけ作る。本文の列は一覧の問い合わせに含めないので、ページの記事の識別子で別に読む。

### D9：強調の表示

- Web：一覧の見出し（訳したタイトルを出すときはその文字列）と抜粋を、D7の範囲で `<mark>` に分けて描く。本文は `react-markdown` にrehypeのプラグインを足し、文字の部分の一致を `<mark>` に包む。コードの中も対象にする。
- Web：抜粋は2行まで出す。抜粋は一致した語の前に約40文字を含むので、1行では語が幅から外れることがあるからである。
- アプリ：一覧の見出しと抜粋は、`Text` の入れ子で強調する。本文は、`marked` の字句から文字を描く箇所で、同じ範囲を強調の `Text` にする。
- 強調する語は、APIの応答の `terms` を使う。画面の側で語を正規化し直さない。
- 見た目は、`DESIGN.md` に新しい色（たとえば `search-match`）を足して決める。`mark` と `mark-fill` は重要度の印だけに使う決まりなので使わない。色のほかに下線を付け、重要度5の見出しの塗りと重なっても見分けられるようにする。語の色付け（#54）が足す色とも分ける。#54も同じ時期に `DESIGN.md` へ色を足すので、実装のときに並べて確かめる。

### D10：Webの経路

- 結果の画面は `/search` と `/search/:articleId` にし、検索語と絞り込みはパラメーターに置く。`q`、`category`（カテゴリのslug）、`feed`、`unread=true` である。
- 結果の画面の中の操作（絞り込み、未読だけの切り替え、記事を開く）は、パラメーターを保ったまま経路を変える。再読み込みと戻る操作で同じ結果が出る（round 2 Q7）。
- `ReaderPage` に `view="search"` を足し、記事の一覧と同じ部品で描く。一括の既読のボタンは出さない（round 2 Q5）。一括の既読を呼ぶキーがほかの変更（#53）で足されても、この画面では何もしない。
- 検索欄は `Shell` の左のペインの上端に置く。`useHotkeys` に `/` を足し、検索欄にフォーカスを移す。`/` のキーの既定の動き（ブラウザーのページ内検索）は止める。`Shell.tsx` の `KEYS` に `["/", "検索欄へ移る"]` を足す。

### D11：アプリの経路

- 結果の画面は `app/(main)/search.tsx` に置き、検索語と絞り込みは経路のパラメーターで渡す。
- 本文を払って隣の記事へ移る操作が結果の並びに従うよう、結果の一覧を、いまの一覧と同じく読む順の情報（`session`）に渡す。本文の画面は、検索から開いたときだけ `terms` を受け取って強調する。
- 検索欄は `DrawerContent` の上端に置く。確定のキーは `returnKeyType="search"` にする。

## Risks / Trade-offs

- `sqlite3` のコマンドなど、関数を登録しない接続から記事の表を書き換えると、トリガーが失敗する → 読むだけなら影響はない。記事の表を手で書き換える運用は想定しない。`docs/` の運用の説明に、このことを書く。
- 記事の表を作り直す移行（`DROP TABLE` と `RENAME`）を将来足すと、トリガーが消える → 移行をすべて当てたあとにトリガーと索引の行数を確かめるテストを置く。作り直す移行には、トリガーの作り直しを含める。
- 2文字以下の語だけの検索は、索引を使えずに全件を読む。配信記事の内容は最大10万文字あるため、件数が増えると遅くなる → 並びの索引で新しい順に読み、`limit` 件に達した時点で止まる。まれな短い語だけが全件を読む。5万件の合成データで時間を測り、遅すぎるときは結果を報告して対処を決める。
- 索引の分だけデータベースが大きくなる。`trigram` の索引は元の文字列の数倍になる → 記事は保存期間で消え、索引の行もトリガーで消える。移行のあとの大きさを、合成データで測っておく。
- D7のまとまりの正規化と、索引の文字列全体の正規化が、まれな並びで違う結果になる → そのときは強調と抜粋の位置がずれるだけで、検索の結果は索引の照合で決まる。抜粋が見つからないときは `null` にして、いつもの要約を出す。
- 全文の照合は `trigram` の部分一致なので、英語の短い語が別の単語の一部に一致する。たとえば `ai` は `said` に一致する → 決定どおりの動きとして受け入れる（round 1 Q3）。語の境界での照合は、必要になってから検討する。

## Migration Plan

1. 移行で `article_search`、トリガー、埋め戻しを入れる。埋め戻しは移行の一部として1回だけ走る。
2. 戻すときは、`article_search` とトリガーを消すだけでよい。記事の表には手を入れない。
3. 版を戻したサーバーは、`article_search` を使わない。残った表とトリガーが記事の書き込みを妨げないよう、古い版に戻すときは表とトリガーを消してから起動する。
