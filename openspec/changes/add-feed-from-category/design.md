# Design

## Context

購読フィードの追加の欄は、`apps/web/src/settings/FeedsPage.tsx` の中の `AddFeed` にある。
URLの探索、複数のフィードからの選択、Webページの購読（セレクターの候補と手入力）、3つの切り替えと説明、失敗の文言、成功の知らせと再取得までを、この1つの部品が持つ。
購読フィードの編集の欄は、同じファイルの `EditFeed` にある。自動の要約、翻訳、全文の取得の切り替えと説明は、`AutoSummarize`、`Translate`、`FetchFullContent` の3つの部品で、追加と編集が共有している。
購読フィードの更新のAPI（`api.updateFeed`）は、送った項目だけを変える。
記事の一覧の上部は `apps/web/src/reader/ReaderPage.tsx` の `header` で、いまは「すべて既読にする」と「更新」を置いている。イベントのカテゴリは `EventList` が描くので、この `header` を通らない。

1文字のキーの操作は `apps/web/src/lib/keys.ts` が文書全体で受ける。入力欄の中のキーは無視するが、ダイアログの中のボタンにフォーカスがあるときのキーは、背後の一覧に届く。
狭い画面の左のペインも、Radixのダイアログで開く。そこでも、項目を移動するキーは働かなければならない。

## Goals / Non-Goals

**Goals:**

- 設定の画面とダイアログで、追加の入力と振る舞いを1つの実装にまとめる。
- 3つの切り替えの説明を、設定の画面とダイアログで1つの実装にまとめる。
- ダイアログを閉じたら、次に開いたときは入力していない状態から始める。

**Non-Goals:**

- 購読フィードのメニュー（左のペインの右クリック）からの追加。会話で入口を記事の一覧の上部に決めた。
- Androidアプリでの追加。アプリには追加の機能そのものがない。
- 追加したフィードの一覧へ移ること。読んでいた一覧のままにする。
- 購読フィードの設定のダイアログで、名前、カテゴリ、取得周期、一時停止、セレクターを変えること。会話で3つの切り替えに絞った。

## Decisions

### 追加の欄を部品に切り出す

`AddFeed` の中身を `<apps/web/src/settings/AddFeedForm.tsx>` の `<AddFeedForm>` に移す。
受け取るのは、カテゴリの一覧、最初に選ぶカテゴリ、登録できたときの通知である。
設定の画面は、これまでの `section` と見出しの中に `<AddFeedForm>` を置く。ダイアログは、ダイアログの中に置く。
要素のidは `useId` で作る。いまは固定の文字列で、同じ画面に2つ置くと衝突する。

別案は、設定の画面へ移ってカテゴリを選んだ状態にする方法で、会話で取りやめた。追加の欄を複製する案は、失敗の文言とWebページの購読の振る舞いが2か所に分かれるので採らない。

### ダイアログ

`<apps/web/src/reader/AddFeedDialog.tsx>` に、Radixのダイアログで作る。見た目はキー操作の一覧のダイアログにそろえ、`max-h-[90dvh]` で縦にはみ出す分をダイアログの中でスクロールさせる。Webページの候補を出すと縦に長くなるからである。
見出しは「購読フィードを追加」とし、閉じるボタンを下に置く。
開いたときは、Radixがダイアログの中の最初の入力欄、つまりURLの入力欄にフォーカスを移す。閉じたときは、Radixが開いたボタンへフォーカスを戻す。

追加の欄はダイアログの内容の中に置くので、閉じると部品ごと外れ、入力の状態は消える。次に開いたときは、初期の値から始まる。

登録できたときは、`<AddFeedForm>` が知らせと再取得（`feeds`、`counts`、`articles`）をこれまでどおり行い、ダイアログは通知を受けて閉じる。左のペインの購読フィードは、`feeds` の再取得で加わる。

### 3つの切り替えを部品として出す

`AutoSummarize`、`Translate`、`FetchFullContent` の3つを、`FeedsPage.tsx` から `<FeedSwitches.tsx>` に移す。設定の画面と購読フィードの設定のダイアログは、どちらもこの部品を使う。
説明の文言を2か所に書くと、片方だけが古くなるからである。

### 購読フィードの設定のダイアログ

`<apps/web/src/reader/FeedOptionsDialog.tsx>` に作る。見出しは「購読フィードの設定」とし、下に「保存する」と「やめる」を置く。
3つの値は、開いたときの購読フィードの値から始め、ダイアログの中だけで持つ。保存を選んだとき、`api.updateFeed` に3つの項目だけを送る。名前やカテゴリを送らないので、ほかの設定は変わらない。
保存できたら、`feeds`、`counts`、`articles` を再取得し、知らせを出して閉じる。失敗したら、`ErrorNotice` で理由を出し、ダイアログを開いたままにする。
入力の欄は追加のダイアログと同じく、ダイアログの内容の中に置く。閉じれば値は捨てられ、次に開いたときは購読フィードの値から始まる。

別案は、一覧の上部に切り替えを並べ、切り替えた瞬間に保存する形で、会話で取りやめた。一覧の上部には、切り替えごとの説明を置く場所がない。要約と翻訳は外部のサービスを使うので、保存の前に説明を読めるようにする。

### ダイアログの外枠

追加と購読フィードの設定の2つのダイアログは、外枠を `<apps/web/src/ui/FormDialog.tsx>` の1つの部品にまとめる。見出し、`data-hotkeys="off"`、縦のスクロールをこの部品が持つ。

### ボタンを出す条件

「購読フィードを追加」は、`view === "category"` で、カテゴリの種別が `news` のときだけ出す。カテゴリの「AI生成」の一覧は `category-generated` なので出ない。イベントのカテゴリは `EventList` が描くので出ない。
「購読フィードの設定」は、`view === "feed"` で、購読フィードが分かったときだけ出す。
どちらも、2行目の切り替えと並び順の後ろに置く。「すべて既読にする」と「更新」の行に3つ目のボタンを足すと、一覧の名前が1文字まで縮み、読めなくなった。

### ダイアログの中のキー

キーを止めるダイアログの内容には `data-hotkeys="off"` を付ける。`keys.ts` は、キーの発生元がその要素の中にあるとき、何もしない。
対象は、狭い画面の左のペインを除く、すべてのダイアログである。購読フィードの追加、購読フィードの設定、キー操作の一覧、確認のダイアログ（`ConfirmDialog`）に付ける。
隠すフィルターを作る、ハイライト、メモを書いてハイライトする、アプリを接続する、の4つのダイアログにも付ける。
ダイアログを名前で並べる要件にすると、ダイアログを足すたびに要件を直す必要があり、漏れる。そのため、要件は除く1つだけを名前で挙げる。
`role="dialog"` で一律に止める案は採らない。狭い画面の左のペインもダイアログとして開き、項目を移動するキーを使うからである。

## Risks / Trade-offs

- ［切り出したあと、設定の画面の追加のテストが通らなくなる］→ 設定の画面の追加のテストを書き換えずに通す。テストはラベルで要素を探しているので、idを変えても影響しない。
- ［Webページの候補を求めている途中でダイアログを閉じる］→ LLMの呼び出しはサーバーで終わるまで進むが、何も登録しない。候補の結果は捨てる。1回の呼び出しは、これまでも利用者が選んだときにだけ起きる。
- ［購読フィードの設定のダイアログを開いている間に、ほかの画面で同じ購読フィードを変える］→ 保存すると3つの項目はダイアログの値で上書きされる。ほかの項目は送らないので変わらない。利用者は1人なので、これで足りる。
- ［新しく足したダイアログに `data-hotkeys="off"` を付け忘れる］→ 要件はすべてのダイアログを対象にしているので、付け忘れは要件に反する。ダイアログを足すときは、キーが背後に届かないことをテストで確かめる。
- ［キー操作の一覧、確認、隠すフィルター、ハイライト、アプリの接続のダイアログでも、キーが背後に届かなくなる］→ 背後の記事を動かしたりスターを付けたりしないほうが正しいので、仕様に足して受け入れる。
