# Design

## Context

ストップワードは `packages/core/src/db/stop-words.ts` にある。照合の形への変換 `normalizeForMatch`（NFKCで正規化し、小文字にする）もこのファイルにあり、設定ファイルの読み込みも使っている。
このファイルはデータベースに依存するので、ブラウザーとアプリからは読み込めない。`packages/core` の入口 `.` もNodeの機能を含む。ブラウザーとアプリが読めるのは、型とスキーマだけの `@smarternews/core/api` である。
`packages/client` はWebとアプリが共有する処理を置く場所で、`@smarternews/core` に依存してよい。画面の部品とNodeの機能には依存させない。

記事の文字は、どこでもMarkdownとして描いている。

- Webは `apps/web/src/reader/Markdown.tsx` で `react-markdown` を使う。生のHTMLは解釈せず、リンクと画像のURLを絞っている。本文、訳のまとまり、原文のまとまりは、この部品で描く。配信記事の要約は、段落の文字として描く。
- アプリは `apps/mobile/src/reader/Markdown.tsx` で、`marked` の字句を自前の `Text` に描く。
- 一覧の行は、見出し（訳があれば訳したタイトル）と `summary`（生成記事の要約の1行、配信記事の内容の冒頭）を、ただの文字として描く。

`pnpm run tokens`（`scripts/design-tokens.ts`）は、`DESIGN.md` の色の値を書き出す。書き出す先は、WebのCSS（`apps/web/src/styles/tokens.css`）とアプリの定数（`apps/mobile/src/theme/tokens.ts`）である。名前の末尾が `-darkblue` の値は「ダークブルー」、`-dark` の値は「ダーク」の値になる。「ダーク」の値がない色は「ダークブルー」の値を使う。
`DESIGN.md` は、目立つ色を重要度の黄色の印（`mark`）だけにする方針を書いている。リンクは `primary`（藍色）の文字と下線である。

## Goals / Non-Goals

**Goals:**

- ストップワードと同じ照合の形を、サーバー、Web、アプリが1つの関数から使う。
- 色付けを、描いたあとの文字の上で行い、Markdownの構造、リンク、HTMLを文字として出す安全の扱いを変えない。
- 一覧と本文の表示を、色付けのためにAPIの往復で遅らせない。

**Non-Goals:**

- まとまりに一致した記事の絞り込み（grillingで後回し）。
- 一致の数による並べ替え。関連度での並び（#60）が、あとで照合の関数を使うことはありうる。
- アプリでの語とまとまりの編集。アプリの設定の画面にはストップワードの区画もないので、編集はWebの画面だけで行う。
- 読み手への影響、出典の題名、イベントの一覧の行の色付け。決定は、見出し、抜粋、本文、訳、要約を挙げている（未決の問いの2を見よ）。
- 書式の境目をまたぐ一致。たとえば語の前半だけが太字の箇所は、文字のつながりが分かれるので一致しない。

## Decisions

### 照合はブラウザーとアプリで行い、サーバーは語を保存して返すだけにする

一覧の行と本文を描くとき、画面とアプリが手元の文字に語を当てる。
サーバーで一致した範囲を求めて返す案は採らない。範囲は、Markdownを描いたあとの文字の位置で求めないと使えない。訳、原文、要約は別々の応答で届くので、範囲の受け渡しも増える。
語を変えたとき、保存済みの記事に何かを書き戻す必要もない。仕様 `term-highlights` の「記事を変えない色付け」を、この形で満たす。

一覧の行の印も、行に出す文字（見出しと抜粋）から画面とアプリが求める。本文まで照合する案は、未決の問いの1に残す。

### 照合の形への変換を、ブラウザーでも読める場所へ移す

`normalizeForMatch` を、依存のない新しいファイル `packages/core/src/text-match.ts` へ移す。`packages/core/package.json` の `exports` に `./match` を足して公開する。
`stop-words.ts` と `settings-file.ts` は、ここから読み込む。ストップワードの振る舞いは変えない。
変換を `packages/client` に書き写す案は採らない。2つの実装がずれると、ストップワードで隠れる語と色付けされる語が食い違う。

### 一致した範囲は、元の文字の単位に戻して求める

NFKCは文字の数を変える。半角のカタカナと半角の濁点は1文字にまとまり、「㍿」は4文字に開く。照合の形の上の位置は、そのままでは元の文字の位置に使えない。
`packages/client/src/highlight.ts` で次のように求める。

1. 元の文字列を単位に分ける。単位は、1つの文字と、そのあとに続く結合文字（`\p{M}`）と半角の濁点と半濁点（U+FF9E、U+FF9F）である。
2. 単位ごとに照合の形にして、つなげる。照合の形の各文字が、どの単位から来たかを控える。
3. 照合の形の上で、語の出現をすべて探す。重なる出現も探す。
4. 出現の最初と最後の文字が属する単位を求め、その単位の全体を元の文字の範囲とする。

単位ごとに変換するので、文字列の全体を一度に変換するストップワードとは、ごくまれな並び（結合を伴う字母の連なり）で結果が変わりうる。仕様の例と、半角のカタカナ、全角の英数字、合字では同じ結果になることをテストで確かめる。

### 重なる一致は、文字ごとに最も上のまとまりを選んで解く

すべての出現を求めたあと、元の文字ごとに、その文字を覆う出現のうち並び順の最も上にあるまとまりを持ち主にする。持ち主の同じ文字が続く区間を、1つの色付けの区間にする。
語の長さや出現の順で決める案は採らない。決定は、設定の画面で上に並ぶまとまりを優先するとしている。
同じまとまりの語どうしの重なりは、区間を合わせるだけになる。

`packages/client` は、まとまりの一覧を受け取って、次の2つを返す関数を公開する。

- 文字列を、色付けしない区間と、まとまりごとの色付けの区間に分けたもの
- 複数の文字列（行の見出しと抜粋）が一致したまとまりの、並び順の一覧

語を前もって照合の形にしておき、同じ文字列の結果は覚えておく。

### Webは、Markdownを描いたあとの木の文字の節にだけ色を付ける

`Markdown.tsx` に、`react-markdown` の `rehypePlugins` として小さな処理を足す。HTMLの木をたどり、文字の節だけを区間に分けて、`mark` の要素で包む。要素には、まとまりの色の名前を `data-term` の属性として付ける。
属性（`href`、`src`）は文字の節ではないので照合しない。仕様の「文字だけの照合」をこの形で満たす。生のHTMLは、いまと同じく文字のままである。
Markdownの文字列に印を差し込む案は採らない。URLやコードの中に差し込むと、リンクやコードのまとまりとして解析されなくなる。
木をたどる処理は自前で書き、依存を増やさない。

一覧の行、本文の見出し、原文のタイトル、要約の区画の段落は、ただの文字なので、同じ区間を `mark` で包む小さな部品で描く。
語のまとまりは、APIから取得してReact Queryのキャッシュに置き、部品は文脈から読む。編集の画面で変えたときは、このキャッシュを無効にする。仕様の「語の変更の反映」をこの形で満たす。

### アプリは、Markdownの字句の文字を入れ子の `Text` に分ける

`apps/mobile/src/reader/Markdown.tsx` で、字句の文字（`text` と `codespan`）を描くところで区間に分ける。色付けの区間は、地をまとまりの色、下線を引いた入れ子の `Text` にする。
リンクの字句は、いまと同じ押す操作を持たせたまま、中の文字だけを分ける。
Androidの `Text` は下線の色を指定できない。下線は文字の色で引き、まとまりの色は地で示す。
語のまとまりは、一覧の取得と同じ仕組みで取得する。一覧を引いて更新したときに取得し直す。

### 色は、名前を固定した4色にし、値は `DESIGN.md` に置く

APIと設定ファイルでは、色を `green`、`purple`、`pink`、`orange` の名前で表す。画面では「緑」「紫」「桃色」「橙色」と書く。
色の値を保存する案は採らない。値は配色ごとに変わる。利用者が自由に選ぶと、暗い配色で文字が読めなくなる。

黄色と青は使わない。黄色は重要度の印（`mark`、`mark-fill`）と見分けられなくなる。青は、リンクの藍色の文字と下線に見えてしまう。

`DESIGN.md` の `colors` に、4色のそれぞれで2つの値を足す。

- `term-<色>-fill`: 一致した箇所と、一覧の行の印の地。文字は `on-surface` のままにする。
- `term-<色>`: 下線と、一覧の行の印の左の線。

それぞれに `-darkblue` の値も足す。「ダーク」の値は定義せず、「ダークブルー」の値を使う。`mark` や `warning` と同じく、意味を持つ色は暗い配色の間で変えないという規則に従う。
値は、次を満たすように決める。

- `on-surface` の文字と `term-<色>-fill` の地のコントラストが、3つの配色のそれぞれで4.5対1以上である。
- `term-<色>` と `surface` のコントラストが3対1以上である。
- 4つの `term-<色>-fill` は、選択中の行の地（`selected`）や重要度の地（`mark-fill`）と見分けられる。

`DESIGN.md` の文章も直す。

- 概要の「目立つ色は重要度の黄色の印だけ」に、利用者が選んだ語の色付けを例外として書き足す。
- 「Components」に、色付けの区間（地、下線の太さと位置）と、一覧の行の印（`label-sm`、角は `sm`、左に `term-<色>` の線、地は `term-<色>-fill`）を足す。
- 「Layout」の一覧の行の補足の並びに、まとまりの印を最後に置くことを足す。

色を足したあと、`pnpm run tokens` でCSSとアプリの定数を作り直す。画面のコードには色の値を直接書かない。

### 色以外の手がかりは、下線と名前で示す

色付けした箇所には、`term-<色>` の色で2pxの下線を引く。リンクの下線より太くし、文字から離して引く。
一覧の行の印は、まとまりの名前を文字で出す。読み上げは、この文字を行の内容に続けて読む。
本文の `mark` の要素には、名前を読み上げさせない。本文の途中で名前を読み上げると、文章が聞き取りにくくなる。どのまとまりに一致したかは、一覧の印で分かる。

### 一覧の行の印は、補足の行の右端に置く

印は、補足の行（カテゴリ、時刻、出典の件数、印）の最後に、並び順のとおりに並べる。幅が足りないときは、まとまりの名前の末尾を省略する。
見出しの行に置く案は採らない。見出しの長さが行ごとに変わり、印の位置がそろわない。

### 語とまとまりの保存

移行 `<番号>_term_highlights.sql` で2つの表を足す。

- `term_groups`: `id`、`name`（一意）、`color`、`position`、`created_at`
- `highlight_terms`: `id`、`group_id`（`term_groups` の削除に連動して消える）、`text`、`normalized`、`created_at`。`(group_id, normalized)` を一意にする

並び順は、カテゴリと同じく `position` の整数で持ち、動かす操作もカテゴリと同じ形にする。
語の文字は、ストップワードと同じく、前後の空白を除いて1文字から100文字までとする。まとまりの名前も1文字から100文字までとする。
語とまとまりの数に上限は設けない。数十の語で照合が遅くならないことを、テストの中で確かめる。

### API

ストップワードとカテゴリの操作にそろえる。

- `GET /api/v1/term-groups`: 並び順のとおりに、`id`、`name`、`color`、`terms`（`id` と `text`）を返す
- `POST /api/v1/term-groups`: `name` と、省略できる `color`（既定は `green`）
- `PATCH /api/v1/term-groups/:id`: `name` と `color`
- `DELETE /api/v1/term-groups/:id`
- `POST /api/v1/term-groups/:id/move`: `before`（前に置くまとまりの `id`。末尾は `null`）。動かしたあとの一覧を返す
- `POST /api/v1/term-groups/:id/terms`: `text`。語を足したまとまりを返す
- `DELETE /api/v1/term-groups/:id/terms/:termId`

同じ名前と同じ語は、ストップワードと同じく競合（409）として返す。スキーマは `packages/core/src/api.ts` に、色の名前の列挙とともに置く。

### 設定ファイル

最上位に `termGroups` を足す。まとまりがないときは書かない。

```yaml
termGroups:
  - name: 例のまとまり
    color: green
    terms:
      - 例の語
```

読み込みは、名前でまとまりを突き合わせる。色は上書きし、語は足すだけにする。並び順は、カテゴリと同じく、ファイルにあるまとまりをファイルの順に、ないまとまりをそのあとに置く。
読み込みの結果に、作ったまとまりの数と足した語の数を加え、Webの画面に表示する。
書き出しと読み込みの説明の文（設定の画面）に、語の色付けを書き足す。

### 設定の画面

設定の画面の「購読フィード」の区画のすぐあとに、「語の色付け」の区画を置く。ストップワードは「購読フィード」の区画の中のリンクなので、その隣にあたる位置である。
色付けは生成記事にも及ぶので、「購読フィード」の区画の中には置かない。
区画から、新しい画面 `/settings/term-highlights` を開く。画面の形は `StopWordsPage.tsx` にそろえる。
並べ替えは、まとまりごとの「上へ」「下へ」のボタンで行う。数の少ない一覧なので、ドラッグは足さない。ボタンはキーボードで押せ、押したあともフォーカスを同じまとまりのボタンに残す。
色は、4つの選択肢から1つだけを選ぶ操作にし、見本と名前を並べる。

## Risks / Trade-offs

- ほかの変更と移行の番号がぶつかる → 同じ時期に作る変更（#47、#51、#52、#58、#66）も移行を足しうる。実装の時点で、取り込み済みの最後の番号の次に付け直す。
- 単位ごとの変換が、ストップワードの照合と食い違う → 食い違うのは結合を伴うまれな並びだけである。仕様の例に加え、半角のカタカナ、全角の英数字、合字でストップワードと同じ結果になることをテストで確かめる。
- 色が増えて、重要度の印が目立たなくなる → 黄色を使わず、地は薄い色にする。重要度5の見出しの中の語は、語の部分だけ地が替わる。重要度の印（左の線と読み上げの文字）は残るので、重要度は伝わる。
- リンクの文字に一致すると、リンクの下線と色付けの下線が重なる → 色付けの下線を太くし、文字から離して引く。リンクの文字の色は `primary` のままにする。
- 長い本文と多い語で、描くのが遅くなる → 語を前もって照合の形にし、文字列ごとの結果を覚えておく。10万文字の本文と50の語で、区間に分ける時間を測るテストを置く。
- アプリの下線が、まとまりの色にならない → Androidの制約である。まとまりは地の色と一覧の印の名前で見分けられる。
- 書式の境目をまたぐ語が色付けされない → 受け入れる。太字やリンクの途中で語が切れることは少ない。

## Migration Plan

1. 移行で2つの表を足す。既存の表と行は変えない。
2. 古い版に戻すときは、2つの表が残るだけで、古い版はそれを読まない。
3. 古い版のサーバーは、設定ファイルの `termGroups` を知らない項目として無視する。新しい版で書き出したファイルを古い版へ読み込んでも、ほかの設定は読み込める。

## Open Questions

1. 一覧の行の印を、行に出す見出しと抜粋で決めるか、本文まで照合して決めるか。決定は「語を含む記事の行に印を付ける」で、どの文字を照合するかは決めていない。仕様は、行に出す文字で決めるとして書いた。本文まで照合するなら、サーバーが一覧の応答に一致したまとまりを加えることになり、仕様（`http-api`、`web-reader`、`mobile-reader`）と作業が変わる。
2. 読み手への影響、出典の題名、イベントの一覧の行を色付けするか。決定が挙げた場所に含まれないので、この変更では対象にしていない。対象にするなら、`web-reader` と `mobile-reader` に要件を足す。
