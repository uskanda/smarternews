# grilling 記録: complete-event-list

Issue #187「イベントの一覧が50件で切れ、読み込み中と失敗の表示、読み直す操作、一括の既読もない」の計画の記録である。
計画の段階で、Issueの上で2つの質問を出した。どちらも推奨の案が選ばれた。
そのあと、回答に沿った計画を示し、利用者は変更を添えずに `/ok` で承認した。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 終了したイベントを一括の既読に含めるか | A：APIを直し、一括の既読から終了したイベントを除く。すべての一覧とAndroidアプリで、既読にした件数が一覧の未読と合う。`http-api` の仕様と `docs/api.md` も変える | Issue #187 第1ラウンド Q1 |
| Androidアプリにも一括の既読を足すか | A：Webだけを直す。アプリのイベントの一覧に一括の既読のボタンは足さない | Issue #187 第1ラウンド Q2 |
| 上部の作り | 記事の一覧と共通にし、読み込み中、失敗と再試行、「さらに読み込む」、「読み直す」、「すべて既読にする」を同じ見た目で出す。「既読も表示」、重要度の絞り込み、並び順のメニューは出さない | Issue #187 第1ラウンドの前提（計画で承認） |
| 一括の既読のあとの取り消しと次の項目へ移る設定 | 記事の一覧と同じ。範囲はカテゴリ、取り消しは10秒のトースト、移るかは設定に従う | Issue #187 第1ラウンドの前提（計画で承認） |
| `web-shell` の「一括の既読を選べない一覧」のシナリオ | 例を、イベントのカテゴリから最近読んだ記事の一覧に書き換える | Issue #187 第1ラウンドの前提（計画で承認） |
| `r` のキー | すでにイベントの一覧で働くので、変えない | Issue #187 の計画（`/ok` で承認） |
| URLに `min=4` が残っているとき | イベントの一覧では重要度の下限を送らない | Issue #187 の計画（`/ok` で承認） |
| 計画の承認 | 上の判断に沿った計画を、変更なしで承認 | Issue #187 への返答（`/ok`） |

## 後回しにしたもの

- Androidアプリのイベントの一覧の一括の既読（Q2でWebだけに決めた）。サーバーの変更で、アプリのほかの一覧での一括の既読も終了したイベントを除くようになるが、画面は変えない
