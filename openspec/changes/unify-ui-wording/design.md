# Design

## Context

動機はproposal.mdのWhyにある。文言は`apps/web/src`の各画面に直接書かれている。テストは、ボタンやダイアログを、支援技術に伝わる名前で探す。そのため文言を変えると、テストも変える必要がある。

## Goals / Non-Goals

**Goals:**

- 同じ操作には、どの画面でも同じ名前を付ける。
- 「更新」を、続報で記事を書き直した意味だけに使う。

**Non-Goals:**

- Androidアプリの文言。続報の「更新」の印は、Webとアプリの要件とDESIGN.mdが名前で決めているので変えない。
- READMEの説明。「登録の解除」「AIによる要約」（要約の見出し）など、いまの文言と合っている。
- フィルターも消えることを伝える文の「削除」の語。消えるのはフィルターなので、この語のままにする。
- 保存したあとの知らせの文。何を保存したかを伝える役があるので残す。

## Decisions

### 購読フィードの画面の説明

説明の文は次のとおりにする。READMEの「要約と翻訳は、利用者が選んだ購読フィードの記事だけに行う」と同じ内容である。LLMを使うことは、切り替えの横の説明がすでに伝えている。

`登録したフィードを定期的に取得し、配信された記事をそのまま一覧に並べます。要約と翻訳は、選んだ購読フィードの記事だけに行います。`

### 登録の解除の文言

左のペインと設定の画面で、同じ文言を使う。

- 確認のダイアログの見出し：`購読フィードの登録を解除しますか`
- 確認のボタン：`登録を解除する`
- 知らせ：`購読フィードの登録を解除しました`
- 失敗の知らせ：`登録を解除できませんでした。もう一度試してください。`

設定の画面の行のボタンは、見える名前を「登録を解除」、aria-labelを「〇〇の登録を解除」にする。ほかのボタン（「〇〇をいま取得」「〇〇を編集」）と同じく、aria-labelで行の購読フィードを区別する。

### 1つの画面に「保存する」が2つ以上あるとき

設定の画面（読み手情報と全体設定）、購読フィードの画面（行の編集と取得周期）、カテゴリの画面（カテゴリの設定とトピック）には、保存のボタンが2つ以上ある。どのボタンも、見出しのある区画（`section`のaria-label）の中にある。何を保存するかは、区画の見出しで分かる。

テストは、区画（`getByRole("region", { name })`）か一覧の行の中でボタンを探す。ボタンの名前に区画の名前を足す案（「読み手情報を保存する」）は採らない。Issueの改善案とも、DESIGN.mdの「保存する」と「保存しました」の対の例とも合わないからである。

### 進行中の変更の文言

進行中の変更`add-feed-from-category`は、「フィードを追加」「フィードの設定」をボタンの名前として書いている。この変更を閉じると、この語がweb-readerの要件に入る。そこで、その変更のproposal、design、tasks、web-readerの差分の要件を「購読フィードを追加」「購読フィードの設定」に直す。grilling.mdは会話の記録なので直さない。

## Risks / Trade-offs

- ［テストが画面の中の同じ名前のボタンを取り違える］→ 区画か行の中で探すように直す。`getByRole`は同じ名前が2つあると失敗するので、取り違えはテストの失敗として表に出る。
- ［一覧の上のボタンの名前が2文字長くなる］→ このボタンは折り返すことのある行にあり、一覧の名前の欄は狭くならない。
