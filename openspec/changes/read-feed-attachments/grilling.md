# grilling 記録: read-feed-attachments

GitHubのissueの126番のコメントで、1ラウンドの質問（Q1〜Q6）に答えた記録である。
issueは、購読フィードのenclosureとMedia RSS（`media:` の要素）を読まずに捨てているという、Web UIの監査の項目（R-03）である。
YouTubeのフィードの記事は本文が空になり、音声の配信のフィードでは音声へのリンクが消える。一覧のサムネイル（#49）も、取り出す元がない。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 添付を表示する画面の範囲 | WebとAndroidアプリの両方に出す（A） | 第1ラウンド Q1 |
| 添付をAPIでどう渡すか | 記事に `attachments` の配列（URL、種類、MIMEの型、大きさ、題）を足し、画面が本文の下に一覧を描く。画像のURLは、APIの応答を作るときに中継のURLへ書き換える。本文には混ぜない（A） | 第1ラウンド Q2 |
| 画像の添付と動画のサムネイルの出し方 | 画像は中継を通して画像として表示する。動画のサムネイルは、記事のURLへのリンクにした画像として出す。音声・動画・その他は、リンクの横に種類と大きさを書く（A） | 第1ラウンド Q3 |
| media:descriptionの変換の規則 | `type="html"` のときは今の変換を通す。それ以外はプレーンテキストとして扱い、空行で段落を分け、行の改行は改行として残し、http(s)のURLだけをリンクにする（A） | 第1ラウンド Q4 |
| 保存済みの記事と書き換えの扱い | 説明から作った本文は「内容が変わった」として今の書き換えの規則に従う。添付だけが変わったときは列を書き換えるだけで、書き換えとは数えない（A） | 第1ラウンド Q5 |
| 一覧のサムネイル（#49）との境界 | 今回は添付の保存と記事の詳細での表示までにする。一覧の項目にサムネイルを足すのは#49で行う（A） | 第1ラウンド Q6 |

## 計画で決めたこと

承認を求めた計画（issueのコメント）で、次を決めた。利用者は変更なしで承認した。

| 決定 | 選択 |
|---|---|
| 読む要素 | RSSの `enclosure`、`media:content`、`media:thumbnail` と、`media:group` の中の同じ要素 |
| 種類の決め方 | `medium` を先に見て、なければMIMEの型の頭（`image/`・`audio/`・`video/`）で決める。`media:thumbnail` は画像として読み、サムネイルであることを示す印を付ける |
| URLの扱い | 相対のURLは記事のURLを基準に直し、http(s)以外は捨てる。同じURLは1つにまとめ、数とURLの長さに上限を設ける |
| 説明を探す順 | 項目の直下、`media:group`、最初の `media:content` |
| 保存の列 | `articles` の `attachments`（JSON、NULLは「なし」） |
| 説明の検索用のパーサー | `parseFeed` と `collectFeed` は変えない |
| RSSの出力とLLM | 添付は載せず、渡さない。テストで確かめる |
