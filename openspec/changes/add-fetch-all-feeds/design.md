# Design

## Context

次の取得の時刻は保存していない。前回の取得の時刻、取得周期、連続の失敗の回数、Retry-Afterの時刻から、そのつど計算している（`nextFetchFrom`）。
取得は `FeedPoller` の1本の列で直列に進む。30秒ごとの `tick` が、取得の時刻が来た購読フィード（`dueFeeds`）を古い順に取得する。ホストごとの間隔は、取得の部品（`Fetcher`）が守る。
購読フィードごとの「いま取得」（`POST /feeds/:id/fetch`）は、取得が終わるまで応答を待つ。Retry-Afterの待ちも無視する（`distinguish-feed-http-failures` の決定）。
Webは、購読フィードの一覧、未読の数、記事の一覧を60秒ごとに読み直す。

## Goals / Non-Goals

**Goals:**

- 一括の取得を、既存の定期の取得と同じ列、同じ順で進める。直列化とホストごとの間隔のための経路を増やさない。
- サーバーの応答はすぐに返し、画面は購読フィードの一覧から取得の進みを読み取る。
- 2つのボタンが同じ状態を見て、同じ表示になる。

**Non-Goals:**

- Androidアプリの操作と、キーボードのキー。
- 一括の取得の途中での取りやめ。
- 新しい記事の件数の知らせ。サーバーは終わりを待たないので、件数は集めない。

## Decisions

### 取得の求めの時刻を保存する

`feeds` に `fetch_requested_at`（取得の求めの時刻）の列を足す。値がある購読フィードの次の取得の時刻は、その値にする。
これで `dueFeeds` が対象を返し、`FeedPoller` の列が1件ずつ取得する。取得の順は、次の取得の時刻の古い順のままである。

取得の成功と失敗の記録は、求めの時刻を消す。購読フィードを一時停止したときも消す。消したあとの次の取得の時刻は、もとの計算に戻る。

保存せずに、メモリの中で対象を列に積む案もあった。移行は要らないが、定期の取得と別の経路が増え、再起動で残りが失われる（grillingのQ4）。

### 対象と、飛ばすもの

求めを記録する関数（`requestFetchAll`）は、対象の購読フィードへ今の時刻を書く。対象は、有効で、Retry-Afterの時刻が今より先にない購読フィードである。
返すのは、求めた件数（`requested`）、Retry-Afterの待ちで飛ばした件数（`skipped`）、求めの時刻（`requestedAt`）である。
連続の失敗で延びた間隔は、Retry-Afterの時刻とは別の計算なので、求めの時刻がそれを上書きする。
一時停止中の購読フィードは、どちらの件数にも数えない。

### 取得の途中の `tick`

今の `tick` は、取得の回が待機中または進行中のとき、何もせずに戻る。一括の求めが取得の回の途中に来ると、次の30秒の周期まで始まらない。
取得の回が進行中に `tick` が呼ばれたときは、その回が終わったあとに、もう1回まわるようにする。待機中の回は、始まるときに対象を読むので、何も足さない。
`idle`（列が空になるのを待つ）は、待っている間に足された回も待つようにする。

30秒の周期の `tick` が長い回の途中に来たときも、もう1回まわる。対象がなければ問い合わせ1回で終わるので、負荷は増えない。

### APIの形

`POST /api/v1/feeds/fetch` は、求めを記録して `tick` を呼び、`{ requested, skipped, requestedAt }` をすぐに返す。
購読フィードの応答（`Feed`）に `fetchRequestedAt` を足す。値がある間、その購読フィードは取得を待っている。

取得が終わるまで応答を待つ案は採らなかった。応答のないサイトがあると数分かかり、途中で画面を移ると結果を失う（grillingのQ3）。

### Webの状態の持ち方

`lib/fetch-now.ts` に、一括の取得の処理を2つ足す。

- `useFetchAllFeedsNow`：ボタンが使う。購読フィードのどれかに `fetchRequestedAt` がある間は `fetching` を真にする。状態を購読フィードの一覧から読むので、2つのボタンは同じ表示になり、画面を読み込み直しても表示は続く。
- `useFetchAllCompletion`：`Shell` が1度だけ呼ぶ。押した画面で、待っている購読フィードがなくなったときに、知らせを出し、未読の数、記事の一覧、購読フィードの統計を読み直す。

押したあと、画面は `POST` の応答を受け、購読フィードの一覧を読み直してから、求めの記録（求めの時刻と、飛ばした件数）を問い合わせのキャッシュに置く。
読み直す前に置くと、求めの前の一覧を見て、すぐに終わったと判断してしまう。
求めの記録はメモリの中だけに持つ。画面を読み込み直すと、ボタンの表示は続くが、終わりの知らせは出ない。

取得を待っている購読フィードがある間、`useFeeds` は60秒ごとではなく3秒ごとに読み直す。

失敗の件数は、前回の取得の時刻が求めの時刻以後で、失敗の理由が残っている購読フィードを数える。
求めた購読フィードの番号は持たない。求めのあとに取得された購読フィードは、ほぼ求めたものだからである。

### ボタンの置き方

- 左のペイン：「カテゴリ」の見出しの行の右端に、小さいボタン「いま取得」を置く。読み上げ用の名前は「すべての購読フィードをいま取得」にする。購読フィードが1つもないときは出さない。
- 設定の画面：一覧の見出しの下の、「問題のある購読フィードを先頭に並べる」の行の右端に、ボタン「すべていま取得」を置く。

左のペインの見出しの行にボタンを置く形は新しいので、`DESIGN.md` に置き方を書き足す。

## Risks / Trade-offs

- 一括の取得は、押すたびに全部のサイトへ要求を出す。→ 取得は条件付きの要求（ETag、Last-Modified）のままで、変更のないフィードは本文を返さない。Retry-Afterで待つものは飛ばす。取得中はボタンを押せない。
- 求めの直前に始まっていた取得が、求めの時刻を消す。→ その購読フィードは、求めの直後に取得を終えているので、もう1度取得する必要はない。
- 取得を待っている間に、利用者が購読フィードごとの「いま取得」を押すと、その購読フィードの求めの時刻も消える。→ どちらも取得は1度で済み、表示にも矛盾は出ない。
- 画面を読み込み直すと、終わりの知らせは出ない。→ ボタンの`取得中…`は続き、未読の数は60秒ごとの読み直しで新しくなる。
