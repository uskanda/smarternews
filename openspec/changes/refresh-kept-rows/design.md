# Design

## Context

未読の一覧と最近読んだ記事の一覧は、訪問の間に読んだ行を`kept`（残した行）に持ち、`mergeKept`で取得した行と混ぜて表示する。今の`mergeKept`は、同じ記事があると残した行で上書きする。残した行は既読にした時点の写しなので、続報、翻訳の見出し、失敗の巻き戻しが行に出ない。
`kept`はキャッシュの外にあるので、`patchArticle`がキャッシュに書いた変更も届かない。Webは失敗したときだけ、`flagFailed`が手で戻している。アプリの`useArticleFlags`は、記事の詳細のキャッシュがあるときだけ戻す。動機は`proposal.md`の「Why」を参照する。

## Goals / Non-Goals

**Goals:**

- 取得した行にある記事は、取得した行の内容で表示する。続報は未読の見た目で出す（`grilling.md`のQ1）。
- キャッシュに書いた変更を、Webとアプリのどちらでも`kept`に届ける（`grilling.md`のQ2）。
- アプリで失敗したとき、記事の詳細がない行も元に戻す。

**Non-Goals:**

- アプリの失敗の知らせと「もう一度試す」（`grilling.md`のQ2のC）。
- サーバーが続報を未読に戻す動き。

## Decisions

### 取得した行の更新の時刻で、どちらを使うかを決める

取得した行の`updatedAt`が残した行より新しければ、取得した行をそのまま使う。サーバーは続報で記事を書き直すと`updatedAt`を進めて未読に戻すので、この行は未読の見た目で出る。既読やスターの変更では`updatedAt`は変わらない。
同じか古いときは、取得した行に残した行の`isRead`と`starred`を重ねる。変更がサーバーへ届く前に取得した一覧で、行が一瞬だけ元に戻るのを防ぐためである。見出しや既読の時刻は取得した行のものを使い、並べ替えの鍵も重ねたあとの行から取る。

### patchArticle の変更を受け手へ渡す

`patchArticle`は、キャッシュに書いたあと、登録した受け手に`(id, patch)`を渡す。受け手は`QueryClient`をキーにした`WeakMap`で持つ。接続を変えてキャッシュを作り直したときに、古い受け手が残らないためである。`useArticlePatchListener`は、描画のたびに変わる関数を`ref`で呼ぶので、登録は`QueryClient`が変わるときだけ行う。
Webは`ReaderPage`、アプリは`ReaderSessionProvider`が受け取り、残した行にある記事にだけ当てる。残した行にない記事では状態を変えず、描画を増やさない。
Webの`patchArticle`は外れの印を一覧へ渡さないので、受け手にも渡さない。

### Web の flagFailed は知らせるだけにする

失敗したときの巻き戻しは`useArticleFlags`の`onError`が`patchArticle`で行い、受け手を通して`kept`にも届く。`flagFailed`の中で`kept`を手で戻す処理は同じことをするので消す。知らせと「もう一度試す」は残す。

### アプリの onError は送った値の反対を当てる

Webと同じく、送った`isRead`や`starred`の反対を当てる。アプリでこれらを送る操作は、どれも今の値の反対を送るので、送る前の値と一致する。記事の詳細のキャッシュを読まないので、長押しのメニューや払う操作の行でも戻る。

### Web のスクロールでの既読は今の行を写す

スクロールで既読にした行は、すでに`kept`にある行も、今の一覧（`items`）の行から写し直す。`items`は取得した行を優先して混ぜたものなので、古い写しの見出しを使い続けない。アプリの`showRead`と`setRead`はすでに今の行を写している。

## Risks / Trade-offs

- 同じ記事に続けて2つの要求を送り、先の要求だけが失敗すると、後の要求の値を反対に戻してしまう。Webの`notify-flag-failures`と同じ割り切りで、一覧は1分ごとに取得し直すので、いずれサーバーの値にそろう。
- 続報で未読に戻った行は、その訪問の間は未読の一覧に残る。取得した行がそのまま使われるので、未読数とも一致する。
