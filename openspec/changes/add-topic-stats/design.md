# Design

## Context

動機は proposal.md の「Why」を参照する。

- 候補（`candidates`）は30日で消える。除外の理由は文（`reason`）だけで保存しており、プログラムの理由も判定の理由も同じ列に入る。トピックの試し（add-topic-trial）では、文を `reasons.ts` の日本語と英語の文に照らして見分けていた。
- 外れの印（#137）は `misses` と `miss_topics` に残り、記事が消えても記録は残る。生成記事は180日残る。
- 記事は `article_topics` で、候補は `candidate_topics` でトピックにつながる。1件の候補や記事が、2つのトピックにつながることがある。
- main には、番号が024の移行が2つあった（`024_feed_http_failures.sql` と、#164 で入った出典の理由の移行）。移行は番号を版として記録するため、新しいデータベースでは2つ目の記録が一意の制約で失敗する。024まで進んだデータベースでは、もう片方が飛ばされる。

## Goals / Non-Goals

**Goals:**

- トピックの成績を、保存してある行だけからLLMなしで数える。
- プログラムの理由の種類を、文を照らさず、列の値で見分ける。

**Non-Goals:**

- 日ごとの集計の表と、30日より前の推移（grilling の Q11）。
- Androidアプリの画面（トピックの設定の画面がない）。
- #137 の「解釈し直す」の文とボタンを変えること。

## Decisions

### 理由の種類は候補の列に持たせる

移行の027で、`candidates` の表に `reason_code` の列を足し、`CHECK` で5つの値と NULL に限る。プログラムが除外するときだけ値を入れ、判定（モデル）による除外、保留中、採用済みの候補は NULL にする。`rejectCandidates` は理由の文ではなく種類と出力の言語を受け取り、文は `reasonText` で作る。これで、文と種類の食い違う書き込みはできなくなる。

移行の中で5回の `UPDATE` を行い、過去の候補のうち、理由の文が日本語か英語の文と一致する除外済みのものだけに値を入れる（Q10）。文の一覧は、移行のSQLと `reasons.ts` の2か所で持つ。そこで、`reasons.ts` の全種類と両言語の文で移行を試すテストを置き、食い違いを見つける。

試しの候補の読み出し（`listTrialCandidates`）も、文の照合をやめてこの列を読む。照合の関数 `programReasonCode` は使う所がなくなるので消す。

代わりの案は、移行をせずに読み出しのたびに文を照らす方法である。SQLの集計の中で照合できず、全件を読んでから数えることになるので採らない。

### 集計は3つの問い合わせで行う

`db/topicStats.ts` の `topicStats(db, categoryId, now)` は、次の3つで数える。

1. 候補：`candidates` と `candidate_topics` をつなぎ、トピックと取得元の種類でまとめる。理由の種類ごとの数も、同じ問い合わせの `sum` で出す。
2. 記事：`articles` と `article_topics` をつなぎ、`origin = 'generated'` に限ってトピックでまとめる。作った記事は `created_at`、更新した記事は `revision > 0` と `updated_at` で期間を測る。外れは、記事に `misses` があり、その `miss_topics` にこのトピックがあるものを数える。
3. よく除外されるサイト：候補のあるトピックごとに、除外済みでサイト名のある候補をサイトでまとめ、件数の多い順、同じならサイト名の順に3つ取る。

トピックは `topics` から全件をIDの順に読み、何もないトピックにも0を返す。カテゴリがなければ `getCategory` が not_found を投げ、APIは404を返す。候補の期間の絞り込みのために、`candidates (category_id, created_at)` の索引を足す。

### 並べ方は純粋な関数にして core から出す

`rankTopicStats` は `api.ts` に置き、Webが `@smarternews/core/api` から読む。並べ方は次のとおりである（Q9）。

1. 集めた候補が0件のトピック
2. 外れの割合の大きい順。作った記事が0件なら、割合は0とする
3. 記事にならなかった候補の割合の大きい順。除外の4つの数の合計を、集めた候補の数で割る
4. トピックのIDの順

並べ替えは画面の状態だけで、サーバーは常にIDの順で返す。

### 画面は別のファイルの区画にする

`settings/TopicStats.tsx` に `TopicStatsSection` を置き、`CategoryPage` のトピックの区画の次に並べる。各行は `id="topic-stats-<id>"` を持ち、その印へのリンクで開いたときは行まで送る。トピックの名前は `topicEditPath` へのリンクにして、編集を開く。数の並びは購読フィードの統計（`StatsList`）と同じ `dl` の形にし、狭い画面では1列、広い画面では2列に並べる。

成績の問い合わせのキーは `["topic-stats", categoryId]` にする。カテゴリの画面でトピックを追加、保存、削除、解釈し直したとき、読み手の画面からトピックを足したとき、外れとスターを付け外ししたときに、古い扱いにする。

実行の詳細では、「トピックごとにまとめる」の見出しごとに、「このトピックを直す」の横に「このトピックの成績」を置く。パスの関数 `topicStatsPath` は `lib/paths.ts` に置く。

### 重なった移行の番号を直す

出典の理由の移行を、024番から026番（`026_ref_reasons.sql`）に移す。main へ先に入っていたのは `024_feed_http_failures.sql` なので、後から入った方を動かす。これで、024まで進んだデータベースでも出典の理由の列が足される。同じ番号の移行が2つないことを、`database.test.ts` で確かめる。

## Risks / Trade-offs

- ［1件の候補や記事が2つのトピックにつながると、両方のトピックで数えられる］→ 成績はトピックの当たり外れを見るためのもので、合計を出さないので問題にしない。docs/api.md に書く。
- ［候補は最後の理由しか持たない］→ 判定が受け入れたあとにプログラムが除外した候補は、プログラムの理由で数える。判定の当たり外れとプログラムの選別を分けたいときには足りない。それでも、今の表の形で出せる最善である。
- ［理由の文を `reasons.ts` で変えると、移行の文と食い違う］→ 移行は一度しか走らないので、変えた後の文は列の値で見分けられる。移行のテストは、その時点の文で移行が正しく働くことを確かめる。
- ［出典の理由の移行を024番として当てた開発用のデータベース］→ 026 として、もう一度当てようとして列の重複で失敗する。main から配備したデータベースにはこの状態がないので、手当てはしない。

## Migration Plan

- 起動時の移行で、026（出典の理由）と027（理由の種類）が順に当たる。どちらも列と索引を足し、既存の行を埋めるだけである。
- 戻すときは、前の版のサーバーを動かせばよい。足した列と索引は前の版では読まれない。
