# grilling 記録: fix-export-blob-revoke

Issue #104「書き出しで、ダウンロードの開始前にBlob URLを解放している」の計画の記録である。
計画の段階で、質問は出していない。どの判断もIssueの文面か既存の規約から決まるためで、計画に「前提にした判断」として3つを並べ、変えたいものがあれば承認に添えてもらう形にした。
利用者は、変更を添えずに計画を承認した。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 直し方 | Blob URLの解放をなくさず、`setTimeout`で遅らせる | Issue #104の本文、計画 前提2（`/ok` で承認） |
| 重複した手順 | OPMLと設定ファイルの書き出しの手順を、共通関数`saveBlob(blob, filename)`（`apps/web/src/lib/download.ts`）に1つにまとめる。片方だけに直しが入るのを防ぐ | Issue #104の計画 前提1（`/ok` で承認） |
| 解放までの待ち時間 | 定数`REVOKE_DELAY_MS`で40秒。FileSaver.jsが同じ理由で使う値で、0msでは遅いSafariで足りない場合がある。Blobを40秒長く持つだけで済む | Issue #104の計画 前提3（`/ok` で承認） |
| エラー処理 | 2つの画面のエラー処理と`setError(null)`は今のまま残す | Issue #104の計画 変えること2（`/ok` で承認） |
| 確かめ方 | 偽のタイマーで、クリックの直後には解放せず、待ち時間のあとに同じURLで1回解放することを先にテストする。今ある2つの書き出しのテストが通ることも確かめる | Issue #104の計画 確かめ方（`/ok` で承認） |
| 計画の承認 | 上の判断に沿った計画を、変更なしで承認 | Issue #104への返答（`/ok`） |
