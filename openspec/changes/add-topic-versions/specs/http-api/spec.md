# Spec Delta

## ADDED Requirements

### Requirement: トピックの版の記録

トピックの残す項目のどれかが変わったとき、APIは、変わった後の値でトピックの版を1つ残さなければならない（MUST）。残す項目は、文章、検索語、判定基準、取得元（フィードのURL、ニュース検索、LLM検索）、検索の言語と地域である。版は、作った時刻、契機、解釈が済んでいるかどうかを持つ。契機は、トピックの作成が「作成」（`created`）、編集が「編集」（`edited`）、解釈の結果が「解釈」（`interpreted`）、設定ファイルの読み込みが「設定ファイル」（`settings-file`）、「この版に戻す」が「版に戻す」（`restored`）である。

残す項目が直前の版と同じ保存では、APIは版を作ってはならない（MUST NOT）。有効と無効の切り替えと、「解釈し直す」の要求も版を作らない。

#### Scenario: トピックを作る

- **WHEN** トピックを作る
- **THEN** そのトピックに契機「作成」の版が1つできる

#### Scenario: 文章を直す

- **WHEN** トピックの文章を変えて保存する
- **THEN** 新しい文章を持つ、契機「編集」で解釈が済んでいない版が1つ増える

#### Scenario: 同じ値で保存する

- **WHEN** トピックの文章と取得元を、今と同じ値で保存する
- **THEN** 版は増えない

#### Scenario: 無効にする

- **WHEN** トピックを無効にする
- **THEN** 版は増えない

### Requirement: 設定ファイルの読み込みでのトピックとカテゴリの版

設定ファイルを読み込んだとき、APIは、既存のトピックにつき版を多くとも1つ、契機「設定ファイル」で作らなければならない（MUST）。取得元の更新と解釈の取り込みの両方で値が変わっても、版は1つにまとめる。既存のカテゴリも、最低重要度か件数上限が変わったときに、契機「設定ファイル」の版を1つ作る。

#### Scenario: 取得元と解釈を同時に読み込む

- **WHEN** 既存のトピックの取得元と解釈の結果の両方を変える設定ファイルを読み込む
- **THEN** そのトピックの版は、契機「設定ファイル」で1つだけ増える

### Requirement: トピックの版の一覧

`GET /api/v1/topics/:id/versions` を受けたとき、APIは、トピックの版を新しい順に返さなければならない（MUST）。各版は、ID、作った時刻、契機、戻した元の版のID（契機が「版に戻す」のときだけ）、解釈が済んでいるかどうか、残す項目の値を持つ。存在しないトピックには404を返す。

#### Scenario: 一覧を求める

- **WHEN** 作ってから文章を1回直したトピックの版を要求する
- **THEN** 契機「編集」の版、契機「作成」の版の順に2つ返る

#### Scenario: 存在しないトピック

- **WHEN** 存在しないトピックの版を要求する
- **THEN** 404が返る

### Requirement: この版に戻す

`POST /api/v1/topics/:id/versions/:versionId/restore` を受けたとき、APIは、その版の残す項目の値をトピックの今の値として保存し、契機「版に戻す」の新しい版を作り、トピックを返さなければならない（MUST）。古い版は消さない。戻した後の取得元は、利用者が決めたものとして扱い、後の解釈で上書きしない。

解釈が済んだ版に戻したとき、APIは、トピックを解釈済みのままにし、解釈した時刻を戻した時刻にしなければならない（MUST）。解釈が済んでいない版に戻したとき、トピックは解釈が済んでいない状態になり、次の実行で解釈される。

版がそのトピックのものでないとき、または存在しないとき、APIは404を返さなければならない（MUST）。

#### Scenario: 解釈済みの版に戻す

- **WHEN** 判定基準Aで解釈が済んだ後に文章を直して判定基準Bになったトピックで、判定基準Aの版に戻す
- **THEN** トピックの判定基準はAになり、解釈済みのままで、解釈した時刻は戻した時刻になり、外れの数は戻した時刻から数え直される
- **AND** 契機「版に戻す」の版が増え、それまでの版はすべて残る

#### Scenario: 解釈が済んでいない版に戻す

- **WHEN** 解釈が済んでいない版に戻す
- **THEN** トピックは解釈が済んでいない状態になる

#### Scenario: 別のトピックの版

- **WHEN** トピックAのURLで、トピックBの版に戻すよう要求する
- **THEN** 404が返り、どちらのトピックも変わらない

### Requirement: カテゴリの版

カテゴリの最低重要度か件数上限が変わったとき、APIは、変わった後の2つの値でカテゴリの版を1つ残さなければならない（MUST）。カテゴリの作成でも版を1つ作る。ほかの項目だけの変更では版を作らない。`GET /api/v1/categories/:id/versions` を受けたとき、APIはカテゴリの版を新しい順に返す。存在しないカテゴリには404を返す。

#### Scenario: 最低重要度を変える

- **WHEN** カテゴリの最低重要度を3から4に変える
- **THEN** 最低重要度4の版が1つ増える

#### Scenario: 名前だけを変える

- **WHEN** カテゴリの名前だけを変える
- **THEN** 版は増えない

### Requirement: 既存のトピックとカテゴリの最初の版

版を残す前からあるトピックとカテゴリには、サーバーは更新のときに、今の値で契機「作成」の版を1つずつ入れなければならない（MUST）。版の時刻は、トピックやカテゴリを作った時刻とする。

#### Scenario: 更新の後

- **WHEN** トピックを2つ持つサーバーを更新する
- **THEN** 各トピックに、今の値で契機「作成」の版が1つずつある

### Requirement: 成績の版の切れ目

トピックの成績を返すとき、直近30日の中にトピックの版の切れ目があれば、APIは、そのトピックの項目に、最後の切れ目の時刻と契機（`boundary`）と、切れ目の前（`before`）と後（`after`）の成績を足さなければならない（MUST）。切れ目は、最初の版と、最初に解釈が済んだ版までの版を除いた、版の作られた時刻である。前の成績は期間の始まりから切れ目まで、後の成績は切れ目から後に数える。候補は集めた時刻で、記事は作った時刻で分け、外れは記事が作られた側に数える。切れ目がなければ、`boundary`、`before`、`after` を含めない。全体の数は、切れ目があっても変えない。

#### Scenario: 判定基準を変えた前後

- **WHEN** 10日前に判定基準を変えたトピックが、その前に生成記事を5件作って2件に外れの印があり、その後に3件作って外れがない状態で成績を要求する
- **THEN** そのトピックの項目の `before` は作った記事5件と外れ2件、`after` は作った記事3件と外れ0件になり、全体は作った記事8件と外れ2件になる

#### Scenario: 最初の版だけのトピック

- **WHEN** 作ってから版が増えていないトピックの成績を要求する
- **THEN** そのトピックの項目に `boundary` はない

#### Scenario: 31日前の変更

- **WHEN** 最後の変更が31日前のトピックの成績を要求する
- **THEN** そのトピックの項目に `boundary` はない

### Requirement: 版でのLLMの扱い

版の記録、一覧、「この版に戻す」、成績の切れ目のどれでも、APIはLLMを呼んではならない（MUST NOT）。

#### Scenario: 戻しても呼ばない

- **WHEN** 解釈済みの版に戻し、その後に成績を要求する
- **THEN** LLMのタスクは1回も呼ばれない
