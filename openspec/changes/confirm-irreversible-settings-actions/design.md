# Design

## Context

動機は `proposal.md` の「Why」を見よ。ここでは、設計を決める今の作りだけを書く。

- 取り消せない操作の確認には、`apps/web/src/ui/ConfirmDialog.tsx` がある。カテゴリ、購読フィード、語のまとまり、ハイライトの削除が使っている。開くと最後のボタン（安全な選択肢）にフォーカスを置き、Escで閉じる。閉じたときは、開いたボタンか `returnFocus` が返す要素にフォーカスを戻す。
- フィルターの行 `FilterRow`（`FiltersPage.tsx`）は、削除のあと一覧の読み直しで消える。
- 設定ファイルの読み込みは、`SettingsFile`（`SettingsPage.tsx`）の入力欄の送信で `api.importSettings` を呼ぶ。
- トークンの消去は、設定の画面のボタンが `clearToken` を呼ぶ。サーバーが401を返したときは、`App.tsx` がトークンを消す。

## Goals / Non-Goals

**Goals:**

- 3つの操作を、既存の確認のダイアログと同じ見た目と動きで確かめる。
- 確定のあとの処理と知らせは、いまと変えない。

**Non-Goals:**

- 取り消しの知らせ（grillingのQ1）、試しの読み込みのAPI（Q2）。
- 401のときの自動の消去の確認（Q3）。
- Androidアプリ。接続の解除は、すでに確認している。

## Decisions

### 既存の `ConfirmDialog` を使う

ボタンは、実行する操作を先に、「やめる」を最後に置く。`ConfirmDialog` は最後のボタンにフォーカスを置くので、Enterを2回押しても実行されない。
フィルターの削除の「削除する」とトークンの消去の「消す」は `danger` にする。設定ファイルの「読み込む」は、何かを消す操作ではないので `primary` にする。

### フィルターの削除

「削除」のボタンでは確認を開くだけにする。確定したら、いまの `remove()` が削除と知らせを行う。削除に成功したら、ダイアログを閉じる。
行は削除のあとに消えるので、フォーカスは一覧の見出し「一覧」に移す。見出しは `tabIndex={-1}` でフォーカスを受けられるようにする。やめたときは、開いた「削除」のボタンに戻す。
一覧に戻る件数は、行が持つ `hiddenCount` を使う。無効のフィルターは何も隠していないので、件数を出さない。

### 設定ファイルの読み込み

入力欄の送信では確認を開くだけにし、いまの読み込みの処理は確認の「読み込む」で動かす。確認の文は決まった文にし、ファイルの名前だけを差し込む。

### トークンの消去

ボタンで確認を開き、確定したら `clearToken` を呼ぶ。トークンが消えると入力の画面に替わるので、ダイアログは画面ごと消える。

### 採らなかった案

- フィルターの削除のあとに取り消しを出し、同じ内容で作り直す案。IDが変わり、隠していた記事の扱いも作り直しに頼るので採らない。
- サーバーに試しの読み込みを足し、作成と更新の件数を確認に出す案。サーバーとコアに手が入るので、今回は採らない。

## Risks / Trade-offs

- 確認の文は件数を含まないので、読み込みで何件が変わるかは確定まで分からない → 先に書き出して控えを取れることを確認に示す。件数が必要になったら、試しの読み込みを別のissueにする。
- フィルターの削除に失敗したときもダイアログを閉じ、知らせを出す → 行は残るので、もう一度「削除」を選べる。
