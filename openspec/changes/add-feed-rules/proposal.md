# Proposal

## Why

Inoreaderから乗り換えるには、条件に合う新しい配信記事へ決めた操作を自動で行う「ルール」が要る。
今のsmarternewsには、配信記事を隠すフィルターはあるが、スターを付ける、既読にする、通知する、要約を頼むといった操作を自動で行う手段がない。

## What Changes

- 配信記事の「ルール」を新しく足す。ルールは、フィルターと同じ形の条件と適用する範囲（全体・カテゴリ・購読フィード）、操作（スター、既読、通知、要約から1つ以上）、有効と無効の別を持つ。
- サーバーは、配信記事を初めて保存したときにだけルールを適用する。重複として隠した記事、フィルターで隠れた記事、再取得で書き換わった記事には適用しない。合ったルールが複数あれば、操作を合わせて行う。
- ルールで既読にした記事は通知の対象にしない。
- ルールで頼んだ要約は、自動の要約を有効にしていない購読フィードの記事でも行う。順番は、開いて頼んだ記事の次で、ほかの自動の要約より先とする。1日の上限に数え、既読になっても待ちから外さない。
- **BREAKING** 「配信記事を通知しない」規則を改め、ルールで通知の対象になった配信記事だけを、Androidアプリが通知する。通知の設定が「出さない」以外なら、「重要度5だけ」でも通知する。通知には見出しと購読フィードの名前を出し、生成記事と合わせて4件以上なら1つにまとめる。
- APIに、ルールの一覧、登録、変更、削除、保存の前の件数の確認と、ルールの通知の対象になった配信記事の一覧を足す。
- Webの設定の画面に「ルール」のページを足す。フィルターの画面の条件と範囲の入力を使い回す。
- 購読フィードかカテゴリの削除の確認で、一緒に削除されるルールの数も示す。
- 設定ファイルの書き出しと読み込みで、ルールも扱う。
- AGENTS.mdの、配信記事の要約の対象についての規則に、ルールで頼んだ記事を足し、ルールの判定でLLMを呼ばないことを書き添える。
- webhookへ送る操作は、この変更に含めない。

## Capabilities

### New Capabilities

- `feed-rules`: 配信記事のルールの登録、条件、範囲、適用する時点と対象、操作、件数の確認、有効と無効、範囲の対象を削除したときの扱い。

### Modified Capabilities

- `mobile-notifications`: 「配信記事を通知しないこと」を、ルールで通知の対象になった配信記事だけを通知することに改める。通知する記事、通知の内容、通知のまとめ、有効にする前からある記事に、ルールの通知の場合を足す。
- `feed-subscriptions`: 要約の対象に、ルールで要約を頼んだ配信記事を足す。順番、1日の上限、既読になったときの扱いを定める。
- `http-api`: ルールの操作と、ルールの通知の対象になった配信記事の一覧を足す。
- `web-settings`: ルールの設定の画面と、削除の確認で消えるルールの数の表示を足す。
- `settings`: 設定ファイルでのルールの書き出しと読み込み、範囲の結び付け、往復を足す。

## Impact

- `packages/core`: 移行 `032_rules.sql`（表 `rules`、記事の列 `rule_notify_at` と `rule_summary_requested_at`）、`db/rules.ts`、`feeds/ingest.ts`、`db/articles.ts`（要約の待ち）、`api.ts`（型）、`settings-file.ts`。
- `apps/server`: `/api/v1/rules` と `/api/v1/rule-notifications` の経路。
- `packages/client`: APIの呼び出しと、通知する記事の選び方（`planNotifications`）。
- `apps/mobile`: 定期的な確認（`check.ts`）と、見た位置の保存（`store.ts`）。
- `apps/web`: ルールの設定の画面、フィルターの入力の部品化、削除の確認。
- `docs/api.md`、`AGENTS.md`、`openspec/glossary.yml`。
- LLMの呼び出しは増えない。要約の呼び出しは、今の1日の上限の中に収まる。
