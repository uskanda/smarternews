# Design

## Context

ダイジェストは表 `digests` に保存し、`DigestWorker` が1つずつ作る。きっかけは `schedule`・`catch-up`・`manual` の3つで、表のCHECK制約で縛っている。
次の期間の始めを決める `digestPeriodStart` は、全ダイジェストの `max(period_end)` を見る。
1日の上限は、呼び出しの記録のうち `digest` のタスクを数える `runner.digestBlocked()` で守る。
アプリの通知は、`GET /digests?limit=1` の最新のidが前回より大きいかだけで決まる。

## Goals / Non-Goals

**Goals:**

- Webの名前の記事の一覧、検索の結果、スターの一覧から、その一覧の記事をまとめたダイジェストを作れる
- 一覧のダイジェストが、時刻のダイジェストの期間と通知を乱さない

**Non-Goals:**

- アプリの一覧からの操作
- 一覧のダイジェスト専用の1日の上限
- カテゴリやフィードの一覧からの操作

## Decisions

### 対象を列 `target` に持つ

`digests` に `target`（JSON、NULL可）を足す。中身は種類（`mention` / `search` / `starred`）、名前または検索語と絞り込み（`category`・`feed`・`unread`）、表示用の説明 `label` である。`trigger` には `list` を足す。
SQLiteはCHECK制約を変えられないので、移行 `034_list_digests.sql` で表を作り直し、行をidごと移す。期間の列はNOT NULLのままにし、一覧のダイジェストには入力の記事の時刻の最古と最新を入れる。
`digestPeriodStart` は `target IS NULL` の行だけを見る。`trigger = 'list'` で見分けることもできるが、対象の有無で見分けるほうが、対象を持つきっかけが増えても正しい。

### 説明はサーバーが作る

表示用の説明（`名前：〇〇`、`検索：〇〇`、`スター`）は、サーバーが対象から作って保存する。Webとアプリは送らない。
検索に絞り込みがあれば、括弧の中に書く（例：`検索：半導体（カテゴリ：Tech、未読だけ）`）。カテゴリ名とフィード名は、保存の時点のものを使う。時刻のダイジェストも、作った時点のカテゴリ名を保存している。

### 記事の集め方

`listDigestArticles(db, target, now)` は、画面と同じ条件で記事のidを新しい順に200件まで取る。検索は `searchArticles`、名前は `listMentionArticles`、スターは `listArticles` の `starred=true` を使う。
そのうえで、入力の形に読み替える。タイトルと、生成記事は要約、配信記事は自動の要約か内容の先頭300文字である。画面と同じ関数を使うので、絞り込みの条件がずれない。
時刻のダイジェストと違い、無効なカテゴリの記事も除かない。画面に出ている記事をまとめるためである。

### 作る流れ

`DigestWorker` の `buildFromList` は `buildNow` と同じ順で確かめる。作っている最中なら `busy`、記事が0件なら `empty` を返す。上限か予算に当たれば `limit` / `budget` を返し、それ以外は順番待ちに積んで `queued` を返す。
`makeDigest` は対象を受けると、`listDigestArticles` で記事を集め、タスクの入力に `scope` を入れ、保存のときに `target` を書く。
区画はいまと同じく、入力の記事を持つ有効なカテゴリについて作る。

### API

`POST /digests` の本文に任意の `target` を足す。本文がないか `target` がなければ、いまの「今すぐ作る」である。
`GET /digests` に `kind=period` を足し、`target` のないダイジェストだけを返す。アプリの通知の確認はこれを使う。

### タスクの入力

`DigestInput` に任意の `scope` を足す。あるときは、タスクの説明の文を「利用者が選んだ一覧の記事」に置き換え、期間の行を出さない。
対象の説明は記事の名前や検索語を含むので、記事の一覧のあとに資料の区切り（`material`）で囲んで渡す。記事の一覧のあとに置くので、カテゴリと記事の資料の順番は変わらない。

## Risks / Trade-offs

- アプリの古いビルドは `kind=period` を送らない。更新するまでは、一覧のダイジェストも通知する。
- 上限を共有する。昼に一覧を何度もまとめた日は、夕方の定時のダイジェストを作れないことがある。その期間は、24時間の範囲で次の時刻のダイジェストに含まれる。
