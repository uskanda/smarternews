# grilling 記録: distinguish-feed-http-failures

GitHubのissueの129番のコメントで、1ラウンドの質問（Q1〜Q6）に答えた記録である。
issueは、購読フィードの取得で2xxと304以外の応答をすべて同じ失敗として扱い、429、Retry-After、410を区別しないという、Web UIの監査の項目（R-08）である。
相手の指定した待ち時間を守らない場合があり、配信を終えたフィード（410）と一時的な失敗も見分けられない。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 410をどう記録し、APIでどう返すか | feedsに列 `gone_at` を足す。連続する410のうち、最初に受けた時刻を入れる。成功すると空に戻す。APIの `Feed` に `goneAt: string \| null` を足す。`last_error` と `failure_count` は今と同じように記録する（A） | 第1ラウンド Q1 |
| 410が続くフィードを取得する頻度 | ほかの失敗と同じにする。失敗ごとに間隔を2倍に延ばし、24時間で止める。自動では無効にしない（A） | 第1ラウンド Q2 |
| 410のときの画面 | FeedStateに `gone`（表示は「配信終了」）を足し、`failed` より強い状態にする。一覧の上の帯で登録の解除を勧め、設定の該当する行へのリンク「設定で登録を解除する」と「いま取得」を置く。設定の画面には印「配信終了」を出す。左のペインでは、ほかの状態と同じ印にする（A） | 第1ラウンド Q3 |
| Retry-Afterを守る応答 | 429と503のときだけ守る。秒数と日付の両方の形を読み、上限は24時間とする。読めない値や過去の時刻は無視して、2倍の延長だけを使う。429の理由の文言は「アクセスが多すぎると返されました（HTTP 429）」に変える（A） | 第1ラウンド Q4 |
| 待っている間の「いま取得」 | 今と同じように、すぐに取得する。自動の取得だけがRetry-Afterを守る（A） | 第1ラウンド Q5 |
| Webページの購読フィードの扱い | 両方の形式で同じにする。`PageResult` の `http` の結果に Retry-After を持たせ、Webページの購読フィードでも410を記録し、Retry-Afterを守る。本文の取得（全文）は、この値を使わない（A） | 第1ラウンド Q6 |

## 計画で決めたこと

承認を求めた計画（issueのコメント）で、次を決めた。利用者は変更なしで承認した（`/ok`）。

| 決定 | 選択 |
|---|---|
| Retry-Afterの記録 | feedsに列 `retry_after_until` を足す。次の取得の時刻は、2倍の延長による時刻とこの時刻の遅いほうにする。失敗のたびに上書きし、成功すると空に戻す |
| 410以外の失敗のあとの `gone_at` | 空に戻す。「連続する410のうち最初の時刻」だからである |
| 理由の文字列 | 今と同じ `HTTP status N: url` のままにする。登録のときの拒否の文言も変えない |
| Retry-Afterを読む関数 | `packages/core/src/fetch/` に純粋関数として置く |
| Androidアプリ | 取得の状態を表示していないので、変えない |
