# Design

## Context

実行（`packages/core/src/pipeline/run.ts`）は、未了のトピックを解釈し、候補を集め、判定済みのURLを除いてから判定する。判定は`judgeBatchSize`件ずつである。
判定のあとで、プログラムが重要度、件数上限、開催日で除外することがある。そのときは、理由を`reasons.ts`の決まった文で上書きする。
LLMの呼び出しは`TaskRunner`を通り、`llm_calls`に1行ずつ記録される。1日の上限は`llm_calls`を数えて判定する。セレクターの提案は、タスクの名前で数えて別の上限を持つ。
試しは既存の解釈と判定のタスクを使うので、タスクの名前では見分けられない。

## Goals / Non-Goals

**Goals:**

- 試しは、実行と同じ判定のタスクの入力を作り、文章だけを差し替えた結論を出す。
- 試しは、`llm_calls`のほかに何も書き込まない。

**Non-Goals:**

- 試しで候補を集め直すこと。試すのは保存してある候補だけである。
- 試しの解釈を保存に使うこと（grillingのQ7）。
- 試しの結果をデータベースに残すこと。

## Decisions

### 呼び出しの用途の列

`llm_calls`に`purpose TEXT`を足す（`022_llm_call_purpose.sql`）。NULLは今までの用途、`'trial'`は試しである。
`CallBudget`に`purpose?: "trial"`を持たせ、`TaskRunner`の記録の処理が書き込む。試しの回数は`purpose = 'trial'`の行を数える。
タスクの名前を新しく作る案は採らない。定義済みのタスクだけを使う要件に反し、割り当ても二重になる。

### 上限の確かめ

`budget.purpose`が`"trial"`のとき、`TaskRunner`は呼び出しの前に、まず試しの1日の上限を確かめる。達していれば`LlmLimitError("day")`を投げる。
そのあと、今までどおり実行あたりの上限、1日あたりの上限、予算を確かめる。試しの呼び出しは用途を問わず`callsToday()`に入るので、1日の上限と予算にも数えられる。
始める前の確かめは`trialBlocked(calls)`が受け持つ。返す値は次のとおりである。

- 試しの残りが`calls`より少なければ`"limit"`
- 1日の残りが少なければ`"day"`
- 解釈か判定のプロバイダーが金額のかかるもので、予算に達していれば`"budget"`

### 試しの候補

`listTrialCandidates(db, topicId, perSide)`は、`candidate_topics`でトピックに結び付いた候補を読む。公開日時が不明で除外した候補（理由が`no-date`の決まった文）は除く。
採用待ちと採用済みの候補、プログラムの理由で除外した候補を「判定では採用」とする。それ以外の除外は「判定では除外」とする。
各側を新しい順（`created_at`と`id`の降順）に`perSide`件取る。片方が足りなければ、もう片方の残りから新しい順に埋める。
プログラムの理由は`programReasonCode(reason)`で見分ける。日本語と英語のどちらの決まった文にも当たるので、出力言語を変える前の候補も見分けられる。
候補は保存期間の30日を過ぎると消える。そのため、「直近30日」は保存してある候補の全体と同じである。

### 判定の入力

`planTopicTrial`は、候補を`created_at`の昇順に並べて、`judgeBatchSize`件ずつの組に分ける。組ごとに、組の中の最大の`created_at`を`now`として渡す。
古い組に今の時刻を渡すと、文章と関係のない古さで除外に変わるからである。
トピックは、組の候補が当たったトピックをすべて渡す。差し替えるのは試すトピックだけで、文章は下書き、判定基準は試しの解釈の結果にする。ほかのトピックは、データベースの文章と判定基準のまま渡す。
解釈のタスクには、下書きの文章とカテゴリの種別を渡す。検索の言語と地域は下書きの値で、空なら全体設定の値である。

### 結果の形

結果は、新しい検索語と判定基準、カテゴリの最低の重要度、試した件数、入れ替わった候補の一覧である。
入れ替わった候補ごとに、タイトル、URL、サイト名、公開日時を返す。前の側は、結論と保存してある理由、その理由がプログラムのものかどうかである。
新しい側は、結論と理由と重要度である。新しい重要度がカテゴリの最低を下回るかどうかも返す。
プログラムの理由で除外した候補には、判定の理由が残っていない。そのため、前の理由はプログラムの理由そのものになる。

### サーバーでの置き場

`apps/server`の`TopicTrials`が、試しをメモリーの`Map`に置く。動いている試しは1つまでとし、2つ目は`DomainError("conflict")`の409で断る。
終わった試しは30分残し、次の試しを始めたときにも古いものを消す。識別子は`randomUUID()`で作る。
`POST /api/v1/topics/:id/trials`は、トピックの存在と本文を確かめる。`trialBlocked`が理由を返せば、200で`{ status, id: null }`を返す。`status`は`limit`、`day`、`budget`のどれかである。
始めたときは、202で`{ status: "started", id }`を返す。ダイジェストの`POST /digests`の返し方に合わせた。
`GET /api/v1/topic-trials/:id`は、試しの状態と結果を返す。状態は`running`、`succeeded`、`failed`、`stopped_by_limit`のどれかである。

### 画面

`TopicEditor`の保存の隣に「試す」を置く。押すと、編集中の文章と検索の言語と地域を送り、2秒ごとに問い合わせる。
結果は編集の欄の下に置き、入れ替わった候補の前と新しい結論を並べる。結論は「採用」「除外」の語で示し、色だけに頼らない。

## Risks / Trade-offs

- LLMの答えは毎回少し違う → 入れ替わりには、文章と関係のないゆらぎも混じる。画面は件数と理由を並べるだけで、判断は利用者に任せる。
- サーバーを再起動すると結果が消える → 結果は一時的なものなので、もう一度試せばよい。画面は404を「結果がありません」として扱う。
- 呼び出しの途中で上限に達する → やり直しで回数が増えたときに起こる。状態を「上限で停止」として終え、結果は返さない。

## Migration Plan

- マイグレーション022は列を足すだけである。既存の行は`purpose`がNULLになり、今までの用途として数えられる。
- `llmCallsPerDay`を設定に書いていない環境は、既定が350回から380回に上がる。書いている環境は変わらない。
