# Design

## Context

左のペインと引き出しの項目は、`packages/client/src/nav.ts` の1つのモデルから描く。
上段の項目は「未読」「すべて」「スター」「AI生成」「最近読んだ記事」「注釈」で、項目の種類（`ListTarget`）ごとに、キー、一覧の絞り込み、一括の既読の範囲が決まる。
サーバーの記事の一覧と一括の既読は、`origin=feed` をすでに受ける。件数のAPIは、未読の総数と生成記事の未読数を返す。
項目ごとの並び順は `list_views` の表に保存し、項目の名前をCHECK制約で縛っている。

## Goals / Non-Goals

**Goals:**

- 「AI生成」と対になる固定の項目「購読フィード」を、WebとAndroidの両方に出す。
- 一覧の操作を「AI生成」にそろえ、項目ごとの特別な分岐を増やさない。

**Non-Goals:**

- 記事の一覧、件数、一括の既読のAPIの変更。
- 「購読フィード」へ移るショートカット。
- LLMの呼び出し。

## Decisions

### 項目の種類とキー

`ListTarget` に `{ type: "feeds" }` を足す。キーは `feeds` で、Webのパスは `/feeds` である。
1つの購読フィードは `feed-12` と `/f/12` なので、区別できる。
ラベルは「購読フィード」で、定数 `FEEDS_LABEL` に置く。設定の画面や確認の文面が、同じ語を1つの購読フィードの意味で使っている。上段の項目として「AI生成」の隣に並ぶので、まとめの一覧であることは位置から分かる。

### 未読数

`counts.unread − counts.generatedUnread` で出し、負にならないよう0で止める。
記事の出所は生成と配信の2つだけなので、差は未読の配信記事の数に等しい。
件数のAPIに項目を足す案もあったが、すでにある2つの数から決まる値であり、足せばAPIの文書と古いアプリとの互換の検討が増える。

### 一覧の操作

絞り込みは `origin: "feed"`、一括の既読の範囲も `origin: "feed"` である。
`hasReadToggle`、`hasListControls`、`hasSortMenu` は除外の列挙で書かれており、`feeds` は何も足さずに「AI生成」と同じ扱いになる。
一括の既読のあとの移動（`nextTarget`）は、上段の項目からはどこへも移らないので、変えない。
既読の項目を隠す処理（`hideEmptyEntries`）は上段の項目を残すので、変えない。

重要度4以上の切り替えは、配信記事に重要度がないため出さない。
WebとAndroidは、この条件を `view !== "feed" && view !== "uncategorized"` と別々に書いている。`feeds` を足すにあたり、共有のモデルに `hasImportanceFilter` を置き、両方がそれを使う。

### 表示の設定

`ListViewTarget` の固定の項目と、設定ファイルの `list` の列挙に `feeds` を足す。
`list_views` のCHECK制約は、SQLiteでは書き換えられない。`031_list_views_feeds.sql` で新しい表を作り、行を写し、古い表を消して名前を替え、索引を作り直す。
`list_views` を参照する表はないので、外部キーの扱いは要らない。

### Androidの引き出し

引き出しは `model.views` から「注釈」だけを除いて描くので、「購読フィード」は何もしなくても出る。
一覧の見出しの表（`TITLES`）に `feeds` を足す。

## Risks / Trade-offs

- 「購読フィード」のラベルは、1つの購読フィードを指す語と同じである。上段の項目の位置と、数の違いで区別する。Issueが指定した名前なので、そのまま使う。
- 古いアプリが `feeds` のキーを知らないまま、新しいサーバーの表示の設定を読む場合がある。知らないキーの行は、どの項目にも当たらず無視される。
- マイグレーションで表を作り直す。既存の行が残ることを、テストで確かめる。
