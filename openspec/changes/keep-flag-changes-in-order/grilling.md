# grilling 記録: keep-flag-changes-in-order

Issue #95（監査ID B-09）では、番号付きの質問のラウンドは行っていない。計画のコメントに、計画が拠る決定を表にして載せた。Issueのオーナーはその計画を`/ok`で承認し、変更の指示はなかった。下の表は、その計画の決定を記録する。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 直す範囲 | issueの「直し方」のうち、#114（`notify-flag-failures`）で済んだ「失敗を知らせる」「巻き戻しの値を一覧の行からも取る」は除く。残りの「実行中の取得を取り消す」「同じ記事への変更を順に送る」を直す | 計画のコメント（承認済み） |
| アプリ（`apps/mobile`）も直すか | 直さない。Webだけを直す。issueの「場所」は`apps/web`だけで、#114でもアプリは別のissueとした | 計画のコメント（承認済み） |
| 上書きを防ぐ方法 | issueの書くとおり、実行中の取得を取り消す。`useDismissAttention`と同じ方法である | 計画のコメント（承認済み） |
| 取り消した取得の扱い | 取り消したキーだけを覚え、既読とスターの変更がすべて終わったあとに取得し直す | 計画のコメント（承認済み） |
| 変更のあとの再取得の時機 | 件数などの再取得も、変更がほかに残っている間は出さず、最後の変更が終わったときにまとめて出す | 計画のコメント（承認済み） |
| 順に送る単位 | 記事ごと。別の記事への変更は待たせない | 計画のコメント（承認済み） |
| 仕様（`openspec/specs`）を変えるか | 変えない。テストで確かめる | 計画のコメント（承認済み） |
| スクロールでの既読と一括の既読 | 触らない | 計画のコメント（承認済み） |
| 計画 | 承認。追加の変更の指示はなし | Issueのコメントの`/ok`（2026-11-14） |

## 後回しにしたもの

- アプリの`useArticleFlags`にも同じ問題がある。別のissueで扱う。
- 変更を送っている最中に始まった60秒ごとの定期の取得は、楽観的な値を一度戻すことがある。変更のあとの再取得か次の定期の取得でサーバーの値にそろうので、扱わない。
