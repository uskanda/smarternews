# Design

## Context

スター、既読、外れの印は`useArticleFlags`で送る。`onMutate`で、すべての一覧と記事のキャッシュに先に反映する。失敗したら送った値の反対に戻し、`onFailed`で知らせる。この失敗の扱いは`notify-flag-failures`で入った。
今は、反映する前に実行中の取得を取り消していない。変更の前にサーバーを読んだ応答が反映のあとに届くと、キャッシュは古い値に戻る。要求も押した順に1つずつ送るとは限らない。動機は`proposal.md`の「Why」を参照する。

## Goals / Non-Goals

**Goals:**

- 変更の前に始まった取得の応答で、押した値が戻らないようにする。
- 同じ記事への変更が、押した順にサーバーへ届くようにする。

**Non-Goals:**

- アプリ（`apps/mobile`）の修正。
- 変更を送っている最中に始まった定期の取得への対処（Risks を参照）。
- スクロールでの既読（`markRead`）と一括の既読。

## Decisions

### 実行中の一覧と記事の取得を取り消す

`onMutate`で、キーが`["articles", …]`の取得と、変えた記事の`["article", id]`の取得のうち、実行中のものを取り消す。取り消しは`cancelQueries`で行い、取得の前の値に戻ってから反映する。`useDismissAttention`と同じ順である。
取り消したキーは覚えておき、変更がすべて終わったあとに、そのキーだけを`exact`で取得し直す。取り消さなかった一覧は取得し直さないので、`j`と`k`で読み進めるときの通信は増えない。

### 最初の読み込みと次のページの読み込みは取り消さない

まだ値のない一覧を取り消すと、変更のあとの再取得まで一覧が出ない。未読の一覧では、そのあいだに開いた記事が既読になるので、再取得した一覧から開いた記事が消える。次のページの読み込みを取り消すと、`fetchNextPage`は前のページのまま終わり、最後の行の先へ進んだキーが最後のページの先頭へ戻ってしまう。
この2つは取り消さず、取得の応答が届いたあとに同じ変更を当て直す。応答は届いた時点でキャッシュの値を置き換えるので、当て直さないと古い値が残る。変更が失敗したあとは当て直さない。値のないクエリと`fetchMeta.fetchMore`のあるクエリを、この扱いにする。

### 再取得は最後の変更が終わったときにまとめて出す

件数、トピック、トピックの統計、スターの一覧、最近読んだ記事の一覧の再取得と、取り消したキーの再取得は、変更がほかに残っている間は出さない。先の変更の再取得が後の変更の保存より先にサーバーを読むと、後の変更の表示を戻すためである。
集めたキーは、最後の変更の`onSettled`でまとめて無効にする。`["articles"]`全体を取得し直すときは、その下の取り消したキーを重ねて出さない。`invalidateQueries`は実行中の取得を取り消して始め直すので、重ねると同じ一覧を2回取得するためである。

### 同じ記事への変更を順に送る

記事のIDごとに、最後の変更の応答で解決する Promise を持つ。`onMutate`は、何かを待つ前に、その記事の前の Promise を変更の順番として受け取る。`onMutate`の中の`await`の長さは実行中の取得の有無で変わるので、待ったあとに受け取ると順序が入れ替わる。
`mutationFn`は順番の Promise を待ってから送る。`mutationFn`は`mutate`に渡したのと同じオブジェクトを受け取るので、順番はそのオブジェクトをキーにして渡す。応答が成功でも失敗でも`onSettled`で次へ進めるので、列の中の1つが失敗しても、後ろの変更は送る。別の記事は別の列なので待たない。
画面への反映は、今と同じく押した時点の`onMutate`で行う。待つのは送信だけである。

### 状態はフックの中に持つ

順番、残っている変更の数、取得し直すキーは`useRef`に持つ。`useArticleFlags`を呼ぶのは`ReaderPage`だけなので、画面の中で1つになる。

### テストでは応答を止める

`renderApp`は`hold(match)`を返す。一致した要求は、サーバーがすぐに答え、画面は`release`まで答えを受け取らない。遅い接続で、変更の前に読んだ応答があとから届く場合を作れる。

## Risks / Trade-offs

- 変更を送っている最中に60秒ごとの定期の取得が始まると、その応答が楽観的な値を一度戻すことがある。変更のあとの再取得か次の定期の取得で、サーバーの値にそろう。窓は要求1回分の長さなので、扱わない。
- `notify-flag-failures/design.md`の Risks は、同じ記事に続けて2つの要求を送り、先の要求だけが失敗した場合を挙げている。順に送るようになったので、2つの要求がサーバーで入れ替わることはなくなった。先の要求だけが失敗すると後の変更の値を反対に戻す点と、定期の取得でサーバーの値にそろう点は変わらない。
- 未読の一覧で、最初の読み込みが届く前に開いた記事は、`kept`に残らない。届いた一覧には既読として出るが、次の取得で一覧から消える。今と同じ動きである。
