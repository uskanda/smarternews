# Design

## Context

`ReaderPage.tsx` の `refresh` は、この訪問で既読にして残している行（`kept`）を捨て、`["articles"]` と `["counts"]` の問い合わせを無効にするだけである。
取り直しの完了を待たず、状態も持たない。
「すべて既読にする」（`markAllRead`）も `refresh` を呼び、既読にした件数を自分で知らせる。
記事の要約には作成日時がなく、サーバーは前回から何件増えたかを返さない。
未読の一覧では、取り直すと既読の行が消え、読み込んでいなかったページの記事が下から繰り上がる。
取り直しの失敗は、一覧の上の `ErrorNotice` がすでに知らせる。

## Goals / Non-Goals

**Goals:**

- 利用者が始めた取り直しの間、進んでいることを見せる。
- 取り直しが終わったら、新しく一覧に入った記事の数を知らせる。

**Non-Goals:**

- サーバーのAPIの変更
- 注釈の一覧の「読み直す」
- 「すべて既読にする」と60秒ごとの自動の取り直しの知らせ

## Decisions

- 件数は純粋な関数 `countNewArticles({ before, after, complete })` で数える。`before` は取り直す前の画面の行のID、`after` は取り直したあとの一覧である。`after` のうち `before` になかった記事を数える。
- ただし、読み込んでいないページが残っていたとき（`complete` が偽）は、`before` の行のうち `after` で最後に現れる位置より後ろの記事を数えない。読み込んでいなかったページからの繰り上がりとみなすためである。このとき `before` の行が `after` に1つもなければ0件とする。
- 前の一覧を最後のページまで読み込んでいたとき（`complete` が真）は、繰り上がる記事がないので、末尾に足された記事も数える。これで、古い順の一覧で全部を読み込んでいた場合は、Q1の弱点が出ない。
- `refresh` は今の動きのまま内側の処理として残し、`markAllRead` はそれを呼ぶ。利用者の操作からは `refreshByUser` を呼ぶ。
- `refreshByUser` は `refreshing` の状態を立て、`fetched` と `kept` のIDを控えてから `refresh` と同じ無効化を `await` する。終わったら、表示中の一覧の問い合わせ（一覧、検索、名前の記事のいずれか）を `client.getQueryState` で読む。失敗の状態なら知らせない。成功していれば、ページの行を並べて件数を数え、画面の下の知らせ（`useToast`）に出す。
- 取り直し中は、ボタンを「読み直し中…」と表示して `disabled` にし、`r` の処理は何もしない。
- 文言は `fetch-now.ts` の0件の文言「新しい記事はありませんでした」にそろえる。

## Risks / Trade-offs

- 古い順の一覧で、読み込んでいないページが残っているとき、新しい記事が読み込み済みの範囲の後ろに入ると、その記事は数えない。→ Q1で受け入れた弱点である。
- 注釈の一覧を開いている間の `r` は、今までどおり取り直すだけで、知らせない。注釈の一覧には自分の「読み直す」があるためである。
- 取り直しの間に一覧を切り替えると、前の一覧の結果を知らせることがある。→ 取り直しは短く、知らせるのは件数だけなので受け入れる。
