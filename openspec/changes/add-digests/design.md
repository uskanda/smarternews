# Design

## Context

動機は `proposal.md` の「Why」を見よ。ここでは、設計を決める今の作りだけを書く。

- LLMの呼び出しは `packages/core/src/llm/runner.ts` の `TaskRunner` だけが行う。1日の上限は `llm_calls` の表の行を数えて判定する。`callsToday` は要約のタスクを除いた行を数え、要約は `summariesToday` が別に数える。
- 配信記事の要約は `packages/core/src/feeds/summarize.ts` の `SummaryWorker` が、実行の順番待ち（`RunQueue`）とは別の直列の処理で作る。
- 時刻での実行は `packages/core/src/runs/scheduler.ts` の `Scheduler` が決める。`latestSlot` が、前回の確認から今までに来た最後の時刻を返す。起動のときは、6時間（`CATCH_UP_MS`）前から確認を始める。
- 生成記事と配信記事は、同じ `articles` の表にある。配信記事の `category_id` は購読フィードのカテゴリの写しで、カテゴリのない購読フィードでは空である。配信記事の `updated_at` は並びの時刻（公開の時刻か取得の時刻）で、保存の時刻は `created_at` にある。
- 保存期間での削除は `packages/core/src/runs/retention.ts` の `purgeExpired` が行う。`Scheduler` が1時間ごとに呼ぶ。

## Goals / Non-Goals

**Goals:**

- 1回のダイジェストのLLMの呼び出しを1回にし、入力を200件の短い文章に抑える。
- 生成記事だけを対象にする問い合わせ（続報の判定、イベントの重複、RSS、180日の削除）に触れない。
- 配信記事の本文と全文をLLMに渡さない。

**Non-Goals:**

- ダイジェストのRSS（grillingのQ5）。
- アプリでの作る時刻の編集と、アプリの「今すぐ作る」。
- 失敗したダイジェストの自動のやり直し。

## Decisions

### 保存

移行 `021_digests.sql` で、表 `digests` を作る。記事の表には入れない。入れると、生成記事だけを対象にする問い合わせのすべてに、由来の条件が要るためである。

| 列 | 内容 |
|---|---|
| `id` | 識別子 |
| `period_start`、`period_end` | 期間の始めと終わり（UTCのISO 8601） |
| `created_at` | 作った時刻 |
| `trigger` | `schedule`、`catch-up`、`manual` のいずれか |
| `slot` | 時刻で作ったときの予定の時刻（`2026-03-02T07:00` の形）。手動では空。空でない値は一意 |
| `executive_summary` | エグゼクティブサマリー |
| `sections` | カテゴリの区画のJSON。区画ごとにカテゴリの識別子、作った時点のカテゴリの名前、行の一覧を持つ。行は文章と根拠の記事の識別子を持つ |
| `article_count` | 入力にした記事の数 |

カテゴリの名前を写して持つ。カテゴリの名前を変えたり削除したりしたあとも、ダイジェストは作ったときの名前で読める。
同じ移行で、全体設定の表へ列 `digest_schedule` を足す。値はJSONの配列で、既定は `["07:00","19:00"]` である。

180日の削除は、`purgeExpired` に `digests` の `created_at` での削除を足す。根拠の記事の行は表の参照で結ばないので、記事が消えてもダイジェストは残る。

### 期間と入力

期間の終わりは、作り始めた時刻である。期間の始めは、最後に保存したダイジェストの `period_end` と、終わりの24時間前の遅いほうである。失敗した回は保存しないので、次の期間は最後に成功したダイジェストの終わりから数える。

入力に入れる記事は次のとおりである。どちらも、無効なカテゴリの記事を除く。無効なカテゴリは画面に出ないためである。

- 生成記事：`updated_at` が期間内のもの。作られた記事と、続報で書き直された記事の両方が入る
- 配信記事：`created_at` が期間内のもの。フィルターで隠した記事と、隠した重複は除く。一覧に出ない記事だからである

選び方は次のとおりである。生成記事を重要度の高い順に並べ、同じ重要度なら `updated_at` の新しい順にする。そのあとに配信記事を `updated_at` の新しい順に並べ、先頭の200件をとる。
1件の入力は次の項目からなる。

- 識別子と由来
- カテゴリの識別子。ないときは空
- タイトルと、生成記事だけは重要度
- 本文の代わりの短い文章

短い文章は次のとおりである。

- 生成記事：要約
- 配信記事：自動の要約。ないときは `content_text` の先頭300文字

配信記事のタイトルは、訳したタイトルがあればそれを使う。全文の列（`full_content`、`full_content_text`）は読まない。
入力が0件のときは、LLMを呼ばず、何も保存しない。

### タスク

`packages/core/src/llm/tasks.ts` に `digest` を足す。入力は、出力言語、読み手情報、今の時刻とタイムゾーン、期間、カテゴリの一覧（区画を作ってよいカテゴリだけ、並び順）、記事の一覧である。
記事の一覧は `<material>` の中に、1行に1件のJSONで置く。
出力のスキーマは次のとおりである。

```text
executiveSummary: string (1〜800文字)
sections: [{ categoryId: int, lines: [{ text: string (1〜200文字), articleIds: int[] }] (1〜5行) }]
```

指示では、行は3行程度、1行は100文字程度とする。スキーマの上限は指示より広くとり、少し長い出力も受け付ける。
`check` は、区画のカテゴリが入力のカテゴリの一覧にあることと、同じカテゴリの区画が2つないことを確かめる。違反はほかのタスクと同じく1回だけやり直す。
入力にない記事の識別子は、`check` では不正にしない。保存の前に捨てる（grillingのQ7）。

カテゴリの一覧に入れるのは、入力に記事のあるカテゴリだけである。カテゴリのない配信記事はカテゴリの識別子が空で、指示で「エグゼクティブサマリーにだけ使う」と伝える。
区画は、保存の前にカテゴリの並び順に並べ直す。

割り当ての既定は `smart`（`config.ts` の `CAPABLE_TASKS`）とする。入力が長く、記事の重要さの判断を含むためである。

### 1日の上限

`limits.digestsPerDay`（既定4、0で止める）を足す。`TaskRunner` に `digestsToday` と `canDigest` を足し、`callsToday` の数えから `digest` を除く。
`#spend` では、`digest` を要約と同じく専用の上限だけで判定する。予算の判定はほかのタスクと同じく行う。
1回目が不正で2回目を呼んだときは、2回と数える。要約の数え方と同じである。

### 作る処理

`packages/core/src/digests/worker.ts` に `DigestWorker` を置く。要約と同じく、実行の順番待ちとは別の直列の処理である。

- `start()` は、確認の始めを6時間前に置いて1回確認し、そのあと30秒ごとに確認する。起動のときの確認で見つけた時刻は、`trigger` を `catch-up` にする
- 確認では、`latestSlot` で前回の確認から今までに来た最後の時刻を求める。その `slot` のダイジェストがまだなければ作る。過ぎた時刻がいくつあっても、作るのは最後の1つだけである
- 作る時刻の一覧が空のときは、時刻では作らない。「今すぐ作る」は一覧が空でも使える。利用者が明示して求めた操作だからである
- `buildNow()` は「今すぐ作る」の処理である。作成中なら `busy` を返す。上限か予算に達していれば `limit` か `budget`、入力が0件なら `empty` を返す。それ以外は作成を始めて `queued` を返し、終わりを待たない。LLMの応答は数分かかることがあるためである
- 失敗は記録して投げない。呼び出しの記録には `TaskRunner` が失敗を残す

### API

- `GET /api/v1/digests`：新しい順の一覧（既定30件、`limit` で最大200件）と、作成中かどうか（`building`）
- `GET /api/v1/digests/:id`：1件。区画と、根拠の記事のうちまだある記事のタイトルと由来（`articles`）を返す。消えた記事の識別子は、行の `articleIds` に残し、`articles` には入れない
- `POST /api/v1/digests`：今すぐ作る。作成を始めたら202と `{"status":"queued"}`、作成中なら409を返す。上限、予算、0件のときは200と、それぞれ `limit`、`budget`、`empty` の値を返す
- `GET /api/v1/providers`：`digestsToday` と、`limits.digestsPerDay` を足す

### 画面

Webは、左のペインの「注釈」の下に「ダイジェスト」を置く。`buildNav` の `views` には入れない。`views` は記事の一覧の項目で、`Shift+J` と `Shift+K` で巡る対象だからである。
画面 `/digests/:digestId?` は、左に一覧、右に選んだダイジェスト（指定がなければ最新）を出す。行の根拠の記事は `/all/<記事の識別子>` へのリンクにする。「今すぐ作る」は画面の上部に置き、作成中は押せなくし、一覧を5秒ごとに読み直す。
設定の画面の全体設定に「ダイジェストを作る時刻」の欄を置く。入力の形は、カテゴリの実行の時刻の欄と同じく、`HH:MM` を「,」か空白で区切る。

アプリは、引き出しの「最近読んだ記事」の下に「ダイジェスト」を置く。画面は `(main)/digests` で、最新のダイジェストと、過去のダイジェストの一覧を出す。行の根拠の記事を押すと、記事の本文の画面を開く。

### 通知

通知の確認（`apps/mobile/src/notifications/check.ts`）で、記事の確認のあとに `GET /api/v1/digests?limit=1` を読む。端末は、最後に知らせたダイジェストの識別子を持つ。
判断は `packages/client/src/notify.ts` の `planDigestNotification` に置き、新しいダイジェストの識別子が持っている値より大きいときに通知を1つ出す。
記録がないとき（有効にした直後と、この変更の前から使っている端末）は、最新の識別子を記録するだけで通知しない。有効にする前からあるダイジェストを知らせないためである。
通知の識別子は `digest` に固定し、前の通知を置き換える。押したときのデータは `{ digestId }` で、アプリはそのダイジェストを開く。

## Risks / Trade-offs

- 配信記事の多い日は、200件に入らない配信記事が出る → 生成記事を先に選ぶのは、重要度のある記事を入力から除かないためである。配信記事は新しい順なので、古いものから外れる。
- `smart` の呼び出しは時間がかかる → 今すぐ作る操作は終わりを待たず、画面は一覧を読み直して完成を知る。
- 6時間の補完で、失敗した回を起動のときにもう1回作ることがある → 1日の上限で回数は抑えられる。
